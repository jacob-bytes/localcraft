# 需求规格说明书（SRS）

**项目**：localcraft — 内网工具 / Skill 共享平台
**版本**：v0.1（待评审）
**目标读者**：需求方、后端/前端开发、运维、测试

---

## 1. 文档目的与范围

### 1.1 目的

本文档定义 localcraft 平台的业务需求、角色权限、功能行为、业务规则与非功能约束，作为设计、开发、测试与验收的唯一依据。文中每条功能需求都有唯一编号（如 `FR-TOOL-05`），用于追溯。

### 1.2 范围

**在范围内**：

- 工具 / Skill 的归档、分类、检索与分发门户
- 个人用户上传、版本管理、可见性授权
- 管理员权限管理、审批流、白名单、下架
- 面向脚本的管理 API 与 API Token
- 单机 systemd 部署、离线双架构打包、备份恢复

**明确不在范围内**（见第 10 章详述）：

- 工具在线执行 / 沙箱运行
- 代码仓库托管、CI/CD 能力
- 部门组织架构与 OA 集成
- 数据可视化大屏与投屏轮播
- 多实例高可用与容器编排

### 1.3 术语

| 术语 | 定义 |
| --- | --- |
| **工具（Tool）** | 平台上的一个归档条目，是分类、检索、授权、审批的基本单位。一个工具拥有 0..n 个版本 |
| **版本（Version）** | 工具的一次具体交付物快照，承载实际的文件/URL/文本内容。带 SemVer 字符串标识 |
| **当前版本** | 工具上唯一处于 `approved` 且对外提供服务的版本，门户下载默认指向它 |
| **历史版本** | 曾经是当前版本、后被新版本取代的版本，保留供回退下载 |
| **待审版本** | 已提交但尚未审批通过的新版本，此时旧版本仍在服务 |
| **Skill 包** | 一种特殊的 zip 交付物，解压后根目录含 `SKILL.md`，平台会解析并做预览 |
| **免审白名单** | 一组用户，其上传内容跳过审批直接发布 |
| **可见性** | 工具对谁可见、可下载的三级模型：public / restricted / private |
| **ACL** | 针对 `restricted` 可见性的授权条目，主体为用户或用户组 |
| **API Token** | 供脚本调用管理接口使用的高熵长效凭证，带权限范围（Scope） |

│   (普通/审批/超管)  │                                          │
│                    ▼                                          │
│              ┌───────────┐        ┌──────────────────────┐   │
│   自动化脚本 ─▶│  nginx    │───────▶│  FastAPI (systemd)   │   │

│                                             │                  │

平台是一个**单体应用**：前端构建产物由后端托管，不单独部署前端服务。这是为了减少组件数量、降低内网运维成本，代价是无法独立扩缩前端。

## 3. 角色与权限

### 3.1 角色定义

采用 RBAC。一个用户可拥有多个角色，权限取并集。

| 角色代码 | 名称 | 定位 | 典型使用者 |
| --- | --- | --- | --- |
| `superadmin` | 超级管理员 | 平台最高权限，管理用户、角色、系统设置、API Token | 平台负责人，1~2 人 |
| `approver` | 审批管理员 | 审批工具上架、下架工具、管理分类标签、查看审批历史 | 各方向技术负责人，3~5 人 |
| `user` | 普通用户 | 浏览、下载、上传自己的工具 | 全体研发同事 |
| `viewer` | 只读访客 | 只能浏览 `public` 工具，不能下载受限内容、不能上传 | 审计人员、外部协作方 |

### 3.2 权限矩阵

| 能力 | viewer | user | approver | superadmin |
| --- | :---: | :---: | :---: | :---: |
| 登录、查看门户、搜索 | ✅ | ✅ | ✅ | ✅ |
| 查看 `public` 工具详情 | ✅ | ✅ | ✅ | ✅ |
| 下载 `public` 工具 | ❌ | ✅ | ✅ | ✅ |
| 查看/下载被授权的 `restricted` 工具 | ❌ | ✅ | ✅ | ✅ |
| 查看自己的 `private` 工具 | — | ✅ | ✅ | ✅ |
| 创建 / 编辑 / 提交自己的工具 | ❌ | ✅ | ✅ | ✅ |
| 删除自己的工具 | ❌ | ✅ | ✅ | ✅ |
| 查看审批队列 | ❌ | ❌ | ✅ | ✅ |
| 批准 / 驳回 / 下架 / 重新上架 | ❌ | ❌ | ✅ | ✅ |
| 管理分类、标签 | ❌ | ❌ | ✅ | ✅ |
| 查看审批历史 | ❌ | ❌ | ✅ | ✅ |
| 查看全部工具（含他人 `private`） | ❌ | ❌ | ❌ | ✅ ¹ |
| 管理用户、角色、用户组 | ❌ | ❌ | ❌ | ✅ |
| 管理免审白名单 | ❌ | ❌ | ❌ | ✅ |
| 修改系统设置（审批开关等） | ❌ | ❌ | ❌ | ✅ |
| 签发 / 吊销 API Token | ❌ | ❌ | ❌ | ✅ |
| 批量导入 / 导出 | ❌ | ❌ | ❌ | ✅ |
| 转移工具负责人 | ❌ | ❌ | ❌ | ✅ |

> ¹ 受系统设置 `portal.allow_admin_view_private` 控制，默认开启。关闭后超级管理员也看不到他人 `private` 工具的**内容**，但仍能看到其存在（用于配额统计）。此点见待确认事项 Q1。

**明确不给 approver 的权限**：用户管理、系统设置、API Token。理由是审批与授权应当职责分离，避免审批人自行放行自己的工具。（若实际场景中审批管理员也需要上传，用 `user` + `approver` 双角色即可。）

### 3.3 权限实现约束

- 权限判定必须在**服务端**完成，前端隐藏按钮仅作体验优化，不构成安全边界。
- 所有涉及资源的接口都必须做**对象级授权检查**，而不只是角色检查。例如 `approver` 可以审批任意工具，但 `user` 调用 `PATCH /tools/{id}` 时必须校验 `owner_id == current_user.id`。
- 建议实现一个统一的 `authorize(user, action, resource)` 函数并集中测试，避免散落在各处的 `if` 判断。

## 4. 核心业务对象与状态机

### 4.1 工具状态机

```
                  ┌──────────┐
     创建 ────────▶│  draft   │◀──────── 用户撤回提交
                  └────┬─────┘
                       │ 提交(submit)
                       ▼
                  ┌──────────┐
     修改后重提 ──▶│ pending  │
        ▲         └────┬─────┘
        │              │
        │      ┌───────┴────────┐
        │      │ 批准            │ 驳回(必填理由)
        │      ▼                ▼
   ┌────┴───────┐         ┌──────────┐
   │  rejected  │         │ approved │◀─────────┐
   └────────────┘         └────┬─────┘          │
                               │                │ 重新上架
                   上传新版本   │                │ (relist)
                               ▼                │
                       ┌───────────────┐   ┌────┴─────┐
                       │pending_update │   │ offline  │
                       └───────┬───────┘   └────▲─────┘
                               │                │
                    批准 ──────┘                │ 下架(offline, 必填理由)
                    (新版本转正, 旧版本转历史)    │
                               └────────────────┘
```

| 状态 | 含义 | 门户可见 | 可下载 |
| --- | --- | --- | :---: |
| `draft` | 草稿，仅本人与超管可见 | 否 | 否 |
| `pending` | 首次提交，等待审批 | 否（仅本人在个人中心可见进度） | 否 |
| `approved` | 已发布 | 是（按可见性规则） | 是 |
| `rejected` | 已驳回 | 否 | 否 |
| `pending_update` | 已发布，但存在待审新版本 | 是（展示当前版本） | 是（下载当前版本） |
| `offline` | 已下架 | 否（超管可见） | 否 |

**状态迁移规则**：

| 迁移 | 触发者 | 前置条件 | 副作用 |
| --- | --- | --- | --- |
| `draft → pending` | owner | 必填字段完整、至少有一个版本内容 | 写审批记录 `submit` |
| `pending → draft` | owner | 撤回 | 写审批记录 `withdraw` |
| `pending → approved` | approver/超管 或 系统自动 ¹ | — | 版本转 `approved` 并设为当前版本；`published_at` 落时间；写记录 `approve` |
| `pending → rejected` | approver/超管 | **理由必填** | 版本转 `rejected`；写记录 `reject` |
| `rejected → pending` | owner | 修改后重新提交 | 写记录 `resubmit` |
| `approved → pending_update` | owner | 上传新版本 | 新版本 `pending`；**当前版本保持 `approved` 不变** |
| `pending_update → approved` | approver/超管 或 系统自动 ¹ | — | 新版本转正为当前版本，原当前版本转 `superseded` |
| `pending_update → approved`（驳回路径） | approver/超管 | 理由必填 | 待审版本转 `rejected`，工具**退回 `approved`**，当前版本不变，写记录 `reject` |
| `approved → offline` | approver/超管 | **理由必填** | 写记录 `offline`；门户下架 |
| `offline → approved` | approver/超管 | 理由选填 | 写记录 `relist` |

> ¹ 自动批准的条件：系统设置 `approval.mode = auto_approve_all`，或该用户命中免审白名单且 `approval.whitelist_enabled = true`。自动审批时 `actor` 记为 `system`，审批记录中标注「系统自动放行」及命中的规则。

### 4.2 版本状态机

```
pending ──批准──▶ approved ──被更新版本取代──▶ superseded
   │
   └──驳回──▶ rejected
```

- 一个工具在任意时刻**最多只有一个** `approved`（即当前版本）。
- `superseded` 与 `rejected` 版本不对外提供下载（见下方规则）。
- **历史版本保留规则**：`superseded` 版本按创建时间倒序，只保留最近 **10** 个（数量可配）。超出部分**物理删除**其存储文件，数据库行转为 `purged` 状态保留审计痕迹（不删行，避免审批历史产生悬空外键）。

### 4.3 可见性判定算法

给定 `(当前用户 U, 工具 T)`，判定是否可见：

```
1. 若 T.status 不在 [approved, pending_update, offline] 中：
      仅当 U 是 owner、或 U 是 superadmin、或（U 是 approver 且 T.status ∈ [pending, rejected]）时才可见
      —— approver 的分支是 M3 checkpoint 补入的（2025-03 修订）。原文只给了 owner 与 superadmin，
         与 FR-APPR-06「审批人可在队列中直接进入工具详情预览」自相矛盾：审批人看不到待审工具，
         就无法预览。但 approver **不得**看到 `draft` —— 草稿是用户尚未提交的未完成工作，
         没有任何审批理由需要访问（`contracts/CONTRACT.md` §15.5）
2. 若 U 是 T.owner                        → 可见、可下载
3. 若 U 是 superadmin 且 allow_admin_view_private → 可见、可下载
4. 若 T.visibility == 'public'            → 可见、可下载（viewer 角色只能可见不可下载）
5. 若 T.visibility == 'private'           → 不可见
6. 若 T.visibility == 'restricted'：
      遍历 T 的 ACL 条目：
        条目主体是用户且 == U.id          → 命中
        条目主体是用户组且 U 属于该组      → 命中
      命中 → 可见、可下载；否则不可见
```

**性能要求**：门户列表查询必须把上述判定**下推到 SQL 的 WHERE 子句**（用 `EXISTS` 子查询 join `tool_acl` + `group_members`），不得先查全量再在 Python 里过滤。列表接口的 P95 在百人规模下应低于 300ms。

## 5. 功能需求

### 5.1 认证与账号（AUTH）

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-AUTH-01 | 用户以「用户名 + 密码」登录。登录成功返回 access token（默认 30 分钟有效）并通过 HttpOnly + Secure + SameSite=Lax Cookie 下发 refresh token（默认 7 天） | P0 |
| FR-AUTH-02 | 无自助注册入口。所有账号由超级管理员创建，或通过批量导入接口创建 | P0 |
| FR-AUTH-03 | 新账号或被重置密码的账号，`must_change_password = true`；此类用户登录后强制跳转改密页，未改密前调用任何业务接口返回 `403 PASSWORD_CHANGE_REQUIRED` | P0 |
| FR-AUTH-04 | 密码策略：长度 ≥ 10，至少包含大写字母、小写字母、数字、符号中的 3 类；不得与用户名相同。强度不足时返回明确的逐条错误提示 | P0 |
| FR-AUTH-05 | 密码使用 Argon2id 哈希存储（备选 bcrypt cost ≥ 12）。数据库中任何位置都不得出现明文或可逆密码 | P0 |
| FR-AUTH-06 | 连续登录失败 5 次锁定账号 15 分钟，锁定期内即使密码正确也拒绝并提示剩余锁定时间。失败计数在成功登录后清零 | P0 |
| FR-AUTH-07 | 支持主动登出，登出后 refresh token 立即失效（服务端吊销） | P0 |
| FR-AUTH-08 | 认证方式可插拔：定义 `AuthProvider` 抽象接口（`authenticate` / `get_user_info` / `on_login`），本地实现为 `LocalAuthProvider`，并预留 `OIDCProvider` 桩实现。切换方式通过配置项 `auth.provider` 完成，不修改业务代码 | P1 |
| FR-AUTH-09 | 提供 `GET /api/v1/auth/provider` 返回当前启用的认证方式与登录页需要渲染的字段，供前端适配 | P1 |
| FR-AUTH-10 | 用户可修改自己的密码，需校验旧密码 | P0 |
| FR-AUTH-11 | 用户可修改自己的显示名与邮箱 | P1 |
| FR-AUTH-12 | 超级管理员可强制下线某用户（吊销其全部 refresh token） | P2 |

### 5.2 用户与权限管理（IAM）

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-IAM-01 | 超级管理员可创建用户，字段：用户名（唯一、不可改）、显示名、邮箱（选填）、初始密码、角色列表 | P0 |
| FR-IAM-02 | 超级管理员可编辑用户（显示名、邮箱、角色、启用/禁用状态） | P0 |
| FR-IAM-03 | 超级管理员可重置用户密码，重置后强制该用户下次登录改密 | P0 |
| FR-IAM-04 | 用户列表支持按用户名/显示名模糊搜索、按角色与状态筛选、分页 | P0 |
| FR-IAM-05 | 禁用用户后其所有会话立即失效，登录被拒绝并提示「账号已禁用」 | P0 |
| FR-IAM-06 | **不得删除用户**，只能禁用。原因是用户与工具、审批记录、下载记录存在外键关联，删除会破坏审计链 | P0 |
| FR-IAM-07 | 系统必须始终至少保留一个启用状态的 `superadmin`。尝试禁用或降级最后一个超管时返回 `409 LAST_SUPERADMIN` | P0 |
| FR-IAM-08 | 超级管理员不得禁用或降级自己的账号（防止自我锁死） | P0 |
| FR-IAM-09 | 支持 CSV / JSON 批量导入用户，字段：用户名、显示名、邮箱、角色、初始密码（可留空则生成随机密码并回显）。导入需返回逐行成败报告，部分失败不影响成功行 | P1 |
| FR-IAM-10 | 支持导出用户列表为 CSV，包含角色与状态，**不含密码哈希** | P1 |
| FR-IAM-11 | 超级管理员可将某个工具的负责人转移给另一用户（离职交接场景）。转移需在 `approval_records` 中留痕（`action = transfer_owner`），并同步校验原负责人的存储配额扣减与新负责人的配额增加 | P1 |

### 5.3 用户组（GRP）

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-GRP-01 | 超级管理员可创建、编辑、删除用户组，字段：组名（唯一）、描述、启用状态 | P0 |
| FR-GRP-02 | 支持往组内添加/移除成员，成员列表可分页与搜索 | P0 |
| FR-GRP-03 | 用户组仅用于**可见性授权**，不承载权限角色。不实现「组即角色」 | P0 |
| FR-GRP-04 | 删除用户组时，必须提示该组当前被哪些工具的 ACL 引用，并要求二次确认。确认后连带清理相关 ACL 条目 | P0 |
| FR-GRP-05 | 一个用户可属于多个组 | P0 |
| FR-GRP-06 | 组内成员变更后，可见性判定立即生效，无需重新登录（因为权限在每次请求时实时判定，不做 token 内嵌缓存） | P0 |

### 5.4 分类与标签（TAX）

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-TAX-01 | 分类为**固定一级分类**，由审批管理员或超管维护。字段：名称（唯一）、slug、描述、图标标识、排序权重、启用状态 | P0 |
| FR-TAX-02 | 分类禁止物理删除。若有工具引用，删除操作返回 `409 CATEGORY_IN_USE` 并列出引用数；无引用时允许删除，采用软删除（`is_active = false`） | P0 |
| FR-TAX-03 | 标签为自由标签，用户上传工具时可从既有标签中选择，也可新建。标签名做归一化处理（去首尾空格、转小写、全角转半角），避免 `Python` 与 `python` 并存 | P0 |
| FR-TAX-04 | 单个工具最多绑定 8 个标签 | P0 |
| FR-TAX-05 | 审批管理员可将两个重复标签合并，合并后引用关系转移到目标标签 | P1 |
| FR-TAX-06 | 平台定期清理零引用标签（或提供手动清理入口），避免标签表膨胀 | P2 |
| FR-TAX-07 | 门户展示分类时显示每个分类下的**当前用户可见的**工具数量 | P1 |

### 5.5 工具创建与编辑（TOOL）

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-TOOL-01 | 用户可创建工具，必填：名称、简介（≤500 字）、详情（Markdown）、类型、分类；选填：标签、封面图 | P0 |

## 7. 非功能需求

### 7.1 性能

| 编号 | 需求 |
| --- | --- |
| NFR-PERF-01 | **支持 100 名注册用户。在 20 并发在途请求下，门户列表与详情接口 P95 < 500ms；单机峰值吞吐 ≥ 150 req/s。** 详见下方「容量基线」|

> **NFR-PERF-01 的口径修订（M4 checkpoint，2025-03）**
>
> 本条早先写作「按 100 并发在线用户规划，P95 < 300ms」。**这个口径是错的，责任在监控方**：
> 原始需求是「百人级别的访问量，并发访问也按照百人来规划」，指的是 **100 名注册用户**，
> 被误写成了「100 个并发在途请求」，两者差一个数量级。实测证明后者不成立。
>
> **实测并发阶梯**（macOS 笔记本 + 沙箱直连，无 nginx；`scripts/m4-drill-perf.sh` 可复跑）：
>
> | 并发 | P50 (ms) | P95 (ms) | req/s |
> | --- | --- | --- | --- |
> | 1 | 8 | 9 | 124 |
> | 5 | 25 | 29 | **193（峰值）** |
> | 10 | 107 | 136 | 98 |
> | 20 | 279 | 379 | 70 |
> | 50 | 748 | 1098 | 65 |
> | 100 | 1414 | 1586 | 70 |
>
> **拐点在 10~15 并发**，不是 100。
>
> **根因（M5 后复测修订，2025-03）**：此前本文档写「瓶颈是单进程 CPU/GIL，源于 SQLite 单写者 → 单 worker」——
> **这条因果链未被证实，已推翻**。实测：
> - 纯 DB 访问在 c=20 下可跑 **3968 req/s**（SQLite 不是瓶颈）
> - `/healthz` 在 c=20 下可跑 **3543 req/s**（网络与事件循环不是瓶颈）
> - 序列化 24 条只要 **0.242 ms**（不是瓶颈）
> - 真正现象：**CPU 时间随并发从 4.87 ms 放大到 56.28 ms（11.6 倍）** —— 是「工作量放大」而非饱和
>
> 放大来源怀疑在**异步栈（aiosqlite + greenlet 桥接 + 线程池）在高并发下的上下文切换开销**，
> 尚需对比实验确认。完整数据、被推翻的旧结论与建议的验证顺序见 [`docs/11-优化点分析.md`](11-优化点分析.md)。
>
> **容量的正确理解**：100 名注册用户、峰值约 20~30 人同时打开页面，在途并发通常为 5~15。
> 按每人 10 秒一次请求估算，100 人峰值约 10 req/s，相对 193 req/s 的峰值有约 19 倍余量。
>
> **扩展触发条件**：持续在途并发 > 20，或写事务 > 50/s → 迁 PostgreSQL 并放开多 worker。

> **成本定位（M5 实测，同机 c=20）**：`/healthz` P95 15ms → 列表 `page_size=1` 116ms →
> `page_size=24` 475ms → `page_size=48` 805ms。**成本随条目数近似线性**，说明瓶颈是
> **每个条目的 CPU 开销**（ORM 实例化 → Pydantic 校验 → JSON 编码）在单进程内受 GIL 限制；
> `facets` 只占约 20%。**因此若将来需要更高并发，正确方向是降低每条目序列化成本，
> 而不是继续优化 facets 聚合。** 详见 [`docs/09-勘误与已知限制.md`](09-勘误与已知限制.md) §10。
>
> 生产环境的真实数字必须在目标硬件（openEuler + nginx）上重测，
> 上面的数字**不能代表生产性能**。容量基线与扩展路径见 `docs/08-运维手册.md`。
| NFR-PERF-02 | 文件下载吞吐受限于磁盘与网卡，不做应用层限速；必须使用 sendfile 零拷贝路径 |
| NFR-PERF-03 | 上传 200 MB 文件在千兆内网下应 < 30 秒，前端可取消 |
| NFR-PERF-04 | 首屏 JS 体积（gzip 后）控制在 500 KB 以内，路由级代码分割 |
| NFR-PERF-05 | 服务端不得在单次请求中执行超过 5 秒的同步阻塞操作（Skill 解压与哈希计算必须异步化或限制在合理体积内） |

| AC-13 | A 创建 `restricted` 工具并授权给用户组 G | G 的成员可见可下载；非 G 成员在门户列表与搜索中均看不到 |

## 11. 交付切分：MVP 与二期

你已确认「不急，以质量和可维护性为先」。建议按以下里程碑推进，每个里程碑都是**可独立验证**的完整切片。

### M1 — 地基（可运行的空壳）

- 前后端工程骨架、目录结构、构建脚本
- SQLAlchemy 模型 + Alembic 初始迁移（全部表结构一次建好）
- 本地认证 + RBAC + 强制改密
- 应用配置层（环境变量 + 系统设置表）
- systemd + nginx + 离线 wheel 打包脚本
- 健康检查、日志、request_id

**验证**：能在 openEuler 上部署起来，用超管登录，看到空门户。

### M2 — 核心闭环（MVP，最有价值）

- 工具 CRUD（四种类型）
- 文件上传、存储、SHA256、下载（含 Range）
- 图片上传与缩略图
- Skill 包解析与安全防护
- 版本管理（上传新版本、历史版本、10 份淘汰）
- 可见性三级 + ACL
- 审批流（提交/批准/驳回/下架/上架/审批历史）
- 全局审批开关 + 免审白名单
- 门户首页（搜索、分类、标签、排序、分页）
- 工具详情页（按类型差异化）

**验证**：第 9.1 节 AC-01 ~ AC-13、AC-21 全部通过。

### M3 — 管理与脚本化

- 管理控制台全部页面（用户、组、分类、标签、全站工具、Token、设置）
- API Token 机制与 Scope 校验
- 批量导入导出接口
- CLI 管理工具
- 统计与热门排序（内存聚合落库）
- 存储配额
- 工具负责人转移（含配额重算与审批留痕）

**验证**：AC-14 ~ AC-20 通过；能用 curl 脚本完成一次完整的「建用户 → 建工具 → 审批 → 导出」流程。

### M4 — 打磨与交付

- 深色主题、响应式、骨架屏、空态/错误态
- 回收站、标签合并、零引用清理
- 备份脚本 + 恢复演练 + 监控指标
- 双架构离线发布包制作与实机验证
- 完整文档（用户手册、管理员手册、运维手册）

**验证**：AC-22 ~ AC-24 通过；在 x86_64 与 aarch64 上各做一次全新部署。
