## 1. 这份文档是什么

后端 M5 在交付时附了一份**去重后的 36 条「文档 vs 实现」不一致清单**（来源：三份手册的核对 +
前后端两轮的联调）。本文件是对这 36 条的**处置结论**。

**为什么不直接改原文**：这些不一致分散在 `docs/01`~`docs/05` 的 60 余处，逐条原地改会产生
大量碎片编辑且难以复核。改用勘误表可以：

1. 保留完整的审计痕迹（谁在什么时候、基于什么证据改了哪一条）
2. 让读者一次看全「哪些说法不可信、正确的是什么」
3. 避免在勘误过程中引入新的不一致

**权威顺序**（`contracts/CONTRACT.md` §15.6 + §19.4）：

```
backend/openapi.json   ← 接口形状的唯一权威
   ↓
docs/09（本文件）        ← 对既有文档的勘误，效力高于被勘误的原文
   ↓
docs/01 ~ docs/05       ← 语义、业务规则、错误码、架构决策
```

**读法**：如果你在 `docs/01`~`docs/05` 里读到与本文冲突的说法，**以本文为准**。

> 这是一个「静默跳过导致功能缺失」的典型案例。**安装脚本对应当存在却缺失的交付件，
> 应当报错而不是跳过。**

## 7. 改实现（已列入 M6）

### 7.1 `GET /api/v1/directory` —— 新增 1 个接口（**对 92 冻结的刻意例外**）

**问题**：FR-ACL-02 与 `docs/04` §6.7 要求「搜索用户/组后添加」到 ACL，
但普通用户**没有任何可用的搜索接口** —— `GET /admin/users` 与 `GET /admin/groups` 都要求超管。
结果：设置了 `restricted` 可见性的用户必须**手填数字 ID**才能授权，功能实际不可用。

**裁定：新增 `GET /api/v1/directory`**，接口面从 92 变为 **93**。

- 任何已登录用户可调用
- 参数：`?q=`（前缀/模糊匹配）、`?type=user|group`（可选，默认两者）
- 返回**最小披露**：用户只返回 `{id, username, display_name}`；
  用户组只返回 `{id, name, member_count}`
- 不返回邮箱、状态、角色、最后登录时间等

**为什么值得破例**：92 冻结的目的是防范围蔓延，而这是一个**功能空洞**（feature hole），
不是新功能。在 100 人内网里，工具作者本来就能看到彼此的名字，最小披露是安全的。
不修则 FR-ACL-02（P0）无法交付。

### 7.2 让 ACL 的 `can_download` 真正生效

**问题**：`tool_acl.can_download` 前后端都存，但**可见性 SQL 与下载判定都不读它**
（已核实：`deps.py` 里的 `can_download` 是 `Principal` 的角色派生属性，与 ACL 无关）。
结果是「取消允许下载」的配置**静默无效**，而 `docs/03` §3.11 把它描述为生效字段。

**裁定：实现它。** 理由与 §18.4 修死桩路由相同 —— **一个被文档描述、被 API 接受、
却毫无作用的字段，比没有这个字段更糟**。

- 下载授权在通过可见性检查后，追加判断：若命中的 ACL 条目 `can_download=false` → 拒绝
- 语义：可见（能看详情）但不可下载，用于「让人知道有这个工具，但下载需另行申请」
- `owner` 与 `superadmin` 不受此限
- 默认值 `true`，**对既有数据无行为变化**

### 7.3 `revoke-sessions` 应一并吊销该用户的 API Token

**问题**（监控方实测确认）：`POST /admin/users/{id}/revoke-sessions` 返回 200 之后，
该用户签发的 API Token **仍然可用**。

```
建 Token 后可用: 200
revoke-sessions → HTTP 200
revoke 后同一 Token: 仍可用!     ← 问题
```

管理员的预期是「把这个人踢出去」，会话与 Token 应当一起失效。

**裁定：扩展 `revoke-sessions` 的行为**，同时吊销该用户签发的全部 API Token
（复用已有的 `admin_user_service.revoke_user_tokens`）。**不新增接口**，
这也让 `docs/05` §13.8 的表述对**管理界面**成立，不再只是 CLI 能力。

> SRS FR-IAM-05 在「禁用用户」时已经要求两者同时失效，此处只是把同一语义补到
> 「强制下线」这个更轻的动作上。

### 7.4 `orphan_file_count` 恒为 0 → 接线

`StorageStatsResponse.orphan_file_count` 已声明，但 `stats_service` 从不设置它。
孤儿文件清理任务已能统计数量，**把它接进 `/admin/stats/storage`**。

（备选是删字段；选接线，因为管理员确实需要知道有无孤儿文件。）

### 7.5 删除最后一个待审版本时，工具状态要回落

**问题**：`pending_update` 状态下删除待审版本后，工具仍停在 `pending_update`，
而 `pending_version_id` 已为空 —— 状态与数据不一致。且前端「我的工具」对
`pending_update` 显示「撤回提交」，但 `WITHDRAWAL` 只含 `pending`，点击得
`409 STATE_CONFLICT`（真实可用路径是删除该待审版本）。

**裁定**：

- **后端**：删除版本后，若工具不再有待审版本，状态回落为 `approved`
  （若从未发布过则回 `draft`）
- **前端**：`pending_update` 的操作文案改为「撤回待审版本」，走
  `DELETE /me/tools/{id}/versions/{version}`（该接口在 92 内），不再调用 withdraw

### 7.6 源码注释同步（1 处）

`app/services/tool_service.py` 的注释仍写「翻页时整个 facets 键省略」，
与实现（始终返回、`page>1` 为 `null`）矛盾。**文档已改，注释同步改。**

## 10. 性能：优化未达标的结论（保留完整证据链）

监控方复跑确认，并**撤销自己在 §18.3 的优化假设**。

### 10.1 做了什么、效果如何

| 优化 | 结果 |
| --- | --- |
| 合并 facets 两条聚合为一条（3 条 SQL → 2 条） | 查询数下降，**延迟无可测收益** |
| facets 30 秒短时缓存（键含可见性哈希） | 热态查询数 2 → **0**，**延迟无可测收益** |
| N+1 排查 | **本来就没有 N+1**（`lazy="joined"` + `lazy="selectin"`），无可优化空间 |

**c=20 的 P95：优化前 438ms → 优化后 518ms（噪声范围内，方向甚至略差）。验收 21 未达成。**

### 10.2 成本定位实验（这是本轮最有价值的产出）

同一机器、c=20：

| 请求 | P95 (ms) | req/s |
| --- | --- | --- |
| `/healthz` | 15 | 3114 |
| 列表 `page_size=1` | 116 | 211 |
| 列表 `page_size=12` | 305 | 93 |
| 列表 `page_size=24` | 475 | 56 |
| 列表 `page_size=48` | 805 | 34 |
| 列表 `page_size=24&page=2`（不算 facets） | 383 | 69 |

**两条结论**：

1. **成本随条目数近似线性**（1→48 时 P95 从 116 涨到 805ms）
   → 瓶颈是**每个条目的 CPU 开销**：ORM 实例化 → Pydantic 校验 → JSON 编码，
   全在单进程里受 GIL 限制
2. **facets 只占约 20%**（56 vs 69 req/s）
   → 监控方选的优化目标**错了**。减少数据库负载换不成延迟，因为进程已 CPU 饱和

> ### ⚠ 本节结论已被后续实测修正（2025-03）
>
> §10.2 的成本定位实验本身是对的，但它**只覆盖了「单请求内的成本结构」**
> （按 `page_size` 梯度），**没有做「同一请求在不同并发下的成本对比」**，
> 因此把一个**并发相关的现象**误读成了串行成本结构。
>
> 监控方随后补做了并发维度测量，发现：**CPU 时间随并发从 4.87 ms 放大到 56.28 ms（11.6 倍）**，
> 而纯 DB 访问能跑 3968 req/s、`/healthz` 能跑 3543 req/s、序列化 24 条只要 0.242 ms。
> **SQLite 与序列化都不是瓶颈**，放大来源怀疑在异步栈本身。
>
> **因此 §10.3 里「若需要更高并发，正确方向是降低每条目序列化成本」这条建议方向偏了。**
> 完整数据与被推翻的结论见 [`docs/11-优化点分析.md`](11-优化点分析.md)。
>
> **新增方法论要求**：性能结论必须同时给出「随参数变化」与「随并发变化」两组数据。

### 10.3 裁定与后续

- **接受现实**：`docs/01` NFR-PERF-01 已重新基线为
  「100 名注册用户 / 20 并发 P95 < 500ms / 峰值 ≥ 150 req/s」
- **保留 facets 缓存**：它确实把数据库查询数从 3 降到 2（冷）/ 0（热）。
  这对**将来写压力上升或迁 PG 后**有意义。但**不宣称它改善了延迟**
- **如果将来真的需要更高并发**，正确方向是**降低每条目序列化成本**
  （例如列表项绕过 Pydantic 校验直接构造、或改用更轻的序列化路径），
  **不是**继续优化 facets。这是一个明确的、可执行的下一步
- `database is locked` 在全部压测（读压测 + 写加压至并发 40）中出现 **0 次** ——
  印证瓶颈不是 SQLite 写锁

### 10.4 50 秒的诚实不是缺点

M5 做了监控方裁定的两项优化、实测无效、**如实报告并附成本定位实验**，
而不是用缓存把数字做漂亮。**这正是验收想要的证据质量。**

## 11. 首次公开推送暴露的验证方法缺陷（已修）

仓库开源后第一次跑 GitHub Actions，**后端 job 红了，而本机是全绿的**。
排查结论：不是环境玄学，是测试套件依赖了**未入库的本地产物**，
本机的「全绿」有一半是假的。两类原因：

### 11.1 两处硬编码 `backend/.venv/bin/python`

`tests/test_cli.py` 与 `tests/test_m3_admin.py` 用子进程跑真实 CLI 与真实
`alembic` 迁移，解释器路径写死为 `backend/.venv/bin/python`。
后果是这套测试**只在开发者本机建过 venv 时才跑得过**：
CI 用 `setup-python` 提供解释器（没有 `.venv`），全新 clone 也没有，
两边都直接 `FileNotFoundError`。

而这条依赖从来不是测试的本意 —— 要守的不变量是「CLI 跑在与目标机一致的
Python 3.11 上」（README D34），用 `sys.executable` 同样能断言。
**已改为 `sys.executable`**，`test_venv_python_is_311` 相应改名
`test_cli_python_is_311`。

### 11.2 一个断言只有 `web/dist` 存在时才「通过」

`tests/test_m3_cov.py::test_group_missing_and_duplicate_paths` 断言
`GET /api/v1/admin/groups/999999` 返回 **404**。实际上：

- docs/03 §4.4 对单组**只定义了 PATCH 与 DELETE**，没有 GET。
  所以正确的 HTTP 语义是 **405**（路径存在、方法不允许），不是 404。
- 本机能过，是因为 `web/dist` 存在时 SPA 兜底 `GET /{full_path:path}`
  把这条件请求接走了，对 `/api` 前缀返回 JSON 404，**掩盖了真实状态码**。
- CI 上没有构建产物、不注册兜底路由，于是 405 立刻暴露。

### 11.3 更深一层：API 的可观察行为取决于前端构建产物在不在

上面那个 404/405 的差异**本身就是缺陷**，不只是测试写错：
同一个请求，`web/dist` 存在时得 404、不存在时得 405。
而 CI 没有 dist、开发者本机通常有 —— 两边 API 行为不一致。

根因是 SPA 兜底用了一般的 `@application.get("/{full_path:path}")`。
Starlette 的路由语义是「先找路径+方法都匹配的；全都不匹配时，
若有路径匹配而方法不匹配的路由则 405，否则 404」，
一个无差别的 GET 兜底会让**所有** GET 都在兜底处匹配成功，
API 的 405 再也没机会产生。

**已修**：新增 `_SpaFallbackRoute(Route)`，在**匹配阶段**就把
`api/`、`docs`、`openapi.json` 等非 SPA 前缀判为 `Match.NONE`。
现在 405 固定为 405、未匹配的 API 路径仍为 JSON 404（docs/03 §6.5 不变），
**且与构建产物无关**。

### 11.4 顺带修掉一个会静默失效的守卫

`test_spa_fallback_is_the_only_non_api_catch_all` 原先靠
`isinstance(route, APIRoute)` 收集兜底路由。兜底一旦从 `APIRoute`
换成普通 `Route`，这个集合就变成**空的**，测试在空集合上空转通过 ——
守卫静默失效，正是它想防的那类事。

**已修**：遍历器同时识别普通 `Route`，并新增对「兜底路由不得匹配非 SPA 前缀」
的逐条断言；`test_contract_misc.py::test_spa_fallback_serves_index_for_client_routes`
（自建 dist，因此在任何环境下都真的会跑）也补了端到端的 405 断言。

### 11.5 CLI help 断言依赖 Rich 的终端渲染

上面两类修完后 CI 仍红，换了个失败点：

```
FAILED tests/test_cli.py::test_create_superadmin_from_stdin
assert '--password-stdin' in help_result.stdout
```

实际 stdout 是 Rich 渲染的 help 面板（**带 ANSI 转义**），但里面没有该选项名。

**根因（已定位并本地复现）**：Typer 的 `rich_utils` 在模块导入时做这样的判断——

```python
FORCE_TERMINAL = (
    True if getenv("GITHUB_ACTIONS") or getenv("FORCE_COLOR") or getenv("PY_COLORS") else None
)
```

GitHub Actions 会设 `GITHUB_ACTIONS=true`，于是 Typer **强制把非 TTY 的输出当终端渲染**；
再叠加 runner 上的 `TERM=xterm`，Rich 解析出真实色彩系统，开始输出 ANSI。
而 Rich 的**语法高亮器**会把文档字符串里的 `` `--password-stdin` `` 按 token 拆成多个
带样式的片段，ANSI 转义被插进选项名**内部**：

```
\x1b[1;2m-\x1b[0m\x1b[1;2m-password\x1b[0m…
```

所以原始文本里**根本不存在连续的 `--password-stdin`** 子串。

复现方式（一条命令即可）：

```bash
GITHUB_ACTIONS=true TERM=xterm .venv/bin/python -m app.cli create-superadmin --help
#   原始 stdout 含 '--password-stdin'  → 否   ← 当年的红叉
#   去 ANSI 并压平空白后再匹配        → 是
```

之前本机复现不出来的原因也一并清楚了：我试过 `FORCE_COLOR` / `CLICOLOR_FORCE` /
`TERM=dumb` / 各种宽度高度，**唯独没试 `GITHUB_ACTIONS=true` 与 `TERM` 的组合** ——
单设 `GITHUB_ACTIONS=true` 时本机 `color_system` 仍是 `None`（非交互 shell 没有 `TERM`），
所以不出 ANSI。这个组合才是 CI 的真实条件。

**处理方式**（不检查排版）：

1. `_cli_env` 固定 `COLUMNS=200` + `NO_COLOR=1`，消除终端几何与颜色两个变量
2. 新增 `_plain()`：**去掉 ANSI、把折行与缩进压成单行**后再断言
3. 失败信息一次性带出 `returncode`、stdout/stderr 长度、
   `COLUMNS`/`NO_COLOR`/`LINES`/`TERM`、归一化文本与原始 repr

> 事后实测：真正起作用的是第 2 条的 `_plain()`。
> `NO_COLOR=1` **挡不住** —— Typer 被 `GITHUB_ACTIONS` 强制开终端后照样输出 ANSI。
> 已在原始失败条件（`GITHUB_ACTIONS=true TERM=xterm`）下回归：
> 老断言失败、新断言通过，整个 `tests/test_cli.py` 17 项通过。

同时记录了这条断言的地位：它其实是**冗余**的。测试前半段已经用
`--password-stdin` 真实建出超管并校验了库里的行，这比「help 文本里出现
该字符串」是强得多的证据。真正不可替代的是紧随其后的那条不变量 ——
CLI 必须**拒绝** `--password` 明文选项。

### 11.6 一次未复现的间歇性失败（记录在案）

修 11.1~11.3 的过程中，无 `web/dist` 的一次全量运行里
`tests/test_m2_units.py::test_get_upload_limits_falls_back_to_env`
失败过一次（错误信息以 `sql...` 开头，疑为 SQLite 相关）。

- 随后无 `web/dist` 连跑 **3 次**：均 449 passed
- 又连跑 **8 次**：均 449 passed（共 11 次未再现）

该用例会临时把 `system_settings` 里的 `upload.allowed_extensions`

**但这只是推测，没有证据，故不写成结论。**

处置：记录在案，不在本轮修。若后续 CI 出现间歇性红叉，

## 12. 配置变量命名空间不一致（已修，含对勘误 #28 的反转）

### 12.1 问题：脚本与应用读的不是同一套变量名

`deploy/localcraft.env.example`（`install.sh` 原样装入
`/etc/localcraft/localcraft.env`）用的是**无前缀**名：
`DATA_DIR` / `DATABASE_URL` / `DB_BUSY_TIMEOUT` / `LOG_LEVEL` …
应用 `config.py` 也读这些（只有 4 个字段带 `LOCALCRAFT_` 前缀：
host / port / debug / version —— 原先是 5 个，`public_base_url` 因无读取点已删除，见 §13）。

但**运维脚本读的是另一套前缀名**。改动前 `scripts/backup.sh:17` 是：

```bash
DATA_DIR="${LOCALCRAFT_DATA_DIR:-/var/lib/localcraft}"
```

两者组合出的后果是**静默失败**：systemd 单元用
`EnvironmentFile=/etc/localcraft/localcraft.env` 把 `DATA_DIR` 注入脚本环境，
而脚本根本不看它 → 运维把数据目录改到 `/srv/localcraft`，应用写新路径，
`backup.sh` 却回落到 `/var/lib/localcraft`。备份**跑成功、退出码 0、
日志一切正常**，备的是错目录。

实测对比（同一环境变量 `DATA_DIR=<沙箱>`）：

| | `DATA_DIR` | `DB_FILE` | `FILES_DIR` | `BACKUP_ROOT` |
| --- | --- | --- | --- | --- |
| 改动前 | `/var/lib/localcraft` | `/var/lib/localcraft/localcraft.db` | `/var/lib/localcraft/files` | `/var/lib/localcraft/backups` |
| 改动后 | `<沙箱>` | `<沙箱>/localcraft.db` | `<沙箱>/files` | `<沙箱>/backups` |

### 12.2 解决与命名原则

分两类处理，不搞一刀切：

| 类别 | 例子 | 规则 |
| --- | --- | --- |
| **镜像应用配置** | `DATA_DIR`、`DATABASE_URL` | **应用名优先** → `LOCALCRAFT_` 前缀旧名作兼容别名 → 默认值兜底 |
| **脚本自有开关** | `LOCALCRAFT_BACKUP_KEEP_DB`、`LOCALCRAFT_ALERT_DISK_WARN`、`LOCALCRAFT_PREFIX` | 保留 `LOCALCRAFT_` 前缀。它们不是应用配置，加前缀正是为了避免与系统环境撞名 |

DB 路径由 `DATABASE_URL` 派生（应用只用这一个变量描述数据库位置）：

```bash
case "${DATABASE_URL:-}" in
    sqlite+aiosqlite:///*) _DB_FROM_URL="${DATABASE_URL#sqlite+aiosqlite:///}" ;;
    *) _DB_FROM_URL="" ;;
esac
DB_FILE="${_DB_FROM_URL:-${LOCALCRAFT_DB:-$DATA_DIR/localcraft.db}}"
unset _DB_FROM_URL
```

`sqlite+aiosqlite:///` 之后 3 个斜杠是相对路径、4 个是绝对路径，
两种都靠「去掉这 3 个斜杠」得到正确结果（两种写法均已实测）。

**`install.sh` 是例外且是刻意的**：它是**生成器**，把取值写进
`localcraft.env`。所以它的优先级与消费者脚本相反 ——
`LOCALCRAFT_DATA_DIR`（安装期显式开关，docs/05 与 m4 演练都用它）排最前，
否则环境里一个陈旧的 `DATA_DIR` 就能悄悄改变安装目标目录。

### 12.3 对勘误 #28 的反转

§5 的 #28 原文把**脚本的行为标为「对」**、把文档标为「错」：

> | 28 | §8.7 | `DATA_DIR` / `DB_FILE` | 脚本实际读 `LOCALCRAFT_DATA_DIR` / `LOCALCRAFT_DB` |

这个判定是反的。应用与 `localcraft.env` 用的都是无前缀名，
所以错的是脚本。**#28 已按此反转**（docs/08 同一张表的第 8 行同步反转）。

### 12.4 验证方式

不是只跑语法检查：

1. **路径解析前后对比** —— `bash -x` 抓出 `DATA_DIR`/`DB_FILE`/`FILES_DIR`/`BACKUP_DIR`
   的实际取值，改动前 4 个全落在 `/var/lib/localcraft`，改动后全落在沙箱（见 §12.1 表）
2. **完整往返** —— 沙箱内 `backup.sh` → 删库删文件 → `restore.sh --latest --yes --no-start`
   → 数据行数与文件 SHA256 逐字节一致
3. **真实 schema** —— 用 `alembic upgrade head` 建 26 张表后重跑，
   `verify-backup.sh` 退出码 0（「验证通过」）
4. **反向验证** —— 把快照前几字节改坏，`verify-backup.sh` 必须非零退出（能检出）
5. **兼容性回归** —— 旧的 `LOCALCRAFT_DATA_DIR`、`LOCALCRAFT_DB` 仍生效
   （`m4-drill-*.sh` 依赖它们），两者同时存在时新名优先
6. `contracts/acceptance/pre-delivery-checks.sh` 仍 **PASS=35 / FAIL=0 / BLOCKED=1**

## 13. 配置命名空间清理（第二轮：文档与幽灵配置）

§12 修的是**脚本**读错变量名。这一轮清理**文档**里同一根因的残留，
以及一批「被文档描述、却毫无作用」的幽灵配置。

### 13.1 文档里写错的应用配置名（照抄会「改了没反应」）

`docs/05` §5.4 的环境变量示例与 §14.2 的速查表里，有一整批变量名是错的。
后果不是报错，而是**静默忽略**（pydantic-settings 的 `extra="ignore"`）——
运维改了配置、重启了服务、什么都没发生。

| 文档原先写的（错） | 实际（对） |
| --- | --- |
| `LOCALCRAFT_DB_ECHO` / `_DB_POOL_SIZE` / `_DB_MAX_OVERFLOW` / `_DB_BUSY_TIMEOUT` | `DB_ECHO` / `DB_POOL_SIZE` / `DB_MAX_OVERFLOW` / `DB_BUSY_TIMEOUT` |
| `LOCALCRAFT_DB_BUSY_TIMEOUT=15`（**秒**） | `DB_BUSY_TIMEOUT=5000`（**毫秒**，默认 5 秒） |
| `LOCALCRAFT_MAX_UPLOAD_SIZE` | `MAX_UPLOAD_SIZE`（且只是兜底，实际生效值在 system_settings） |
| `LOCALCRAFT_ALLOWED_EXTENSIONS` | `ALLOWED_EXTENSIONS`（同上，兜底） |
| `LOCALCRAFT_UNZIP_MAX_*`（5 个） | `UNZIP_MAX_*` |
| `LOCALCRAFT_ENABLE_DOCS` | `API_DOCS_ENABLED` |
| `ACCESS_TOKEN_EXPIRE_MINUTES` | `ACCESS_TOKEN_MINUTES`（旧名是兼容别名） |
| `REFRESH_TOKEN_EXPIRE_DAYS=14` | `REFRESH_TOKEN_DAYS=7`（旧名是别名但**默认值不同**） |
| `LOCALCRAFT_LOG_LEVEL` 被当作"日志级别"的唯一开关 | 它有真实用途（systemd → uvicorn 的 `--log-level`），但**应用自身的 JSON 日志读 `LOG_LEVEL`**。原先 env 示例只给了前者，等于应用日志级别不可配 |
| `UNZIP_MAX_FILE_SIZE` 默认 `100 MB` | 实际默认 **200 MB**（`209715200`） |

### 13.2 不是环境变量、而是运行期设置（写在 system_settings 表里）

| 文档原先写的（错） | 实际机制 |
| --- | --- |
| `LOCALCRAFT_USER_QUOTA` / `LOCALCRAFT_TOTAL_QUOTA` | system_settings 的 `quota.per_user_mb`（2048）/ `quota.total_mb`（51200） |

### 13.3 幽灵配置：文档写了、代码里根本没有

| 名字 | 处置 |
| --- | --- |
| `LOCALCRAFT_PUBLIC_BASE_URL` | **删除**。见下节 |
| `LOCALCRAFT_CORS_ORIGINS` | 删除。前后端同源部署，没有 CORS 配置 |
| `LOCALCRAFT_TRUSTED_PROXY_COUNT` | 删除，并改成说明**真实机制**：`X-Forwarded-For` 由 uvicorn 的 `--proxy-headers --forwarded-allow-ips=127.0.0.1` 处理（§6.2 单元文件），只信任来自回环的转发头 |
| `LOCALCRAFT_LOG_TO_FILE` / `LOCALCRAFT_LOG_FILE` | 删除。应用日志写 stdout → journald，**没有**写文件的开关 |
| `PASSWORD_HASH_SCHEME` | 删除。密码哈希固定 argon2id，**不可切换** |

关于 `LOCALCRAFT_TRUSTED_PROXY_COUNT`：早先的记录里我把它标为「可能指向真缺陷」，
理由是"若应用不处理 XFF，客户端 IP 会全是 127.0.0.1，影响限流与审计"。
**这个判断需要修正** —— 应用确实读客户端 IP（`deps.py` 的 `get_client_info()`，
用于 API Token 的 `last_used_ip`），但 XFF 的处理**不在应用里**，而在 uvicorn 的启动参数里。
那套机制是正确且更内聚的：直连模式下没有 127.0.0.1 来的转发头，
客户端伪造 `X-Forwarded-For` 不会被采信。**两种拓扑都安全，不需要这个配置项。**

### 13.4 `LOCALCRAFT_PUBLIC_BASE_URL` 的删除

它在 `config.py` 里有定义，在 **5 处**被文档与 env 示例提及，`install.sh` 甚至
会提醒运维「请检查它」——但**从未被读取过**。实测：

- 图片签名 URL：`/api/v1/images/{id}?variant=thumb&sig=…`（相对路径）
- 下载票据 URL：`/api/v1/tools/{slug}/download?version_id=…&ticket=…`（相对路径）
- `backend/openapi.json` **没有 `servers` 段**

所以「生成下载链接与基址」这句描述是错的（这句话也出现在我写的 README 里，
我照文档抄的，没核代码 —— 已一并改正）。

处置：删除字段与全部 8 处引用。理由与 contracts/CONTRACT.md §20.5 删除 `localcraft-gc.*` 悬空引用一致 ——
**一个被文档描述、被 env 接受、却毫无作用的字段，比没有它更糟**。

> 顺带修掉一个 `docs/05` 自己的位置引用错误：勘误 #25/#26/#27 原先标的位置
> 写成「§12.2」「§12.3」「§14.2」，而 §12.2 是「database is locked」。
