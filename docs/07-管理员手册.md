# 管理员手册

> 面向 **审批管理员（`approver`）** 与 **超级管理员（`superadmin`）**，只讲管理员才有的能力。
> 普通用户操作（浏览、下载、上传、发版本、改密）见 `docs/06-用户手册.md`，本手册不重复。
> 路径、字段名、长度、错误码均取自当前实现（`backend/app/api/v1/admin/*.py`、`backend/app/schemas/*.py`、
> `backend/app/services/*.py`、`backend/app/core/errors.py`、`backend/app/repositories/*.py`）。
> 与实现不符的旧文档说法见 **§16**。所有路径前缀为 `/api/v1`。

## 0. 怎么用

| 角色 | 能进的管理页面 |
| --- | --- |
| `approver` | 审批队列、审批历史、全站工具（只读）、分类、标签、概览 |
| `superadmin` | 以上全部 + 用户、用户组、免审白名单、系统设置、API Token、回收站、导入导出 |

一个用户可多角色、权限取**并集**；`approver` **没有**用户管理、用户组、系统设置、API Token 权限。

先设置两个变量，后续命令可直接复制执行。所有接口都要 `Authorization: Bearer <凭证>`，带请求体的再加 `Content-Type: application/json`：

```bash
BASE=http://127.0.0.1:8000/api/v1   # 直连后端；经 nginx 则用内网域名/IP
TOKEN='<你的 JWT 或 st_ 开头的 API Token>'
```

失败响应统一为 `{code, message, details, request_id}`；脚本按 `code` 分支，**别匹配中文 message**。`request_id` 同时回写响应头 `X-Request-Id`。权限不足两种：角色不足 `403 FORBIDDEN`；Token 的 scope 不足 `403 SCOPE_MISSING`（`details.missing_scopes` 指缺哪个）。

## 1. 角色与权限速查

逐条取自 `backend/app/api/v1/admin/_guards.py`。

> **Scope 列只对 API Token 有意义。** JWT 登录时 `require_scope` 一律放行，只看角色；用 `st_` Token 时**角色与 scope 都要过**。所以「superadmin 用只带 `tools:read` 的 Token 调 `/admin/users`」会拿到 `403 SCOPE_MISSING`。

| --- | --- | --- | --- |

| 审批历史 | `approver`·`superadmin` | `approvals:write` | `GET /admin/approvals/history` |
| 全站工具列表 | `approver`·`superadmin` | `approvals:write` | `GET /admin/tools` |
| 概览/下载排行/角色列表 | `approver`·`superadmin` | `approvals:write` | `GET /admin/overview`、`GET /admin/stats/tools`、`GET /admin/roles` |
| 分类：列表（含禁用）/建/改/删/排序 | `approver`·`superadmin` | `taxonomy:write` | `GET\|POST /admin/categories`、`PATCH\|DELETE /admin/categories/{id}`、`PUT /admin/categories/order` |

## 2. 审批流程

**进队列的路径**：作者建工具、传版本后调 `POST /api/v1/me/tools/{id}/submit`。服务端先判自动放行（§11）：命中 → 直接 `approved`、**不进队列**；未命中 → 工具变 `pending`（首次）或 `pending_update`（发新版本），写一条 `approval_records` 后进队列。**队列里永远只有这两种状态。**

**看队列**：

```bash
curl -s "$BASE/admin/approvals?page=1&page_size=20" -H "Authorization: Bearer $TOKEN"
```

参数：`status` = `pending`（**仅**首次）/ `pending_update`（**仅**新版本）/ `pending_all`（并集，**省略时默认**）；`tool_type` = `file`/`webapp`/`skill`/`prompt`；`owner`（提交人 `username`，服务端转小写）；`page` ≥ 1；`page_size` 1~200 默认 20。**没有 `sort` 参数**，顺序固定为提交时间正序（先提交先处理）。别为「看全部」传 `status=pending` —— 那会藏起新版本待审条目，而已发布工具门户仍正常服务，很难察觉。
每行：`tool_id`、`tool_slug`、`tool_name`、`tool_type`、`summary`、`visibility`、`category`、`tags`、`submission_type`（`new_tool`/`new_version`，**决定驳回后工具去向**）、`status`、`pending_version`（`id`/`version`/`changelog_md`/`file_name`/`file_size`/`file_sha256`）、`current_version`（新工具为 `null`）、`owner`、`submitted_at`、`waiting_hours`、`version_seq`（**乐观锁令牌**）。

**批准**：

```bash
curl -s -X POST "$BASE/admin/approvals/12/approve" \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{ "version_id": 346, "note": "已核对 changelog 与包内脚本", "expected_version_seq": 7 }'
```

`version_id` 选填（传了但不是当前待审版本 → `409 ALREADY_PROCESSED`）；`note` 选填 ≤ 2000；`expected_version_seq` 选填（乐观锁）；`force` 是保留字段、**当前未使用**。响应 `{tool_id, status:"approved", version_seq, current_version, superseded_version, purged_versions, approval_record_id}`。`superseded_version` 是被顶下去的旧当前版本（首次批准为 `null`）；`purged_versions` 是因超出 `version.history_limit`（默认 10）被归档的版本 —— 行转 `purged` 保留审计，**磁盘文件在事务提交后删除**。

| 失败场景 | HTTP | code |
| --- | --- | --- |
| 工具不在 `pending`/`pending_update` | 409 | `STATE_CONFLICT`（`details.status`） |
| 工具不存在或在回收站 | 404 | `NOT_FOUND` |
| 工具没有待审版本 | 409 | `STATE_CONFLICT` |
| 版本已被他人处理 / 乐观锁不匹配 | 409 | `ALREADY_PROCESSED` |

**`version_seq` 乐观锁与并发**：`tools.version_seq` 每次状态变化 +1，批准走 CAS（`UPDATE ... WHERE id=? AND status=? AND version_seq=?`），影响行数不为 1 即报 `409 ALREADY_PROCESSED`。做法：读队列时记下 `version_seq`，批准时原样回传 `expected_version_seq`。若期间有人下架、他人已批、或**负责人被转移**（也推进 `version_seq`），你会立刻拿到该码，`details` 给出 `expected_version_seq`/`actual_version_seq` —— **收到就刷新列表重看，不要重试同一请求**。时序：A、B 同时看到工具 12（`version_seq=7`），A 先批成功（→8）；B 传了锁 → `ALREADY_PROCESSED`，没传锁 → 因工具已不在 `pending` 而 `STATE_CONFLICT`。**两者都不会双写。**

**批量批准**：

```bash
curl -s -X POST "$BASE/admin/approvals/batch-approve" \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{ "tool_ids": [12, 13, 14], "note": "批次 2025-03 例行放行" }'
```

`tool_ids` 1~200、`note` ≤ 2000；响应 `{succeeded, failed, results:[{tool_id, ok, status?, error_code?, message?}]}`。**逐条独立处理、独立提交**，一条失败不影响其他；批量路径**不传** `expected_version_seq`，所以**无乐观锁保护**，并发下后到者计入失败项。**没有批量驳回** —— 驳回必须逐条写理由（`FR-APPR-09`）。

**审批历史**：

```bash
curl -s "$BASE/admin/approvals/history?tool_id=12&page=1&page_size=50" -H "Authorization: Bearer $TOKEN"
curl -s "$BASE/admin/approvals/history?actor_id=3&action=reject&date_from=2025-03-01T00:00:00Z&date_to=2025-04-01T00:00:00Z" -H "Authorization: Bearer $TOKEN"
```

筛选 `tool_id`/`actor_id`/`action`/`date_from`/`date_to` + 分页。`action` 合法值：`submit`、`withdraw`、`resubmit`、`approve`、`reject`、`offline`、`relist`、`purge_version`、`transfer_owner`（非法 → `400 VALIDATION_ERROR`，`details.fields[].field="action"`）。返回 `id`、`tool_id`、`tool_name`、`tool_slug`、`version_id`、`version`、`action`、`from_status`、`to_status`、`version_from_status`、`version_to_status`、`actor_id`、`actor_label`、`is_automatic`、`auto_rule`、`reason`、`note`、`created_at`。`actor_label` 是**写入时的显示名快照**（改名后历史仍准确）；`is_automatic=true` 且有 `auto_rule` 表示自动放行（此时 `actor_id=null`、`actor_label="系统自动放行"`）；`transfer_owner` 记录的 `from_status` 与 `to_status` **相同**，变更内容在 `note` 里。

## 3. 审一个 Skill 包的判断要点

**能看到的两处**：① 队列里的 `pending_version`（`version`/`changelog_md`/`file_name`/`file_size`/`file_sha256`）；② Skill 包预览：

```bash
curl -s "$BASE/tools/log-analyzer-a3f2/versions/1.3.0/skill-preview" -H "Authorization: Bearer $TOKEN"
```

返回字段就是全部：`manifest`（`SKILL.md` frontmatter 解析出的字典，如 `name`、`description`、`allowed-tools`；解析失败为 `null`）、`readme_md`（包内 README 正文，截断处附提示）、`file_tree`（每项 `{path, size, is_dir, sha256}`，目录项 `is_dir=true`/`size=0`/`sha256=null`）、`file_tree_truncated`（`true` = 文件树**不完整**，存储上限 2000 条、超出被丢弃）、`total_size`（文件树内 `size` 之和，即解压后字节数）、`version`。

**实现里没有的别去找**：响应**没有压缩比字段** —— 压缩比只是解析期的 zip 炸弹护栏（解压后 / 压缩包 > 200 → `422 ZIP_BOMB_DETECTED`），不对外暴露；想估「小包大解压」只能用 `file_size`（压缩包）与 `total_size`（解压后）自己除。也没有文件内容在线预览器 —— 除 `manifest` 与 `readme_md` 外，看其它文件必须下载整包。

权限：该接口走**门户**鉴权，Token 必须带 `tools:read`；**只带 `approvals:write` 会拿到 `403 SCOPE_MISSING`（`missing_scopes: ["tools:read"]`）**。审批人可见的**工具**状态集合（`repositories/tools.py`）是 `(pending, pending_update, offline, approved)`，**不含 `draft` 与 `rejected`** —— 门户详情对任何角色都不暴露这两种状态；要复审已被驳回的首次提交，走 `/admin/tools` 或审批历史。

**检查清单**：

- [ ] `manifest` 是否为 `null`？（frontmatter 未解析成字典；连 `SKILL.md` 都没有的包在上传阶段就被 `422 SKILL_MD_NOT_FOUND` 拒掉，不会进队列）
- [ ] `manifest.name` 与工具名/包名是否一致？（不一致常是复制他人包改的）
- [ ] `description` 是否说清能力边界？`allowed-tools` 与包内脚本行为是否匹配（声明只读却带写盘/exec = 重点）
- [ ] `changelog_md` 与文件树变化是否对得上？（说「只改文档」却新增可执行文件要追问）
- [ ] `file_tree` 有无可疑文件：`.env*`、`*.pem`/`*.key`/`*.p12`/`*.jks`、`id_rsa`、`credentials`/`secrets`/`.npmrc`/`.pypirc`/`.netrc`、`*.sql` 导出、`*.bak`/`*.old`/`*.orig`/`*.swp`、`__MACOSX/`、`.DS_Store`、`node_modules/`、`.git/`；`sha256` 可核对是否硬编码过的旧副本
- [ ] 有无不该出现的大文件（单个 `size` 很大的二进制/模型/数据包会长期占配额）
- [ ] **`file_tree_truncated` 是否为 `true`？** 为 `true` 表示包内条目超 2000，你**看不到完整清单**，不要只凭可见部分放行 —— 要求作者说明总量或下载整包核对
- [ ] `file_size`（压缩包）与 `total_size`（解压后）比值是否异常？极大可能是重复内容、填充数据或日志；超 200 倍在上传阶段即被拒，所以队列里的最大就是 200 倍
- [ ] 有无引用外部 URL？（`file_tree` 不显示内容，但 `readme_md` 里的下载链接、`curl | bash`、外部仓库地址要警惕；包内脚本正文须**下载整包后**看）
- [ ] `file_sha256` 是否与作者声称的一致？可见性是否合理？（`restricted` 却无 ACL 的在上传时被 `ACL_REQUIRED` 拦，正常不进队列）

结论三选一：**通过**（批准，可填 `note` 记录核对过什么）；**需要改**（驳回，理由写清「哪里 + 怎么改」）；**已上线但有风险**（下架）。

## 4. 驳回话术

**字段名 `reason`**（不是 `comment`/`message`/`reject_reason`）；**必填**；长度 **5~2000** 字符；服务端先 `strip()` 再校验（全空格会被拒）；失败 → `422 VALIDATION_ERROR`。

```bash
curl -s -X POST "$BASE/admin/approvals/12/reject" \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{ "reason": "包内 scripts/deploy.sh 第 12 行硬编码了生产库口令，请改为读取环境变量后重新提交。", "version_id": 346 }'
```

响应 `{tool_id, status, pending_version:null, rejected_version:{id,version}, approval_record_id}`。

**最容易读错的语义**：驳回**首次提交**（`new_tool`）→ 工具变 `rejected`；驳回**新版本**（`new_version`）→ 版本变 `rejected`、**工具退回 `approved`、当前线上版本完全不变**，所以响应里的 `status` 是 `approved`。`version_id` 传了但不是当前待审版本 → `409 ALREADY_PROCESSED`。
理由写进 `approval_records.reason` 与版本行的 `reject_reason`，**会原样展示给作者**；好理由 = **位置**（哪个文件/字段/环节）+ **问题**（为什么不通过）+ **怎么改**。

| # | ❌ 反例 | ✅ 正例 |
| --- | --- | --- |
| 1 | 「不合格」 | 「`SKILL.md` 的 frontmatter 缺 `description`，门户列表会显示为空。请补一句 20 字以内的功能说明后重新提交。」 |
| 2 | 「有安全问题」 | 「`scripts/deploy.sh` 第 12 行硬编码了数据库口令。请改为从环境变量 `DB_PASSWORD` 读取，并把该文件从包里移除后重传。」 |
| 3 | 「重新传一下」 | 「包内 `__MACOSX/` 与 `.DS_Store` 是 macOS 打包残留（共 14 个文件）。请在打包前清理，或改用 `zip -x '.*' -x '__MACOSX/*'`。」 |
| 4 | 「说明太简单」 | 「`changelog_md` 只写了『修复 bug』，但本次文件树新增 `scripts/migrate.py`。请写清这个脚本做什么、是否需要人工执行。」 |
| 5 | 「包太大」 | 「包内 `assets/demo.mp4` 占 96 MB，超出本工具实际需要。请压到 10 MB 以内或改为外部文档链接后重新提交。」 |
| 6 | 「权限有问题」 | 「可见性设为 `restricted` 但未指定任何授权对象，上传会被 `ACL_REQUIRED` 拒绝。请先在『指定可见』里加上用户或用户组。」 |
| 7 | 「不许外链」 | 「`SKILL.md` 第 8 行要求用户执行 `curl -sL https://example.com/install.sh \| bash`。平台不接受从公网拉脚本执行，请把脚本纳入包内并说明其内容。」 |
| 8 | 「重做」 | 「1) `manifest.name` 写的是 `log_analyzer`，与 slug `log-analyzer-a3f2` 不一致；2) 真实 token 写在了 `config.json`。请修正后重新提交。」 |

建议：**一次说全**（能一次列完的别分多次驳回）；**给可执行的下一步**；**不泄露不该说的**（理由展示给作者，别贴其他用户信息、内部 IP、扫描原文）；纯格式问题也要写。

## 5. 下架与重新上架

**下架（`offline`）**：

```bash
curl -s -X POST "$BASE/admin/approvals/12/offline" \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{ "reason": "检测到包内脚本会向外部地址回传内网主机名，暂停分发直至修复。" }'
```

`reason` **必填**（`FR-APPR-10`），5~2000（`strip()` 后校验）；**仅 `approved`/`pending_update` 可下架**，否则 `409 STATE_CONFLICT`；响应 `{tool_id, status:"offline", approval_record_id}`。同一事务内连带：`status`→`offline`、`offline_reason` 记理由、**`pending_version_id` 被清空**（队列里挂着的新版本被撤下；该版本行仍是 `pending`，重新上架后**不会自动回队列**，需作者重新提交）、`version_seq` +1（并发审批会因此拿到 `ALREADY_PROCESSED`）、写一条 `action=offline` 记录。**文件与版本都保留，不删任何东西。**

**下架后的可见性**：

| 谁 | 能看到什么 |
| --- | --- |
| 普通用户 / viewer | **看不到**（门户列表与详情按 `approved`/`pending_update` 过滤） |
| 工具负责人 | 个人中心「我的工具」可见「已下架」状态与理由 |
| `approver`/`superadmin` | 门户详情**可打开**（`APPROVER_VISIBLE_STATUSES` 含 `offline`），`/admin/tools` 亦可见 |
| 已发出的下载票据 | 票据仅 60 秒有效，下载入口重新判定状态，下架后基本立即失效 |

`deleted_at IS NOT NULL`（软删除）对所有角色都不通过门户，只能从 `/admin/recycle-bin` 找。

**重新上架（`relist`）**：

```bash
curl -s -X POST "$BASE/admin/approvals/12/relist" \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{ "reason": "作者已提交修复并说明整改内容，恢复分发。" }'
```

`reason` **选填**（`FR-APPR-11`）≤ 2000；仅 `offline` 可调，否则 `409 STATE_CONFLICT`。效果：`status`→`approved`、`offline_reason` 清空、`version_seq` +1、写 `relist` 记录，**当前版本不变**（不重走审批）。若修复是通过发新版本完成的，那条新版本要单独走队列。

## 6. 用户与角色管理

**为什么不能物理删除用户**：**接口层根本没有删除用户的端点。** 用户与 `tools.owner_id`、`approval_records.actor_id`、`download_logs.user_id` 有外键关联，删除会打断审计链（`FR-IAM-06`）。离职一律走**禁用**；界面也不提供删除按钮。

**创建用户**：

```bash
curl -s -X POST "$BASE/admin/users" \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{ "username": "zhangsan", "display_name": "张三", "email": "zhangsan@example.com",
        "password": "", "roles": ["user"], "must_change_password": true }'
```

`username` 必填 1~64，只允许字母/数字/下划线/点/连字符，**服务端转小写**、**创建后不可修改**；`display_name` 必填 1~128；`email` 选填 ≤ 255；`roles` 默认 `["user"]`（`viewer`/`user`/`approver`/`superadmin`）；`must_change_password` 默认 `true`；`password` 留空 → 服务端生成并**只回显一次**。
**密码策略**（仅手填时）：长度 **≥ 10**；大写/小写/数字/符号四类中**至少 3 类**；不得与用户名相同（归一化后比较）。不满足 → `422 VALIDATION_ERROR`（`details.fields` 逐条提示）。服务端生成的口令恒满足（`St` + 10 位无歧义字符 + `!7`，共 14 位，去掉了 `0/O/1/l/I`）。
响应 `201` `{user:{...}, generated_password:"StK7mPq2xRv9!7"}`。

> **`generated_password` 只出现这一次**，立刻复制并通过安全渠道告知用户；关掉响应后再也查不到（库里只有哈希）。

失败：用户名已存在 → `400 VALIDATION_ERROR`（`fields[].field="username"`）；用户名非法字符或密码弱 → `422`；角色 code 未知 → `400`（`fields[].field="roles"`）。

**列表与详情**：

```bash
curl -s "$BASE/admin/users?q=zhang&role=approver&role=user&status=active&page=1&page_size=20" -H "Authorization: Bearer $TOKEN"
```

`q` 对 `username`/`display_name` 小写模糊匹配；`role` 可重复（命中任一即可）；`status` = `active`/`disabled`。每行还带 `tool_count`（未删除工具数）、`used_bytes`、**`active_token_count`**（生效中的 Token 数，禁用前用它评估影响面）、`failed_login_count`、`locked_until`、`last_login_at`、`last_login_ip`、`must_change_password`、`auth_source`。

**编辑 / 禁用 / 启用**：

```bash
curl -s -X PATCH "$BASE/admin/users/42" -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" -d '{ "display_name": "张三丰", "email": "zsf@example.com" }'
curl -s -X PATCH "$BASE/admin/users/42" -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" -d '{ "status": "disabled" }'   # 改回 "active" 即启用
```

可更新字段仅 `display_name`/`email`/`status`，`username` **不可改**。**禁用时连带**：`status`→`disabled`、`locked_until` 清空、**吊销全部 refresh token（会话）**、**吊销其全部 API Token**（不是降权，是直接不可用 → `401 TOKEN_REVOKED`）。**启用只把状态改回 `active`，已吊销的会话与 Token 不恢复**，需重新登录 / 重新签发。

**三条硬约束**：

| 约束 | 触发时机 | 返回 |
| --- | --- | --- |
| 不能禁用自己 | `PATCH` 把自己的 `status` 改成 `disabled` | `400 VALIDATION_ERROR`，`details.reason="self_disable"` |
| 不能降级自己 | `PUT .../roles` 把 `superadmin` 从自己角色里去掉 | `400 VALIDATION_ERROR`，`details.reason="self_demote"` |
| 不能禁用/降级最后一个启用的超管 | 见下 | `409 LAST_SUPERADMIN` |

**`LAST_SUPERADMIN` 的确切触发点**只有两处，且目标必须是**当前启用的 `superadmin`**：① `PATCH /admin/users/{id}` 把 `status` 设为 `disabled`；② `PUT /admin/users/{id}/roles` 的新集合里**不再含 `superadmin`**。判定用 CAS（把「除目标外还有启用的超管」写进 `UPDATE ... WHERE`），所以两位管理员同时降级最后两个超管时**只有一个成功**，另一个拿到 `409`（`details.reason="cas_failed"`）。细节：**「自己」的判断先于「最后一个超管」**，所以唯一的超管禁用自己拿到的是 `400`（`self_disable`）而非 `409`；改自己的显示名/邮箱不受影响；重新启用被禁用的超管、或**加上** `superadmin` 均不触发。

**替换角色（全量）**：

```bash
curl -s -X PUT "$BASE/admin/users/42/roles" -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" -d '{ "roles": ["user", "approver"] }'
```

`roles` 长度 1~4，**传 `[]` 会被拒**；这是**全量替换**，未列出的角色会被移除。

**重置密码 / 强制下线**：

```bash
curl -s -X POST "$BASE/admin/users/42/reset-password" -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" -d '{ "password": "" }'
curl -s -X POST "$BASE/admin/users/42/revoke-sessions" -H "Authorization: Bearer $TOKEN"
# → {"status":"ok","revoked_sessions":3}
```

`reset-password` 的 `password` 选填（留空则生成并回显一次，填了按上文校验）；响应 `{user_id, must_change_password:true, revoked_sessions, generated_password}`。效果：密码被替换、`must_change_password` **强制置 `true`**、`failed_login_count` 清零、`locked_until` 清空（锁定中的用户立即解锁）、**吊销全部会话**。

> **重置密码与强制下线都只吊销会话，不吊销 API Token。** 要让 Token 也失效，必须**禁用该用户**（连带吊销）或逐个 `POST /admin/tokens/{id}/revoke`。目前**没有**「一键吊销某用户全部 Token」的 HTTP 接口 —— 该能力在服务层已实现但未暴露路由。

**替换角色后 Token 会怎样**：Token 鉴权取「Token 的 scopes」与「**创建者当前角色权限**」的**交集**，不做签发时快照：

| 对创建者的操作 | 其 Token 行为 |
| --- | --- |
| 降级（去掉 `superadmin`） | **立即降权**：`admin:all` 展开的权限与新角色求交集，越权 `403 SCOPE_MISSING` |
| 角色替换为 `viewer` | 只剩 `tools:read`，不能下载、不能写 |
| **禁用** | Token **全部吊销**，调用 `401 TOKEN_REVOKED`（「创建者已被禁用」） |
| 重新启用 | Token **仍是吊销状态**，不恢复，需重新签发 |

`GET /admin/roles` 可核对四个内置角色当前的权限点与人数。

## 7. 用户组

用户组**只用于可见性授权**（`restricted` 工具的 ACL），**不承载角色权限**（`FR-GRP-03`）；「进组即获得角色」不存在，请直接分配角色。

```bash
curl -s -X POST "$BASE/admin/groups" -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{ "name": "数据平台组", "description": "数据平台团队全体成员", "is_active": true }'
curl -s -X PATCH "$BASE/admin/groups/5" -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" -d '{ "description": "数据平台团队（含外包）" }'
curl -s "$BASE/admin/groups?q=数据&page=1&page_size=50" -H "Authorization: Bearer $TOKEN"
curl -s -X POST "$BASE/admin/groups/5/members" -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" -d '{ "user_ids": [42, 43, 44] }'
# → {"added":3,"already_members":0,"not_found":[]}
curl -s "$BASE/admin/groups/5/members?q=zhang&page=1&page_size=50" -H "Authorization: Bearer $TOKEN"
curl -s -X DELETE "$BASE/admin/groups/5/members/42" -H "Authorization: Bearer $TOKEN"
```

组名唯一（重名 → `400 DUPLICATE_ENTRY`）；列表每行带 `member_count` 与 `acl_reference_count`（被多少个工具的 ACL 引用）。`user_ids` 1~200，**一次事务写入**；已在组内的计入 `already_members`；用户不存在的 id 进 `not_found`（不报错）；移除不在组内的用户 → `404 NOT_FOUND`。成员变更后**可见性立即生效**（每次请求实时判定，不做 token 内嵌缓存），成员无需重新登录。

**删除组**：不带 `force` 时若被 ACL 引用 → `409 GROUP_IN_USE`，`details` 为 `{group_id, group_name, tool_count, tools:[{id,name},...]}`。先看 `details.tools` 评估影响面：删组会让这些工具的「指定可见」失效，组内成员**立即失去**访问权。

> 🚨 **危险操作：`force=true` 删组。** 会删组**并连带清理引用它的全部 ACL 条目**，**不可撤销**。
>
> ```bash
> curl -s -X DELETE "$BASE/admin/groups/5?force=true" -H "Authorization: Bearer $TOKEN"
> # → {"status":"ok","cleaned_acl_entries":4,"affected_tools":[12,18,27]}
> ```
>
> `cleaned_acl_entries` = 实际删掉的 ACL 条目数；`affected_tools` = 受影响的工具 id 列表。执行后请通知这些工具的负责人补齐授权。组**未被引用**时不带 `force` 也会直接删除（`{"status":"ok","cleaned_acl_entries":0}`）。

## 8. 分类与标签

**分类**：

```bash
curl -s "$BASE/admin/categories" -H "Authorization: Bearer $TOKEN"   # 管理侧含 is_active=false
curl -s -X POST "$BASE/admin/categories" -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{ "name": "研发工具", "slug": "dev-tools", "description": "研发日常使用", "icon": "wrench", "sort_order": 10, "is_active": true }'
curl -s -X PUT "$BASE/admin/categories/order" -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" -d '{ "items": [ { "id": 3, "sort_order": 10 }, { "id": 4, "sort_order": 20 } ] }'
curl -s -X DELETE "$BASE/admin/categories/3" -H "Authorization: Bearer $TOKEN"
```

`name` 必填 1~64 **唯一**；`slug` 选填 ≤ 64 **唯一**（留空由 `name` 转写，中文转不出可读 slug 时回退 `cat-<时间戳>`）；`description` ≤ 500；`icon` ≤ 64；`sort_order` 整数（越小越靠前）；`is_active` 布尔。重名/重 slug → `400 DUPLICATE_ENTRY`。排序 `items` 1~200、一次事务写完，有 id 不存在 → `404 NOT_FOUND`（`details.missing_ids`）。
**删除 = 软删除**（置 `is_active=false`），**禁止物理删除**（`tools.category_id` 有外键，硬删会让工具悬空）：有未删除工具引用 → `409 CATEGORY_IN_USE`（`details` 为 `{category_id, tool_count}`）；无引用 → `{"status":"ok","soft_deleted":true}`。要真正移除分类，只能先把引用它的工具改到别的分类（由作者在编辑器里改）。

**标签**：

```bash
curl -s "$BASE/admin/tags?q=py&page=1&page_size=50" -H "Authorization: Bearer $TOKEN"
curl -s -X PATCH "$BASE/admin/tags/7" -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" -d '{ "display_name": "Python" }'
curl -s -X POST "$BASE/admin/tags/merge" -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" -d '{ "source_ids": [7, 9], "target_id": 12 }'
curl -s -X POST "$BASE/admin/tags/cleanup" -H "Authorization: Bearer $TOKEN"
```

- 列表按引用数倒序，`q` 是**前缀搜索**（不是模糊搜索）；`page_size` 1~200 默认 50。
- **重命名**字段名 `display_name`，长度 1~64，**全站生效**；归一化 key 与已有标签撞车 → `400 DUPLICATE_ENTRY`（message「已存在，请改用合并」）—— 这正是该用合并的场景。
- **合并**：`source_ids` 1~100（被消灭的标签）、`target_id`（保留的目标）；`target_id` 出现在 `source_ids` 里 → `400 VALIDATION_ERROR`；任一 id 不存在 → `404 NOT_FOUND`（`missing_ids`）。响应 `{target_id, target_name, merged_tags, moved_references, deduplicated_references, deleted_tags}`：合并前 source 标签被引用的**总条数 = `moved_references` + `deduplicated_references`**；`deduplicated_references` = 工具**同时**打了 source 与 target 的重复关联，**直接删除**（否则改指向会撞 `(tool_id, tag_id)` 复合主键）；`moved_references` = 其余**改指向** target 的条数。合并后 source 标签行被删除，`usage_count` 全量重算。
- **清理零引用**：先**重算** `usage_count`，再删确实没有任何 `tool_tags` 关联的标签（双重确认）；响应 `{deleted, tags:[展示名...]}`。

> 提醒：`tags.usage_count` **不在增删关联时实时维护**，由定时任务重算，列表里的引用数可能短暂偏旧；判断「是否零引用」以 `cleanup` 结果为准 —— 它自己会先重算。

## 9. 全站工具与回收站

**全站工具列表**：

```bash
curl -s "$BASE/admin/tools?status=approved&status=offline&type=skill&category=dev-tools&owner=zhangsan&page=1&page_size=50" -H "Authorization: Bearer $TOKEN"
```

参数：`q`（对**名称与简介**模糊匹配）；`status` 可重复（`draft`/`pending`/`approved`/`rejected`/`pending_update`/`offline`）；`type` 可重复（**别名是 `type`，不是 `tool_type`**）；`category` 可重复（传分类 **slug**）；`visibility` 可重复（`public`/`restricted`/`private`）；`owner`（作者 `username`）；`include_deleted`（默认 `false`，`true` 时连回收站一起列出）；`date_from`/`date_to`（按 `created_at`）；`page_size` 1~200 默认 20。排序固定 `updated_at` 倒序、`id` 倒序。每行带 `reject_reason`、`offline_reason`（可直接看到理由）与 `version_seq`。

**转移负责人**：

```bash
curl -s -X POST "$BASE/admin/tools/12/transfer" -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{ "new_owner_id": 43, "reason": "原负责人转岗，交接给李四" }'
```

`new_owner_id` 必填、`reason` 选填 ≤ 2000。失败：目标用户不存在 → `404 NOT_FOUND`；目标已禁用 → `400 VALIDATION_ERROR`；目标就是现任负责人 → `409 STATE_CONFLICT`。响应 `{tool_id, previous_owner, new_owner, previous_owner_used_bytes, new_owner_used_bytes, approval_record_id}`。
**配额如何重算**：平台**没有「用户配额余额表」**，用量是**按 owner 实时聚合**（`SUM(tool_versions.file_size) WHERE owner=?`）。所以转移这个动作本身就改变了双方用量，无需额外记账；响应里两个字节数就是**转移后重新聚合**的结果，据此判断新负责人是否接近 `quota.per_user_mb`。
**留痕**：写一条 `approval_records`，`action=transfer_owner`，`from_status` 与 `to_status` **相同**，`note` 形如「负责人由 张三 转移给 李四」，`reason` 为你填的理由（可在 `/admin/approvals/history?tool_id=12` 查到）。**副作用**：`version_seq` +1 → **正在审批中的条目会因乐观锁失效而拿到 `ALREADY_PROCESSED`**（有意为之）。

**回收站**：软删除（`deleted_at` 置值）后工具从门户与搜索消失，但库行与磁盘文件保留，**30 天后**由每日清理任务彻底清除。

```bash
curl -s "$BASE/admin/recycle-bin?page=1&page_size=20" -H "Authorization: Bearer $TOKEN"
curl -s -X POST "$BASE/admin/tools/12/restore" -H "Authorization: Bearer $TOKEN"
```

还原会清空 `deleted_at` 与 `deleted_by_id`、重新写回搜索索引；不在回收站中的工具 → `409 STATE_CONFLICT`。**还原不改变 `status`**，它回到删除前的状态。

> **管理员没有「把别人的工具移入回收站」的接口。** 软删除只有作者的 `DELETE /api/v1/me/tools/{id}`（严格校验 owner，超管也过不去）。管理侧对回收站只有**查看 → 还原 / 彻底清除**；要停掉别人的工具请用**下架**。

> 🚨 **危险操作：彻底清除（`purge`），不可撤销。** 删除该工具的**全部版本文件、全部图片（含缩略图）、搜索索引与数据库行**，且 `tool_versions`/`tool_tags`/`tool_acl`/`approval_records` 随外键 CASCADE 一并消失 —— **审批历史也一起没了**。需要留档时**不要用**这个接口，改用下架。
>
> ```bash
> curl -s -X DELETE "$BASE/admin/tools/12/purge" -H "Authorization: Bearer $TOKEN"
> # → {"tool_id":12,"purged_files":7,"purged_versions":4}
> ```
>
> `purged_files` = 实际删除的磁盘文件数（版本文件 + 封面/截图及缩略图）；`purged_versions` = 版本行数。**删除顺序是「先删文件、再删数据库行」** —— 反过来一旦删文件失败，库里已无记录指向那些文件，它们就成了谁也认不出的孤儿文件，只能靠运维扫盘兜底。

**管理侧代创建**：

```bash
curl -s -X POST "$BASE/admin/tools" -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{ "name": "巡检脚本集", "summary": "日常巡检常用脚本合集", "description_md": "## 包含\n\n- 磁盘检查",
        "tool_type": "file", "owner_id": 42, "category_id": 3, "tags": ["ops", "shell"],
        "visibility": "public", "publish": false }'
```

与 `/me/tools` 的关键差别：**允许指定 `owner_id`**，绕过 owner 校验（由 `admin:all` 授权）。`publish` 默认 `false`（建为草稿）；设 `true` 会**跳过审批直接发布**，并写一条 `approve` 记录（`note="admin 代创建并直接发布"`）以保审计链完整。约束：`owner_id` 必须存在且**启用**；`category_id` 必须存在且 `is_active`；`tool_type=webapp` 时 `webapp_url` 必填。

> ⚠️ **`POST /admin/tools/{tool_id}/versions` 当前不可用** —— 固定返回 `404 NOT_FOUND`，提示改用 `/api/v1/me/tools/{id}/versions`。管理侧**没有**代上传能力，代创建的草稿仍须作者本人上传版本。

## 10. 免审白名单

白名单让**指定用户**提交的工具与版本**跳过人工审批**直接 `approved`。适合可信自动化账号（CI 机器人）、长期高频发布且已建立信任的核心维护者。

> 🚨 **风险**：白名单用户上传的任何内容都会**立即对门户可见**，没有任何人事前看过 —— 它等价于把审批权交给这个人。请只给确实需要的账号，并**优先用 `expires_at` 设有效期**，不要长期挂一份只增不减的名单。

```bash
curl -s "$BASE/admin/approval-whitelist" -H "Authorization: Bearer $TOKEN"
curl -s -X POST "$BASE/admin/approval-whitelist" -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{ "user_id": 42, "reason": "CI 发布机器人，2025 Q2 例行放行", "expires_at": "2025-06-30T00:00:00Z" }'
curl -s -X DELETE "$BASE/admin/approval-whitelist/42" -H "Authorization: Bearer $TOKEN"
```

`user_id` 必填；`reason` 选填、最长 **255**（比审批理由短得多）；`expires_at` 选填、**省略即永久**。失败：用户不存在 → `404 NOT_FOUND`；用户已禁用 → `400 VALIDATION_ERROR`；移出时不在名单 → `404 NOT_FOUND`。返回 `user_id`、`username`、`display_name`、`reason`、`added_by_id`、`added_by_name`、`expires_at`、`created_at`、`is_effective`。**`is_effective` 只表示「未过期」，不反映总开关状态** —— 总开关关闭时即使它为 `true` 也不放行。

## 11. 审批模式开关

`approval.mode` 默认 `"require"`（需人工审批）/ 可设 `"auto_approve_all"`（全部放行）；`approval.whitelist_enabled` 默认 `true`（免审白名单总开关）。

**真实判定逻辑**（`settings_service.evaluate_auto_approval`），**先看全局开关、再看白名单**：① `approval.mode == "auto_approve_all"` → 放行，规则记 `auto_approve_all`；② 否则若 `approval.whitelist_enabled == true` **且**该用户在**未过期**白名单内 → 放行，规则记 `whitelist`；③ 否则 → 进人工队列。命中后工具直接 `approved`、当前版本立即切换，审批记录里 `is_automatic=true`、`auto_rule` 记命中规则、`actor_label="系统自动放行"`、`actor_id=null`。**自动放行只在「真正提交」时评估** —— 单纯上传一个不提交的草稿不会触发。

> 🚨 **危险操作：切 `auto_approve_all`。** 打开后**此后所有提交都无需人工审批**，任何作者上传即发布，平台失去人工审核这层保护。请在维护窗口内操作，并**尽快切回 `require`**。

```bash
curl -s -X PUT "$BASE/admin/settings" -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{ "items": [ { "key": "approval.mode", "value": "auto_approve_all" } ] }'
```

`value` 只接受 `require` 或 `auto_approve_all`，其他值 → `400 SETTING_INVALID`。**关键提醒（`FR-APPR-02`）**：切换**不会**自动处理已 `pending` 的条目，它们仍留在队列里，需你手动或批量批准。有积压时响应会带提示：

```json
{ "items": [ "..." ],
  "warnings": [ { "code": "PENDING_ITEMS_NOT_AFFECTED",
                  "message": "当前有 5 个待审条目，切换为全部放行不会自动处理它们。",
                  "pending_count": 5 } ] }
```

关闭白名单：把 `approval.whitelist_enabled` 设为 `false`（同样格式）；关掉后**名单还在但不生效**。

**`approval.version_reapproval`（默认 `true`）：当前未接入。** 设置项清单与界面上都有这个「已发布工具发新版本是否需再审」开关，但**实现没有任何代码消费它**（`backend/app` 内除设置项定义与迁移种子数据外无读取方），它甚至没有 `SETTING_SPECS` 元信息。实际行为固定为「已发布工具上传新版本 → `pending_update` 进队列」（相当于恒为需再审）。**所以设置它目前没有任何效果。**

## 12. API Token

`st_` 前缀 + 43 位 base64url 随机字符；库里只存 **SHA256** 与可读前缀（明文前 8 位），**明文不落库、不打日志**；**明文只在签发响应里出现一次**，列表接口**永远不返回明文**。鉴权取「Token 的 scopes」与「**创建者当前角色**权限」的**交集**，不做签发时快照。

```bash
curl -s -X POST "$BASE/admin/tokens" -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{ "name": "CI 发布脚本", "scopes": ["tools:read", "tools:write"],
        "note": "Jenkins job: publish-selftool", "expires_at": "2025-12-31T00:00:00Z" }'
```

`name` 必填 1~128；`scopes` 必填 ≥ 1 个（重复项自动去重）；`note` 选填 ≤ 255；`expires_at` **省略 → 默认 90 天**，显式传 `null` → **永不过期**。响应 `201` 含 `id`、`name`、`note`、`token`（**明文，仅此一次**）、`token_prefix`、`scopes`、`created_by_id`、`created_by_name`、`expires_at`、`last_used_at`、`last_used_ip`、`revoked_at`、`created_at`、`is_active`、`warning`（「请立即复制保存。此 Token 不会再次显示。」）。

> **`token` 关闭页面后再也拿不到。** 立刻存进密钥管理系统或 CI 凭据库，不要贴在工单、聊天记录、代码仓库里。

**Scope 子集校验**：每个 scope 必须是创建者权限的子集，否则 `403 FORBIDDEN`（`details.exceeds` 列出超出的 scope）；`admin:all` 额外要求创建者是 `superadmin`。

| 场景 | 建议 scopes | 说明 |
| --- | --- | --- |
| 只读脚本拉门户数据 / `skill-preview` | `tools:read` | 门户类接口都要求它 |
| CI 发布工具（建工具/传版本/提交） | `tools:write` + `tools:read` | 写接口要 `tools:write` |
| 审批机器人 | `approvals:write` + `tools:read` | **只给 `approvals:write` 会导致 `skill-preview` 403** |
| 批量导入导出 | `admin:all` | 没有更细的 scope |
| 用户 / 用户组运维 | `users:write` / `groups:write` | 各自独立 |
| 分类与标签维护 | `taxonomy:write` | |
| 设置与 Token 自助管理 | `settings:write` | 含签发/吊销 Token |
| 全站工具 + 回收站 + 存储明细 | `admin:all` | |

**`admin:all` 的含义与风险**：展开成全部权限点，等于把用户管理、系统设置、全站工具（含**彻底清除**）、导入导出全部交给这个 Token，且签名者必须是 superadmin。**风险**：泄露后攻击者可创建超管账号、关闭审批、清空回收站。只在确实需要跨权限域的批处理脚本上使用，并设较短的 `expires_at`。

```bash
curl -s "$BASE/admin/tokens?include_revoked=true&page=1&page_size=20" -H "Authorization: Bearer $TOKEN"
curl -s "$BASE/admin/tokens?include_revoked=false" -H "Authorization: Bearer $TOKEN"  # 只看生效的
curl -s -X POST "$BASE/admin/tokens/5/revoke" -H "Authorization: Bearer $TOKEN"       # 吊销
curl -s -X DELETE "$BASE/admin/tokens/5" -H "Authorization: Bearer $TOKEN"            # 物理删除
```

`is_active` = 未吊销 **且**（无过期时间 或 未过期）；排查「脚本突然 401」先看它。

> 🚨 **危险操作：全量吊销 Token。** 平台**没有**「一键吊销全部 Token」接口，但**禁用用户会连带吊销该用户全部 API Token 与登录会话，且启用后不恢复** —— 这是事实上的「全量吊销」。它会立刻打断该用户名下所有仍在跑的脚本与自动化，执行前请先确认 `active_token_count` 与受影响任务。
>
> 🚨 **吊销 vs 物理删除，选错会丢审计。** **吊销**（`POST .../revoke`）置 `revoked_at`、**立即失效**、行还在，可查签发人与最后使用情况 —— **日常一律用这个**；该接口**不接受请求体**，也没有理由字段。**物理删除**（`DELETE ...`）把行直接删掉，`created_by`/`last_used_*`/scope 记录一并丢失，仅用于清理测试期或确认无审计价值的垃圾行。两者都**没有批量版本**，需逐个处理；吊销是幂等的。

| 事件 | Token 行为 | 调用方看到 |
| --- | --- | --- |
| 创建者被**禁用** | 立即**不可用**（禁用时已连带吊销） | `401 TOKEN_REVOKED`（「创建者已被禁用」） |
| 创建者被**降级** | 立即**降权**（scopes ∩ 新角色权限） | 越权 `403 SCOPE_MISSING`（`details.missing_scopes`） |
| 创建者被**重新启用** | 仍是吊销状态，**不恢复** | 需重新签发 |
| Token 自身过期 | 不可用 | `401 TOKEN_EXPIRED` |
| Token 被吊销 | 不可用 | `401 TOKEN_REVOKED` |

登录会话与 API Token 是两套东西：**重置密码、强制下线只影响会话**；API Token 只在**禁用用户**或**显式吊销**时才失效。

## 13. 批量导入的坑

两条硬保证：导出 CSV **带 UTF-8 BOM**（否则 Excel 打开中文乱码）；`generated_passwords` 是**全平台唯一的明文回显例外，绝不写日志**。

**用户导入（CSV）**：

```bash
# 先预演（不写库、不生成密码），确认无误后把 dry_run 改成 false 再执行一次
curl -s -X POST "$BASE/admin/import/users" -H "Authorization: Bearer $TOKEN" \
  -F "file=@users.csv" -F "dry_run=true" -F "on_conflict=skip"
```

> multipart 请求**不要**加 `Content-Type: application/json`，`curl -F` 会自己带上正确的边界。

导入实际读取的列：`username`（必填，转小写、只允许字母数字下划线点连字符、**文件内不能重复**）、`display_name`（留空则用 `username`）、`email`（留空存 `null`）、`roles`（**分号 `;`** 分隔，留空默认 `user`，未知角色报错）、`password`（留空则生成并回显，填了则校验强度）。

**可复制的 CSV 样例**（存为 `users.csv`，**保存为 UTF-8**）：

```csv
username,display_name,email,roles,password
lisi,李四,lisi@example.com,user,
wangwu,王五,,user;approver,
zhaoliu,赵六,zhaoliu@example.com,viewer,
admin2,运维二号,ops@example.com,superadmin,Init#Pass2025
```

第 1 行是表头，**数据从第 2 行起**，所以错误报告里的 `row` 从 **2** 起算。`roles` 用分号**不是逗号**（逗号是 CSV 分隔符，会撕裂成两列）。密码列建议留空让系统生成。
**`dry_run`**：`true` 时**完全不写数据库**（结束 rollback）、**不生成密码**（`generated_passwords` 恒为 `[]`），只返回预演统计；`false` 时**整批一个事务**提交。
**`on_conflict` 三种策略**（`username` 已存在时）：`skip`（默认）跳过并计入 `skipped`；`update` 更新 `display_name`/`email`/**角色（全量替换）**、**不动密码**，计入 `succeeded`；`fail` 报「用户已存在」并计入 `failed`。其他值（如 `overwrite`）→ `failed: 1` 且 `errors[0].field = "on_conflict"`。
**错误如何定位到行与字段**：`errors[]` 每项为 `{row, field, value, message}`，例如 `{"row":4,"field":"roles","value":"root","message":"未知角色：root"}`；`row` 是 CSV 行号（表头为第 1 行），`field` 是列名，`value` 是**导致问题的原值**（密码类字段用 `***` 占位）。**部分失败不影响成功行**。其他限制：单次最多 **2000 行**（超出时 `failed = 行数`、`errors[0]={row:0, field:"file"}`）；编码按 `utf-8-sig` → `utf-8` → `gb18030` 依次尝试。新建用户固定 `status=active`、`must_change_password=true` —— **`status` 列在导入时被忽略**，无法用 CSV 直接导入 `disabled` 用户。

> 🚨 **`generated_passwords` 是一次性明文**（如 `{"username":"lisi","password":"StK7mPq2xRv9!7"}`）。① 立刻用界面「下载 CSV」存到受控位置；② **不要**粘进聊天工具、工单、Wiki、代码仓库；③ 通过安全渠道逐个告知用户并要求首次登录改密；④ 关页后无法取回，只能对相关用户重置密码。

**用户导出**：

```bash
curl -s "$BASE/admin/export/users" -H "Authorization: Bearer $TOKEN" -o users.csv
```

带 **UTF-8 BOM**（前 3 字节 `EF BB BF`）；列为 `username,display_name,email,roles,status`（`roles` 用 `;` 分隔）、行尾 `CRLF`；**绝不含密码哈希**。注意：**导出不含 `password` 列但导入认它；导出含 `status` 列但导入忽略它** —— 「导出 → 改 → 再导入」不会恢复状态，也不会带上密码。

**工具导入（JSON）**：

```bash
curl -s -X POST "$BASE/admin/import/tools" -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{ "dry_run": true, "on_conflict": "skip",
        "items": [ { "name": "巡检脚本集", "summary": "日常巡检常用脚本合集",
                     "description_md": "## 包含\n\n- 磁盘检查", "tool_type": "file",
                     "owner_username": "zhangsan", "category_slug": "dev-tools",
                     "tags": ["ops","shell"], "visibility": "public", "publish": false } ] }'
```

条目字段：`name` 必填 1~128；`slug` 选填（**判重键**，缺省由 `name` 生成）；`summary` 选填 ≤ 500；`description_md` 选填 ≤ 100000；`tool_type` 必填（`file`/`webapp`/`skill`/`prompt`）；`owner_username` 选填、**默认 `admin`**（该用户必须存在）；`category_slug` 选填（必须存在）；`tags` 选填（最多取前 8 个）；`visibility` 默认 `public`；`webapp_url`（`tool_type=webapp` 时必填）；`publish` 默认 **`true`**。`items` 长度 1~500，`dry_run`/`on_conflict` 在**请求体**里（不是 form）。
**冲突按 `slug` 判重**：`skip` 跳过；`update` 更新 `name`/`summary`/`description_md`/分类/可见性/**负责人**（**不动标签与状态**）；`fail` 报「slug 已存在」。错误定位：工具导入的 `row` 从 **1** 开始（是 JSON 数组不是 CSV）；逐行校验 `name`、`webapp_url`、`owner_username`、`category_slug`、`slug`。

> ⚠️ **`owner_username` 默认值是 `admin`。** 环境里没有叫 `admin` 的用户时，忘了填这一列的行会全部报「用户不存在：admin」。批量导入请**显式写清每一行的 `owner_username`**。
>
> ⚠️ **`publish` 默认 `true`** —— 导入即发布、**跳过审批**。灌历史数据时若不想直接上架，记得显式传 `"publish": false`。

**工具导出**：

```bash
curl -s "$BASE/admin/export/tools" -H "Authorization: Bearer $TOKEN" -o tools.json
```

流式输出 JSON 数组，**只含未删除的工具**；字段包括 `id`、`slug`、`name`、`summary`、`description_md`、`tool_type`、`visibility`、`status`、`owner_username`、`category_slug`、`tags`、`webapp_url`、`download_count`、`view_count`、`published_at`、`created_at`、`updated_at`。**不含版本内容与文件** —— 工具本体不随导入导出迁移。

## 14. 存储配额与水位判断

```bash
curl -s "$BASE/admin/overview" -H "Authorization: Bearer $TOKEN"                        # approver 即可
curl -s "$BASE/admin/stats/storage?limit=50&offset=0" -H "Authorization: Bearer $TOKEN"  # superadmin
```

**`/admin/overview`**：`user_count`/`active_user_count`/`disabled_user_count`；`tool_count`（**未删除**工具总数）；`tools_by_status`（顺序固定 `draft`、`pending`、`approved`、`rejected`、`pending_update`、`offline`）；`pending_count`（**= `pending` + `pending_update`**）；`category_count`/`tag_count`/`group_count`（**含停用/禁用**）；`active_token_count`；`download_count`/`view_count`（**累计**，只统计未删除工具）；`used_bytes`/`quota_bytes`/`used_percent`；`downloads_last_7_days`（近 7 日下载**明细**条数，取自 `download_logs`，**不是** `download_count` 的增量）；`recycle_bin_count`。

> **口径提醒（`used_bytes` 偏高）**：它是 `SUM(tool_versions.file_size)`，**没有**过滤 `deleted_at`，也**没有**排除 `purged` 状态的版本行。所以回收站里的工具、以及已归档（文件已删但行还在）的版本都仍计入。它是**保守偏高的估计**，适合作告警线，不适合作计费口径。

**`/admin/stats/storage`** 概览：`total_used_bytes`（全部版本行 `file_size` 之和）、`total_quota_bytes`（`quota.total_mb`，缺失按 51200 MB 兜底）、`used_percent`、`file_count`（**版本行数**，不是磁盘文件数）、`orphan_file_count`（**当前恒为 0**，见下）、`total`（**曾拥有过工具的负责人数（按 `tools.owner_id` 去重、不含软删除过滤）**，因此可能大于 `items` 的条数）、`page`/`page_size`。`items[]`（**按 `used_bytes` 倒序**，直接回答「谁占了空间」）：`owner_id`、`username`、`display_name`、`tool_count`（该负责人**未删除**工具数）、`version_count`、`used_bytes`、`quota_bytes`（= `quota.per_user_mb` × 1048576）、`used_percent`。`limit` 1~200 默认 20。

**怎么判断谁占了空间**：① 调 `/admin/stats/storage?limit=200&offset=0`，`items` 已按用量倒序，第一屏就是大户；② 换算 `used_bytes / 1048576` = MB、`/ 1073741824` = GB；③ `used_percent` 接近 100% → 该用户**已经传不动新版本**（上传拿 `507 USER_QUOTA_EXCEEDED`）；`tool_count` 小而 `used_bytes` 大 → 单个工具塞了大文件；`version_count` 大 → 历史版本堆积（`version.history_limit` 默认 10，只在**新版本上传/批准时**触发淘汰，长期不更新的工具会一直留着旧文件）；④ 平台水位看 `used_percent`：接近满时新上传拿 `507 INSUFFICIENT_STORAGE`，磁盘满则 `503 STORAGE_FULL`；⑤ 要精确到「哪个版本占多少」，走 `/admin/tools` → 门户详情页版本列表（每条带 `file_size`）。**管理员没有直接删除单个版本的接口**（删版本是 `DELETE /api/v1/me/tools/{id}/versions/{version}`，仅作者、且仅限未过审版本）；管理侧手段是下架、转移负责人、回收站还原/彻底清除。

> ⚠️ **`quota.warn_threshold_pct`（默认 85）：当前尚未接入，设置它暂无效果。** 全仓检索：它只出现在 ① 迁移 `0002` 的种子数据、② `repositories/system_settings.py` 的 `SETTING_DEFAULTS` 与 `SETTING_SPECS`（范围 1~100）、③ 文档、④ 前端 mock 数据；`backend/app` 里**没有任何逻辑读取它**，也没有任何地方用它发告警。管理台可以改、能存、能读回，但**越过阈值不会触发任何提示或动作**；`docs/02 §3.19` 写的「达到此百分比时告警」目前**未实现**。**替代做法**：只能靠人看 —— 读 `/admin/overview` 与 `/admin/stats/storage` 的 `used_percent`，或按 `docs/03 §5.3` 的思路写定时脚本查询并自行告警。

## 15. 常见管理操作 FAQ

**Q1. 队列里明明有新版本待审，我却看不到？** 过滤条件大概率写成了 `status=pending`。`pending` **只含首次提交**，新版本是 `pending_update`；省略 `status`（或传 `pending_all`）才是并集。

**Q2. 批准提示 `ALREADY_PROCESSED`？** 在你打开列表之后有人先处理了它，或发生了下架/转移负责人（都推进 `version_seq`）。刷新列表重看，**不要重试同一请求**；`details` 里有 `expected_version_seq` 与 `actual_version_seq` 可核对。

**Q3. 驳回了新版本，为什么工具还是「已发布」？** 这是正确行为：驳回**新版本**只让该版本变 `rejected`、工具退回 `approved`、**线上当前版本不受影响**；只有驳回**首次提交**才让工具变 `rejected`。

**Q4. 用户离职了，能删掉账号吗？** 不能，也没有这个接口（外键关联会打断审计链）。应**禁用**（连带吊销其全部会话与 API Token），再用 `POST /admin/tools/{id}/transfer` 把工具**转移给接手人**。

**Q5. 想换掉最后一个超管，一直报 `409 LAST_SUPERADMIN`？** 换人顺序要**先加后减**：先给新管理员 `PUT /admin/users/{id}/roles` 加上 `superadmin`，确认生效后再对原超管去掉 `superadmin`（或禁用）；操作过程中必须**始终至少有一个启用的超管**。

**Q6. 我既是超管又是被调整对象，报「不能禁用/降级自己」？** 自我锁死防护：禁用自己 → `400`（`details.reason="self_disable"`）；给自己去掉 `superadmin` → `400`（`reason="self_demote"`）。**先让另一位超管操作你**。

**Q7. 禁用了某人，他的脚本报 `ACCOUNT_DISABLED` 而不是 Token 错误？** `ACCOUNT_DISABLED`（`403`）是**登录会话**（JWT）路径的错误；API Token 路径是 `401 TOKEN_REVOKED`（「创建者已被禁用」）。两者都被拦，只是码不同；重新启用后必须重新登录并重新签发 Token。

**Q8. 重置了密码，为什么用户还能用旧 Token 跑脚本？** 设计如此：**重置密码只吊销会话，不吊销 API Token**。要一并失效请**禁用**该用户或逐个 `POST /admin/tokens/{id}/revoke`；目前**没有**一键吊销某用户全部 Token 的接口。

**Q9. 删用户组报 `GROUP_IN_USE`，`force=true` 到底删什么？** 删掉组，并**连带删除引用它的全部 ACL 条目**；`affected_tools` 列出受影响的工具，`cleaned_acl_entries` 是清理条数。删完后组内成员立即失去访问权，务必先看清影响面并通知相关工具负责人补授权。

**Q10. 删分类报 `CATEGORY_IN_USE`，怎么才能删掉？** 分类只做软删除且禁止物理删除（外键会让工具悬空）。只能先把引用它的工具改到别的分类（由作者在编辑器里改），引用清零后再删；删除效果是 `is_active=false`，存量工具仍挂着它。

**Q11. 合并标签时 `moved_references` 与 `deduplicated_references` 是什么？** 合并前 source 标签的总引用数 = 两者之和。`deduplicated_references` 是「工具同时打了 source 与 target」的重复关联（直接删掉，否则会撞复合主键）；`moved_references` 是其余被改指向 target 的关联。

**Q12. 标签引用数看起来不对（没人用了还显示 3）？** `usage_count` 不在增删关联时实时维护，由定时任务重算，会短暂偏旧。直接跑 `POST /admin/tags/cleanup` —— 它会**先重算**再删真正零引用的标签。

**Q13. 打开 `auto_approve_all` 后，队列积压会自动清空吗？** 不会。切换只影响**此后**的提交；已 `pending`/`pending_update` 的条目仍在队列里，需你手动或批量批准（`warnings` 的 `PENDING_ITEMS_NOT_AFFECTED` 会告知积压数量）。

**Q14. 我把「新版本需重新审批」关了，为什么新版本还要审批？** 该项（`approval.version_reapproval`）**当前未接入实现**，设置后无任何效果（§11）；要免审请用白名单或 `auto_approve_all`。

**Q15. 改了「告警阈值」，为什么从来没收到告警？** `quota.warn_threshold_pct` 目前只存储、**没有任何消费方**（§14）；请用 `/admin/overview` 与 `/admin/stats/storage` 的 `used_percent` 自行观察或写外部巡检脚本。

**Q16. API Token 明文没存下来，能再显示一次吗？** 不能。库里只有 SHA256 与 8 位前缀，列表接口**永远不返回明文**；只能吊销旧 Token 并重新签发。

**Q17. 用 `admin:all` 的 Token 调批准接口报 `403`？** 有效权限 =「scopes ∩ 创建者**当前**角色权限」；创建者被降级成没有 `approvals:write` 的角色时，即使 Token 带 `admin:all` 也过不了；`details.missing_scopes` 会指明缺哪个。

**Q18. 用只带 `approvals:write` 的 Token 打不开 `skill-preview`？** 该接口走门户鉴权，要求 `tools:read`；审批机器人请授 `approvals:write` + `tools:read`（`details.missing_scopes` 会显示 `["tools:read"]`）。

**Q19. 工具导入后一堆行报「用户不存在：admin」？** `owner_username` 省略时默认 `admin`；请显式填每一行的 `owner_username`，且该用户必须**已存在**。

**Q20. 导入工具后发现全都直接发布了，能先建草稿吗？** 可以，显式传 `"publish": false`；工具导入的 `publish` 默认是 **`true`**。

**Q21. 管理员能帮别人把工具移入回收站吗？** 不能。软删除只有作者的 `DELETE /api/v1/me/tools/{id}`（严格校验 owner）；管理侧对回收站只有**查看、还原、彻底清除**，要停掉别人的工具请用**下架**。

**Q22. 回收站里的工具多久自动消失？彻底清除后能恢复吗？** 保留 **30 天**，超期由每日任务彻底清除；彻底清除**不可恢复**（文件、图片、搜索索引、数据库行含审批历史全部删除），需要留档请改用下架。

**Q23. 批量导入用户后 `generated_passwords` 是空的？** 用了 `dry_run=true`（**不生成密码**），或 CSV 的 `password` 列填了值（用你填的）；只有「正式导入 + 密码列留空 + 用户是新建」才生成。

**Q24. `/admin/stats/storage` 的 `orphan_file_count` 一直是 0，是没问题吗？** 不是「没问题」，而是**该字段当前没有被实现填充**，恒为 0；磁盘孤儿文件需运维侧扫盘核对。
