# 前端 UI/UX 审查

**方法**：Playwright 渲染真实页面 → 提取**计算样式**（颜色、尺寸、可访问名、几何）做量化判定
**范围**：10 个页面 × 浅色/深色两套主题，共 812 个文本节点、约 300 个可交互元素
**工具**：`/tmp/uicontrast2.cjs`、`/tmp/uiaudit.cjs`（一次性脚本，非交付物）

> **局限性（必须先说明）**：本次审查的模型**无法读取截图**，因此没有做视觉审美判断。
> 下面全部是**可测量**的问题（对比度、命中区、可访问名）。
> 视觉层面的建议集中在 §6，标注为**未验证的判断**。

## 2. 真实问题（按修复价值排序）

### U1. 浅色主题 `muted-foreground` on `muted` = **4.45:1**，差 0.05 到 AA

**这是浅色主题 66 个不达标里的 ~65 个。**

| 项 | 值 |
| --- | --- |
| 前景 | `--muted-foreground: oklch(0.55 0.02 265)` |
| 背景 | `--muted: oklch(0.97 0.005 265)` → 实测 `rgb(243,245,249)` |
| 实测对比度 | **4.45 : 1**（WCAG AA 普通文本要求 ≥ 4.5） |
| 影响面 | 门户的标签 chips（`#log`/`#demo`/`#storage`…）、ⓘ 搜索框里的 `⌘K` 徽标——**每个页面都有** |

**修法：一处令牌改动**。把 `src/index.css` 里的 `--muted-foreground` 从
`oklch(0.55 0.02 265)` 降到约 `oklch(0.53 0.02 265)`。

> **收益**：一次改动修掉 65/66 个不达标项。这是本次审查里性价比最高的一项。
> **代价**：几乎不可感知的观感变化（4.45 → 约 4.6）。
>
> 也可以反向调 `--muted`（调亮），但那会让 chip 与卡片背景的区分度下降，不推荐。

### U2. 深色主题 `已驳回 0` 徽标 = **3.54:1**

| 项 | 值 |
| --- | --- |
| 位置 | 管理概览页的工具状态分布徽标 |
| 前景 / 背景 | `rgb(255,255,255)` on `rgb(237,83,80)`（destructive 底） |
| 实测 | **3.54 : 1** @ 12px（要求 4.5，差得多） |

深色主题唯一的缺陷。修法：`--destructive` 在 `.dark` 下从 `oklch(0.65 0.19 25)`
再压暗一点，或该徽标在深色下改用 `--destructive-foreground` 的深色文字（现有 token 里
`.dark` 的 `--destructive-foreground` 是 `oklch(0.16 0.02 265)`，即深色文字 ——
**说明这个徽标用错了前景 token**，用的是白色而不是 `--destructive-foreground`）。

> **这更像是一个 bug 而不是调色问题**：`Badge` 的 destructive 变体可能硬编码了白字。

### U3. 管理台表格的行选择 checkbox：**真实命中区只有 16×16**

用户管理（以及其它带多选的 `DataTable`）的每行 checkbox：

```tsx
<Checkbox
  checked={...}
  aria-label={...}          // ← 可访问名有，这点是对的
  onCheckedChange={...}
/>
```

它**没有 `<label>` 包裹**，所以真实可点击区域就是 16×16。
对比：门户的筛选 checkbox 控件本身也是 16×16，但被 `<label>` 包住，**实际命中 198×20**。

**这是全部控件里唯一真实的命中区问题。** 修法：给表格里的 checkbox 加
`className="size-4 ... p-2 -m-2"` 之类的扩展热区，或包一层 `label`。

**影响有限**（桌面鼠标场景，16×16 可点），但既然其它控件都做对了，这一处不统一。

### U4. `cursor: default` 出现在按钮上（**判断题，不是缺陷**）

门户 43 个、设置页 29 个可交互元素的 `cursor` 不是 `pointer`。原因是 shadcn 新版
遵循浏览器原生行为，`<button>` 默认 `cursor: default`。

**我的判断：不改。** 现代设计系统（含 Radix/Tailwind 官方示例）倾向让按钮保持
原生 cursor；`pointer` 是旧习惯。skill 的 checklist 写着 "cursor-pointer on all clickable
elements"，但那是通用清单，不区分「原生按钮」与「div 伪装成按钮」。

**真正需要 pointer 的是「看起来可点但语义不是按钮」的元素** —— 当前代码里这类都用
`<Link>`/`<button>`，没有 `div onClick`，所以这条**实际无需处理**。

## 3. 我自己的 4 个假阳性（透明披露）

审查过程中我报了 4 个问题，**核实后全部是我脚本的 bug，不是 UI 缺陷**。
记录在此，一方面避免误改，另一方面与前几轮要求 agent 达到的证据标准对齐。

| # | 我报的问题 | 真相 | 根因 |
| --- | --- | --- | --- |
| F1 | 可见性选项文字对比度 **1.26:1** | 实际是在 **5% 淡色**上，对比度正常 | 我的 `oklab()` 解析分支**硬编码了 `a = 1`**，把 `bg-primary/5` 当成实心 primary |
| F2 | 16×16 触控目标过小（6 处） | 真实命中区 **198×20 / 395×64** | 只量了控件本身，没算外层 `<label>` |
| F3 | 4 个按钮**无可访问名** | 由 `<label>` + `role`/`aria-checked` 提供，合规 | 只查 `aria-label` 与自身文本，没查 label 关联 |
| F4 | 门户「文本节点 0」 | 实际 297 个 | 颜色是 **`oklch()`**，我的正则只匹配 `rgb()` |

**F1 与 F4 是同一类错误的两次表现：自己写的测量工具本身没被验证，就直接拿它下结论。**
这与我在 M3/M4 前端报告里抓的「mock 比真实更完整」「断言在数据就绪前执行」是同一性质。
**教训：引入新的测量手段时，先用一个已知答案的样本验证它。**
（F1 的验证方式是打印元素到根的完整背景链，一眼就看出 5% 与实心的差别。）

**复测结果（U1 + U2 之后）**：

| 主题 | 修复前 | 修复后 |
| --- | --- | --- |
| 浅色 | 66 / 812 不达标 | **0 / 812** |
| 深色 | 1 / 812 不达标 | **0 / 812** |

**回归**：`npm run verify` 仅 `check:api-types` 失败（**已知的后端阻塞，与本次改动无关**，
见 `contracts/CONTRACT.md` §22.1）；mock E2E **77 passed**，无回归。

**U2 值得单独说明**：它不是调色问题，是**用错了 token**。

改成语义 token 后，浅色仍是白字（值相同，零变化），深色自动变深字。

**U1 先行**：一处令牌改动消除 65/66 个对比度问题。改完用
`/tmp/uicontrast2.cjs` 复测（浅色应从 66 降到 ≤1）。

## 6. 设计层面的建议（**未验证的判断**）

以下**没有实测支撑**，是我基于代码结构与通用设计原则的判断，供参考而非结论。

### 6.1 skill 的建议里，不适用与可用的部分

`ui-ux-pro-max` 对「internal developer tool platform portal」给出的方案是
**「Enterprise Gateway」+「Dark Mode (OLED)」+ Contact Sales CTA** ——
**这是营销落地页的范式，不适用于内网工具门户**（没有转化漏斗、没有销售入口，
且项目明确要求明暗双主题而非 dark-only）。我**没有采纳**其 pattern/风格/配色建议。

可用的部分：
- **Typography 建议 Fira Sans / Fira Code** —— 项目用 Inter + JetBrains Mono，
  **不换**：Inter 的中文混排表现更好，且已在 5 份文档里作为设计令牌固定（`docs/04` §3.1）。
  若要动，属于全局返工，收益不抵成本
- **Pre-Delivery Checklist 的 7 项**：已逐条核过（见 §1 与 §4），仅 U4 有分歧
- **"Avoid: Light mode default"** —— 不适用，内网办公场景明色是主用

### 6.2 我认为值得考虑的方向（需你确认是否要做）

| # | 方向 | 理由 | 成本 |
| --- | --- | --- | --- |
| V1 | **门户卡片封面占位再设计** | 无封面时现在是「分类色块 + 类型图标」。26 个工具里只有 2 个无封面，但**占位色块的观感决定整墙的整齐度**。可考虑：按分类的柔和渐变 + 大号类型图标 + 工具名首字 | 中 |
| V2 | **列表/卡片视图切换的视觉差异化** | 两种视图现在可能只是密度不同。让「列表视图」更偏信息密度（表格式、可扫读），「卡片视图」更偏浏览 | 小 |
| V3 | **空态的插画感** | 目前是图标 + 文案。可以给「无结果」「无工具」「无待审」三类各配一个轻量 SVG | 小 |
| V4 | **管理台表格的密度切换** | 100 人规模下用户表会长。加「紧凑/舒适」切换（8–32px vs 16–64px 间距档），对应 skill 的 `--density` 概念 | 中 |
| V5 | **版本时间线的视觉强化** | 现在是圆点 + 徽标。5 种状态已有色，但**当前版本**可以更强地突出（如加一圈 ring 或左侧强调条） | 小 |
| V6 | **pending 状态的呼吸感** | 「待审」是平台的核心流程状态，但视觉上只是黄色徽标。可给待审计数加轻微 pulse（**且必须 respect `prefers-reduced-motion`** —— 已有该 media query，可复用） | 小 |
| V7 | **深色下的封面图处理** | 用户上传的截图多为浅色背景，在深色主题下会「刺眼」。可给封面容器加深色下的轻微 `opacity`/`brightness` 或边框 | 小 |
| V8 | **⌘K 命令面板的视觉** | 门户的主导航入口，目前应该比较朴素。可加分组标题、快捷键提示、最近访问 | 中 |

**我的建议**：**先做 U1~U3（确定的问题），V 系列只看 V5/V6/V7 这三个小改动** ——
它们影响日常使用体验且成本低。V1/V4/V8 属「锦上添花」，在 M6 收口阶段不建议插入。

### 6.3 不建议做的

| 项 | 原因 |
| --- | --- |
| 改字体（Inter → Fira） | 已在令牌与 5 份文档中固定，且 Inter 中文混排更好 |
| 改成 dark-only | 内网办公场景明色是主用，且 `docs/04` §3.4 定了三态切换 |
| 引入动效库（GSAP 等） | 平台是工具型，动效价值低；且会显著增加包体积（当前首屏 165 KB gzip 已接近良好水平） |
| 加图表/可视化大屏 | `docs/01` 第 10 章明确不做 |
| 换成其它 UI 库 | 无理由，shadcn + Radix 已满足需求 |
