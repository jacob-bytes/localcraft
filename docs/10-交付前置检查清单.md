## 2. 判定口径

| 结果 | 含义 |
| --- | --- |
| `PASS` | 实测通过 |
| `FAIL` | 实测不通过。**已知未交付项（M6 待做）也计为 FAIL** —— 本清单的用途是「交付前必须全绿」，它们到期必须消失 |
| `BLOCKED` | 本机无法检查（缺工具或需目标环境）。不算 FAIL，但**必须在交付说明里显式列出**，不能默认通过 |

**脚本的设计原则**：只报告实测结果，不采信任何 agent 的自述；每项都留下可复核的命令或证据片段。

## 5. 检查过程中的两处自我修正（方法论）

### 5.1 静态检查会被「序列化」骗过

B6 最初写成「grep `tool_acl.py` 里有没有 `can_download`」，结果 **PASS** —— 但那是假阳性：
`tool_acl.py` 只有 `can_download=can_download` 的**写入**。改成 grep「ACL 行的字段读取」后找到 1 处，
**仍然是假阳性**：那处是 `AclEntryOut(can_download=row.can_download)`，只是**把字段序列化给 API 响应**。

**结论：字段「是否被用于授权判定」无法用 grep 判断，只能做行为验证。** 已改为 E14。

### 5.2 行为验证必须有对照组，否则是混淆变量

E14 第一版用 `viewer` 账号，测试 **PASS** —— 但也是假阳性：**`viewer` 角色本来就不能下载**
（FR-ACL-05），所以「下载被拒」无法区分「ACL 生效」与「角色不允许」。

改用 `role=user` 的账号（`zhangsan`）并**加一组 `can_download=true` 的对照**后才成为有区分度的测试，
此时它正确地 **FAIL** 了（`false` 与 `true` 都返回 200）。

> **这两处都是「测试通过但什么都没证明」的典型。** 与我在前端 M3/M4 报告里抓的
> 「mock 比真实后端更完整」「断言在数据就绪前执行」属同一类问题。
> **监控方要求 agent 做到的证据标准，自己也必须达到。**
