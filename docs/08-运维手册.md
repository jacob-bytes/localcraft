# localcraft 运维手册

> **面向运维工程师**：本手册只讲「怎么操作」，照着做即可完成一件事。
> 设计背景与取舍见 `docs/05-部署与运维方案.md`，需要时按章节号回查（例：为什么不能用 `cp` 备份 → docs/05 §8.1）。
> 文中命令与路径**逐条对照过仓库里的真实文件**（`scripts/`、`deploy/`、`backend/app/cli.py`、`backend/app/core/config.py`）。
> 与 docs/05 不一致之处集中在附录 B，请以本手册与脚本实际行为为准。

## 0. 速查：路径、端口、账号

| 项目 | 值 |
| --- | --- |
| 应用代码（软链） | `/opt/localcraft/app/current` |
| 历史版本目录 | `/opt/localcraft/releases/localcraft-<版本>` |
| 虚拟环境 / 运维脚本 | `/opt/localcraft/venv`、`/opt/localcraft/scripts` |
| 环境变量文件 | `/etc/localcraft/localcraft.env`（`0640 root:localcraft`） |
| 数据根 / 文件 / 备份 | `/var/lib/localcraft`、`/var/lib/localcraft/files/`、`/var/lib/localcraft/backups/` |
| SQLite 数据库 | `/var/lib/localcraft/localcraft.db`（附带 `-wal`、`-shm`） |
| 日志 | journald（`-u localcraft.service`）；nginx `/var/log/nginx/localcraft.*.log`；可选 `/var/log/localcraft/` |
| systemd 单元 / logrotate | `/etc/systemd/system/localcraft.service`、`localcraft.slice`；`/etc/logrotate.d/localcraft` |
| 监听 | 应用 `127.0.0.1:8000`（仅回环）；nginx `80`（快速验证）或 `443`（TLS） |
| 服务身份 | 系统用户 `localcraft`，`/sbin/nologin` |
| 备份命名 | `backups/db/localcraft-<YYYYmmdd-HHMMSS>.db[.gz][.meta]`、`backups/files/files-<时间戳>/` |

运维命令默认以 root 执行；需要服务身份时用 `sudo -u localcraft bash -c '...'`
（`localcraft` 的 shell 是 `/sbin/nologin`，交互登录会提示 `This account is currently not available`，属正常）。

> **开工前必读**：`deploy/` 下有 9 个文件 —— `localcraft.service`、`localcraft.slice`、
> `localcraft.env.example`、`nginx-localcraft.conf`、`logrotate-localcraft`，
> 以及 `localcraft-backup.service`、`localcraft-backup.timer`、
> `localcraft-maintenance.service`、`localcraft-maintenance.timer`。
> `install.sh` 第 9 步会把**存在**的单元装到 `/etc/systemd/system/`，但
> **只 `enable` 主服务**，备份与清理的 timer 需要你自己启用（见 §2.6）。
> 这一点很重要：**不启用 timer，自动备份与清理都不会跑。**

## 1. 日常巡检清单

建议每天一次（业务开始前），全部只读。

| 检查项 | 命令 | 正常判据 | 异常怎么办 |
| --- | --- | --- | --- |
| 服务状态 | `systemctl is-active localcraft.service` | `active` | 见 §6.1 |
| 失败原因与重启 | `systemctl show localcraft.service -p Result -p ActiveState -p SubState -p NRestarts` | `Result=success`、`active/running`；1 小时内重启 < 3 次 | 见 §6.1；重启 > 3 次/小时按告警处理 |
| 存活探针 | `curl -fsS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8000/healthz` | `200` | 非 200 → §6.1 |
| 就绪探针 | `curl -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8000/readyz` | `200` | `503` → `curl -sS http://127.0.0.1:8000/readyz` 看 `checks`，见 §6.7 |
| 经 nginx 的链路 | `curl -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1/healthz` | `200` | 直连正常而此处异常 → §6.4 |
| 数据分区 | `df -h /var/lib/localcraft` | < 70%；≥ 80% 需处置 | §6.8 |
| 备份分区 | `df -h /var/lib/localcraft/backups` | < 85% | 清理旧备份或扩容 |
| inode | `df -i /var/lib/localcraft` | < 80% | 小文件堆积，见 §6.8 |
| WAL 大小 | `ls -l /var/lib/localcraft/localcraft.db-wal` | < 1 GB | 持续 > 1 GB → §6.9 |
| 数据库大小 | `ls -lh /var/lib/localcraft/localcraft.db` | 日增 < 1 GB | 查异常写入或未清理数据 |
| 备份新鲜度 | `ls -lt /var/lib/localcraft/backups/db/ \| head -n 3`，看对应 `.meta` 的 `timestamp=` | 最近一份 < 48 小时 | 超 48 小时按告警，见 §2.6 |
| 备份可用性 | `/opt/localcraft/scripts/verify-backup.sh` | 退出码 `0`，末行「验证通过」 | §6.10 |
| 今日错误量 | `journalctl -u localcraft.service --since today -p err --no-pager \| wc -l` | 与基线同数量级 | `journalctl -u localcraft.service --since today -p err \| tail -n 50` |
| `database is locked` | `journalctl -u localcraft.service --since today \| grep -ci 'database is locked'` | 单日 < 10 次 | §6.2 |
| 解压/穿越拦截 | `journalctl -u localcraft.service --since today \| grep -ciE 'zip bomb\|path traversal'` | 0 | 出现即复核上传来源 |
| 登录失败 | `journalctl -u localcraft.service --since today \| grep -ci 'login_failed'` | 单 IP 15 分钟 < 10 次 | 查 nginx 访问日志定位来源 IP |

## 2. 备份与恢复

### 2.1 备份：`scripts/backup.sh`

**做什么**：① SQLite 在线备份 API 生成自包含快照，并做 `PRAGMA integrity_check` 门禁；
② `rsync --link-dest` 硬链接增量同步 `files/`；③ 按保留份数清理旧备份；④ 可选 gzip / 远程同步。

```bash
# 手工执行一次（推荐以服务身份运行，产物属主才是 localcraft:localcraft）
sudo -u localcraft /opt/localcraft/scripts/backup.sh
```

**参数**：没有位置参数也没有选项（脚本无参数解析分支）；一切通过环境变量控制。

> **变量命名优先级（重要）**：下表前三行是**应用配置**，脚本按
> `应用名 → LOCALCRAFT_ 前缀旧名 → 默认值` 的顺序解析。
> 也就是说 `localcraft.env` 里的 `DATA_DIR` / `DATABASE_URL`（应用真正读的名字）
> 会被脚本采纳，`LOCALCRAFT_DATA_DIR` / `LOCALCRAFT_DB` 只是历史兼容别名。
> 这在一版之前是反的 —— 脚本只认前缀名，于是运维改了 `DATA_DIR` 之后
> `backup.sh` 会静默回落到 `/var/lib/localcraft`：备份跑成功、退出码 0、
> 日志正常，备的却是错的目录（docs/09 §12）。

| 环境变量 | 默认值 | 含义 |
| --- | --- | --- |
| `DATA_DIR`（旧名 `LOCALCRAFT_DATA_DIR`） | `/var/lib/localcraft` | 数据根目录 |
| `DATABASE_URL` → DB 路径（旧名 `LOCALCRAFT_DB`） | `$DATA_DIR/localcraft.db` | 数据库文件。SQLite 连接串里 `sqlite+aiosqlite:///` 之后的路径即备份对象 |
| `LOCALCRAFT_FILES_DIR` | `$DATA_DIR/files` | 文件存储目录（脚本自己的开关，应用不读） |
| `LOCALCRAFT_BACKUP_DIR` | `$DATA_DIR/backups` | 备份根目录 |
| `LOCALCRAFT_BACKUP_KEEP_DB` | `14` | 数据库快照保留份数 |
| `LOCALCRAFT_BACKUP_KEEP_FILES` | `7` | 文件快照保留份数（0 = 不清理） |
| `LOCALCRAFT_BACKUP_GZIP` | `false` | `true` 时压缩为 `.db.gz` |
| `LOCALCRAFT_BACKUP_MIN_FREE_MB` | `2048` | 备份前要求的最小剩余空间（MB） |
| `LOCALCRAFT_BACKUP_VACUUM` | `auto` | `true`/`false`/`auto`；`auto` = 周日或每月 1 日走 `VACUUM INTO` |
| `LOCALCRAFT_BACKUP_REMOTE` | 空 | 非空则 `rsync -a` 备份根目录到该目标（失败仅告警） |
| `LOCALCRAFT_PREFIX` | `/opt/localcraft` | 仅用于把版本号写进 `.meta` |

**产物位置与命名**：

```text
/var/lib/localcraft/backups/
├── db/localcraft-20260925-030000.db         # GZIP=false（默认）
├── db/localcraft-20260925-030000.db.meta    # 元信息（同名 + .meta）
├── db/localcraft-20260924-030000.db.gz      # GZIP=true 时，元信息为 .db.gz.meta
└── files/files-20260925-030000/           # 硬链接增量快照目录
    └── latest -> files-20260925-030000    # 指向最近一份，供 --link-dest 使用
```

**`.meta` 字段**（恢复前先看它）：

| 字段 | 含义 |
| --- | --- |
| `timestamp` | 备份时间戳，与文件名中的时间戳一致 |
| `source_db` | 备份时读取的数据库路径 |
| `mode` | `online-backup`（`.backup`）或 `vacuum-into`（整理型备份） |
| `integrity_check` | 固定 `ok`；不通过时脚本已失败，不会留下产物 |
| `journal_mode` | 快照内的 journal 模式（正常为 `wal`） |
| `wal_bytes_at_backup` | 备份时 `-wal` 的字节数（证明 WAL 已折进快照） |
| `users_rows` / `tools_rows` / `tool_versions_rows` | 快照内三张关键表行数，恢复后比对用 |
| `compressed` | 是否 gzip，与文件后缀对应 |
| `host` / `localcraft_version` / `alembic_revision` | 生成备份的主机名、应用版本、迁移版本 |

**退出码**：`0` = 数据库快照成功且 `files/` 同步成功（或 `files/` 不存在被跳过）；
`1` = 任一 `die`（缺 `sqlite3`/`rsync`、库文件不存在、拿不到锁、空间不足、`.backup`/`VACUUM` 失败、完整性校验失败）
**或** `files/` 同步失败（此时数据库快照仍有效）。并发时脚本站 `flock`（无 `flock` 退化为 `mkdir` 原子锁），拿不到锁即以 1 跳过本次，属预期行为。

### 2.2 WAL 的三个关键点

1. **为什么不能 `cp` 数据库**：库在 WAL 模式下，已提交数据可能还在 `localcraft.db-wal` 里未 checkpoint 回主库；
   `cp` 会**丢最近事务**，且复制期间库仍在写，得到的是竞态文件，可能页级损坏。
2. **为什么备份用 `.backup`**：`.backup` 走 SQLite Online Backup API，**自动把 WAL 中未 checkpoint 的内容折进快照**，
   产物自包含 —— 所以备份时**不需要也不应该**单独复制 `-wal`/`-shm`。周日/每月 1 日的 `VACUUM INTO` 同理自包含，顺带整理碎片。
3. **为什么恢复前必须清 `-wal`/`-shm`**：残留 WAL 属于**旧库**，SQLite 打开新库文件时会把它当新库的 WAL 重放 ——
   轻则读到旧数据，重则 `database disk image is malformed`。`restore.sh` 已显式 `rm -f`；**手工恢复也必须做这一步**。

### 2.3 备份可用性验证：`scripts/verify-backup.sh`

回答一个具体问题：**最近那份备份现在真的能恢复吗？** 它不触碰生产数据（在临时目录里解压后校验）。

```bash
/opt/localcraft/scripts/verify-backup.sh
/opt/localcraft/scripts/verify-backup.sh --dir /var/lib/localcraft/backups --expect-tools 500
```

| 参数 / 环境变量 | 含义 |
| --- | --- |
| `--dir <目录>` | 备份根目录（默认 `$LOCALCRAFT_BACKUP_DIR`，再默认 `$DATA_DIR/backups`） |
| `--expect-tools N` | 断言快照内 `tools` 行数为 N，不符即 FAIL |
| `--expect-files N` | 预留参数，当前版本解析后未参与判定 |
| `LOCALCRAFT_VERIFY_SAMPLE` | 文件抽检样本数，默认 `5` |

**检查内容**：备份存在性；`.meta` 存在且 `integrity_check=ok`（新鲜度 > 48 小时仅 WARN）；
真实解压 + `PRAGMA integrity_check`；`users`/`tools`/`tool_versions` 可读；`PRAGMA foreign_key_check` 无违规；
随机抽检 `tool_versions.storage_path` 对应文件是否在文件快照内；保留份数与备份分区剩余空间（< 1024 MB 记 FAIL）。
**退出码**：`0` = 全部通过（WARN 不影响）；`1` = 存在任一 FAIL；`2` = 未知参数或缺 `sqlite3`。
建议每周一次，并在每次恢复演练前执行。

### 2.4 恢复：`scripts/restore.sh`

**做什么**：二次确认 → 临时目录解压并校验备份（`integrity_check` + 行数）→ 停服务 →
把**当前**数据库复制、当前 `files/` **移动**到 `pre-restore-<时间戳>` 回退点 → 还原数据库 →
**清理 `-wal`/`-shm`** → 还原 `files/` → 恢复后 `integrity_check` + 行数比对 →（默认）启动服务 → 打印回退点。

> ⚠️ **危险操作**：本命令会**覆盖当前数据**。执行前必须：① 有一份 `verify-backup.sh` 通过的新备份；
> ② 核对目标备份 `.meta` 的时间戳与行数确实是你要回到的点；③ 在维护窗口内执行并提前通知用户。

```bash
# 用法 1：显式指定数据库与文件备份（生产首选）
/opt/localcraft/scripts/restore.sh \
    --db /var/lib/localcraft/backups/db/localcraft-20260925-030000.db \
    --files /var/lib/localcraft/backups/files/files-20260925-030000
# 用法 2：取最近一份（数据库与文件各自取最新）
/opt/localcraft/scripts/restore.sh --latest
# 用法 3：跳过交互确认（供演练脚本/无人值守）
/opt/localcraft/scripts/restore.sh --db /var/lib/localcraft/backups/db/localcraft-20260925-030000.db --yes
```

| 参数 | 含义 |
| --- | --- |
| `--db <路径>` | 数据库备份路径，支持 `.db` 与 `.db.gz`（自动解压） |
| `--files <目录>` | `files-<时间戳>` 快照目录；省略则**不还原文件**（有 WARN） |
| `--latest` | 从 `$LOCALCRAFT_BACKUP_DIR` 的 `db/`、`files/` 各取文件名排序最后一份 |
| `--yes`/`-y` | 跳过交互确认（交互要求逐字输入 `restore`，输错即取消） |
| `--no-start` | 恢复完成后**不启动** `localcraft.service` |
| `-h`/`--help` | 打印脚本头部用法 |

环境变量：`DATA_DIR`、`DATABASE_URL`、`LOCALCRAFT_FILES_DIR`、`LOCALCRAFT_BACKUP_DIR`（前三者的命名优先级见 §2.1）。
**`--no-start` 的用途**：① 演练时先不对外服务，人工校验完再起；② 恢复后还要接着做别的维护动作
（替换 env、回退依赖）；③ 先用 `sqlite3` 核对行数/内容再放量。
**回退点**：脚本输出 `回退点 : <BACKUP_ROOT>/pre-restore-<YYYYmmdd-HHMMSS>`，内含恢复前的 `localcraft.db`
与 `files/`。恢复错了就停服务后用这里的库和目录再走一次恢复（`--files` 直接指向该目录即可）。
**退出码**：`0` = 流程走完；`1` = 任一 `die`。脚本是 `set -uo pipefail`（无 `-e`），**必须逐行读输出**，别只看退出码。

### 2.5 季度恢复演练（标准步骤）

原则：**绝不在生产数据目录里"试一试"**：独立数据目录 + `--no-start`，全程只读生产备份。

```bash
# 0) 测试机上装一套相同版本，把生产备份拷过来
export DRILL=/var/lib/localcraft-drill
mkdir -p "$DRILL/backups/db" "$DRILL/backups/files"
rsync -a /var/lib/localcraft/backups/db/    "$DRILL/backups/db/"
rsync -a /var/lib/localcraft/backups/files/ "$DRILL/backups/files/"

# 1) 把脚本指向演练目录。
#    DATA_DIR / DATABASE_URL 是与应用同一套名字，脚本优先读它们；
#    LOCALCRAFT_ 前缀名只是历史兼容别名（docs/09 勘误 #28）。
export DATA_DIR="$DRILL"
export DATABASE_URL="sqlite+aiosqlite:///$DRILL/localcraft.db"
export LOCALCRAFT_FILES_DIR="$DRILL/files"
export LOCALCRAFT_BACKUP_DIR="$DRILL/backups"

# 2) 先验证备份本身可用（期望末行「验证通过」，退出码 0）
/opt/localcraft/scripts/verify-backup.sh --dir "$LOCALCRAFT_BACKUP_DIR"

# 3) 恢复（不启动服务）
/opt/localcraft/scripts/restore.sh --latest --no-start --yes

# 4) 恢复后校验：integrity / 外键 / journal_mode / 行数 / 无 -wal、-shm 残留
DB_FILE="$DRILL/localcraft.db"
sqlite3 "$DB_FILE" 'PRAGMA integrity_check;'
sqlite3 "$DB_FILE" 'PRAGMA foreign_key_check;'
sqlite3 "$DB_FILE" 'PRAGMA journal_mode;'
sqlite3 "$DB_FILE" "SELECT 'users', COUNT(*) FROM users UNION ALL SELECT 'tools', COUNT(*) FROM tools UNION ALL SELECT 'versions', COUNT(*) FROM tool_versions;"
ls -l "$DB_FILE"*

# 5) 与生产对账（行数 + 文件数/体积）
sqlite3 /var/lib/localcraft/localcraft.db 'SELECT COUNT(*) FROM tools;'
sqlite3 "$DB_FILE" 'SELECT COUNT(*) FROM tools;'
du -sh /var/lib/localcraft/files "$LOCALCRAFT_FILES_DIR"
find /var/lib/localcraft/files -type f | wc -l; find "$LOCALCRAFT_FILES_DIR" -type f | wc -l

# 6) 用演练数据临时起服务做端到端验证（换端口，不碰生产）
#    注意：第 240 行 source 了生产的 localcraft.env，其中 DATA_DIR/DATABASE_URL
#    指向生产 —— 必须显式覆盖成演练目录，两个变量都要改（只改 DATA_DIR
#    会在 DATABASE_URL 显式给出时失效）。
set -a; . /etc/localcraft/localcraft.env; set +a
cd /opt/localcraft/app/current
DATA_DIR="$DRILL" \
DATABASE_URL="sqlite+aiosqlite:///$DRILL/localcraft.db" \
  /opt/localcraft/venv/bin/python -m uvicorn app.main:app --host 127.0.0.1 --port 8801 &
sleep 3; curl -sS http://127.0.0.1:8801/readyz; echo; kill %1

# 7) 把结论落到书面：时间、备份文件、行数、文件数、耗时、发现的问题
```

> 只写「演练通过」没有价值，要写下实际行数、文件数、耗时，以及任何与生产不一致的项。

### 2.6 备份定时器：现状与启用办法

**现状（已核实）**：`deploy/systemd/` 内已有 `localcraft-backup.service` 与 `localcraft-backup.timer`，
发布包解压后位于 `<release>/deploy/systemd/`；`install.sh` 会把它们装到 `/etc/systemd/system/`，
**但不会 `enable`**。

- **启用（推荐）**：

```bash
systemctl daemon-reload
systemctl enable --now localcraft-backup.timer       # 每日 03:00 备份
systemctl enable --now localcraft-maintenance.timer  # 每小时清理（docs/02 §5）
```

- **办法 B（临时兜底，无 systemd 时）**：用 cron 保证每天有一份备份。

```bash
cat > /etc/cron.d/localcraft-backup <<'EOF'
# localcraft 每日备份（03:00），以服务身份运行；输出进 journal
0 3 * * * localcraft /opt/localcraft/scripts/backup.sh 2>&1 | logger -t localcraft-backup
EOF
chmod 0644 /etc/cron.d/localcraft-backup
```

启用后必须验一次：

```bash
systemctl list-timers 'localcraft*' --no-pager      # 办法 A：确认下次触发时间
sudo -u localcraft /opt/localcraft/scripts/backup.sh  # 手工跑一次
ls -lt /var/lib/localcraft/backups/db/ | head
/opt/localcraft/scripts/verify-backup.sh            # 确认这份可用
```

### 2.7 `SECRET_KEY` 的处置（它不在数据库里）

`SECRET_KEY` 只存在于 `/etc/localcraft/localcraft.env`（`0640 root:localcraft`），由 `install.sh` 用
`openssl rand -hex 32` 生成；**不写数据库、不进数据库快照**。因此：

- **恢复数据库不会恢复 `SECRET_KEY`**。若目标机密钥与备份来源不同，恢复后**旧 access/refresh JWT 全部失效**，
  所有用户被强制重新登录（密码哈希不受影响；API Token 存的是哈希，也不受影响）。
- **升级/迁移机器时必须一并保留 env 文件**，否则等同于「全员登出 + 下载签名链接失效」。
- **env 文件备份要单独加密归档**，不要和数据库备份放在同一个明文目录。

```bash
# 升级/迁移前保存（注意权限，里面是密钥）
install -m 0600 /etc/localcraft/localcraft.env "/root/localcraft.env.bak-$(date +%Y%m%d)"
# 换机时恢复并确认权限
install -m 0640 -o root -g localcraft /root/localcraft.env.bak-YYYYMMDD /etc/localcraft/localcraft.env
systemctl restart localcraft.service
```

轮换（会让所有已签发 token 失效，属预期，需提前通知）：

```bash
cp /etc/localcraft/localcraft.env "/root/localcraft.env.bak-$(date +%Y%m%d)"
sed -i "s|^SECRET_KEY=.*|SECRET_KEY=$(openssl rand -hex 32)|" /etc/localcraft/localcraft.env
systemctl restart localcraft.service
/opt/localcraft/scripts/wait-healthy.sh --url http://127.0.0.1:8000/readyz --timeout 60
```

### 3.3 `install.sh` 做什么

在**解压后的发布包根目录**以 root 执行，幂等、可重复执行：

```bash
tar -C /opt/localcraft/releases -xzf localcraft-1.1.0-offline-20260101.tar.gz
cd /opt/localcraft/releases/localcraft-1.1.0
./install.sh
```

十个步骤：① `scripts/precheck.sh` 环境自检（FAIL 只告警不终止）；② 校验 `SHA256SUMS`，按 `uname -m`
选 `wheelhouse-x86_64`/`wheelhouse-aarch64` 并校验 `MANIFEST.sha256`；③ 建 `localcraft` 系统用户与
`/var/lib/localcraft`、`/etc/localcraft`、`/var/log/localcraft` 及子目录，同步 `scripts/` 到 `/opt/localcraft/scripts/`；
④ 建立软链 `/opt/localcraft/app/current -> 发布包目录`（升级/回滚靠切换它）；⑤ 用 `python3.11` 建 venv 并升级 pip 工具链；
⑥ 从 wheelhouse 离线安装 `requirements/requirements.lock.txt`；⑦ 生成 `/etc/localcraft/localcraft.env`
（**已存在则保留**，绝不覆盖 `SECRET_KEY`）；⑧ `alembic upgrade head`（**必须在服务启动之前**）；
⑨ 安装存在的 systemd 单元 + logrotate，`daemon-reload`、`enable`、`restart`；
⑩ 用 `scripts/wait-healthy.sh` 等 `/readyz`（90 秒）。

装完还需人工做三件事（脚本结尾会打印）：

```bash
# 1) 创建超级管理员（密码交互输入，不要用明文参数）
sudo -u localcraft bash -c '
  set -a; . /etc/localcraft/localcraft.env; set +a
  cd /opt/localcraft/app/current
  /opt/localcraft/venv/bin/python -m app.cli create-superadmin --username admin --email admin@intra.example.com
'
# 2) 安装 nginx 配置（HTTP 快速验证版）
install -m 0644 /opt/localcraft/releases/localcraft-1.1.0/deploy/nginx/localcraft-http.conf /etc/nginx/conf.d/localcraft.conf
nginx -t && systemctl reload nginx
# 3) 验证
curl -sS http://127.0.0.1:8000/healthz; echo
curl -sS http://127.0.0.1:8000/readyz; echo
curl -sS -o /dev/null -w '经 nginx /healthz HTTP %{http_code}\n' http://127.0.0.1/healthz
```

支持的环境变量（演练/沙箱用）：`LOCALCRAFT_SKIP_SYSTEMD=1`（跳过 `useradd`/`chown`/`systemctl`，改用 `nohup`
拉起同一个 uvicorn 命令）、`LOCALCRAFT_PREFIX`、`LOCALCRAFT_DATA_DIR`（安装期开关，优先于 `DATA_DIR`）、`LOCALCRAFT_ETC_DIR`、`LOCALCRAFT_LOG_DIR`、
`LOCALCRAFT_WHEELHOUSE`、`LOCALCRAFT_PYTHON311`。

### 3.4 升级步骤

> ⚠️ 升级前**必须先备份**（数据库 + `files/` + env）。没有备份的升级不算升级，算赌博。

```bash
# 0) 变量
export OLD_VERSION="$(cat /opt/localcraft/app/current/VERSION)"
export NEW_VERSION=1.1.0
export NEW_DIR="/opt/localcraft/releases/localcraft-${NEW_VERSION}"

# 1) 停服务 + 备份（记下这次保护点的路径）
systemctl stop localcraft.service
sudo -u localcraft /opt/localcraft/scripts/backup.sh
BACKUP_DB="$(ls -1t /var/lib/localcraft/backups/db/localcraft-*.db* | grep -v '\.meta$' | head -n1)"
BACKUP_FILES="$(ls -1dt /var/lib/localcraft/backups/files/files-* | head -n1)"
echo "保护点: $BACKUP_DB  $BACKUP_FILES"

# 2) 解压并校验发布包与 wheelhouse
tar -C /opt/localcraft/releases -xzf /root/localcraft-${NEW_VERSION}-offline-*.tar.gz
( cd "$NEW_DIR" && sha256sum -c SHA256SUMS --quiet ) && echo "发布包校验通过"
case "$(uname -m)" in
    x86_64)  WH="$NEW_DIR/wheelhouse-x86_64" ;;
    aarch64) WH="$NEW_DIR/wheelhouse-aarch64" ;;
esac
( cd "$WH" && sha256sum -c MANIFEST.sha256 --quiet ) && echo "wheelhouse 校验通过"

# 3) 原子切换软链 + 同步脚本
ln -sfn "$NEW_DIR" /opt/localcraft/app/current.new && mv -Tf /opt/localcraft/app/current.new /opt/localcraft/app/current
readlink -f /opt/localcraft/app/current
cp -a "$NEW_DIR/scripts/." /opt/localcraft/scripts/ && chmod +x /opt/localcraft/scripts/*.sh

# 4) 对齐 venv 依赖（离线）
/opt/localcraft/venv/bin/python -m pip install --quiet --no-index --find-links="$WH" --upgrade pip setuptools wheel
/opt/localcraft/venv/bin/python -m pip install --no-index --find-links="$WH" --upgrade --requirement "$NEW_DIR/requirements/requirements.lock.txt"
/opt/localcraft/venv/bin/python -m pip check || echo "警告：pip check 报告依赖冲突，请人工确认"

# 5) 数据库迁移（服务停止状态下执行）
( set -a; . /etc/localcraft/localcraft.env; set +a; cd /opt/localcraft/app/current
  /opt/localcraft/venv/bin/alembic current
  /opt/localcraft/venv/bin/alembic history -r current:head
  /opt/localcraft/venv/bin/alembic upgrade head
  /opt/localcraft/venv/bin/alembic current )

# 6) 起服务并验证
systemctl start localcraft.service
/opt/localcraft/scripts/wait-healthy.sh --url http://127.0.0.1:8000/readyz --timeout 90
curl -sS http://127.0.0.1:8000/api/v1/meta; echo
journalctl -u localcraft.service --since "10 min ago" -p warning --no-pager | tail -n 50   # 观察 10 分钟

# 7) 确认无误后清理过老版本（保留最近 3 个）
ls -1dt /opt/localcraft/releases/localcraft-* | tail -n +4
# ls -1dt /opt/localcraft/releases/localcraft-* | tail -n +4 | xargs -r rm -rf
```

> 也可用 `cd "$NEW_DIR" && ./install.sh` 代替第 2~6 步（幂等，会校验→切软链→装依赖→迁移→重启→等就绪，
> 且保留已存在的 env 文件），但第 1 步的备份不能省。

### 3.5 回滚步骤

分三种情况（docs/05 §11.4）：A 未迁移数据库 / B 增量迁移 / C 破坏性迁移。**共同前两步永远是「停服务 + 切回旧软链」。**

```bash
export OLD_DIR=/opt/localcraft/releases/localcraft-<旧版本>

# 1) 停服务 + 切回旧代码（原子切换）
systemctl stop localcraft.service
ln -sfn "$OLD_DIR" /opt/localcraft/app/current.new && mv -Tf /opt/localcraft/app/current.new /opt/localcraft/app/current
readlink -f /opt/localcraft/app/current

# 2) 回退依赖（用旧版本的 lock 对齐）+ 同步旧版脚本
OLD_WH="$OLD_DIR/wheelhouse-$(uname -m)"
/opt/localcraft/venv/bin/python -m pip install --no-index --find-links="$OLD_WH" --upgrade --requirement "$OLD_DIR/requirements/requirements.lock.txt"
/opt/localcraft/venv/bin/python -m pip check
cp -a "$OLD_DIR/scripts/." /opt/localcraft/scripts/ && chmod +x /opt/localcraft/scripts/*.sh

# 3) 判断是否需要还原数据库
( set -a; . /etc/localcraft/localcraft.env; set +a; cd /opt/localcraft/app/current; /opt/localcraft/venv/bin/alembic current )
grep -nE 'drop_|alter_column|op\.drop|nullable=False' "$OLD_DIR/migrations/versions/"*.py
# 情况 A/B（无迁移或纯增量）：只回滚代码，跳到第 5 步
# 情况 C（有删表/删列/收紧约束/数据重写）：必须做第 4 步

# 4) 情况 C：还原升级前的数据库与文件（会丢弃升级后产生的数据！）
/opt/localcraft/scripts/restore.sh --db "$BACKUP_DB" --files "$BACKUP_FILES" --yes
# 若升级时改过 env 文件，一并还原：
# install -m 0640 -o root -g localcraft /root/localcraft.env.bak-<日期> /etc/localcraft/localcraft.env

# 5) 起服务并验证
systemctl start localcraft.service
/opt/localcraft/scripts/wait-healthy.sh --url http://127.0.0.1:8000/readyz --timeout 90
```

> ⚠️ **不要把 `alembic downgrade` 当主要回滚手段**（理由见 docs/05 §11.4：`downgrade()` 常缺测试、
> 可能丢数据、SQLite 上伴随 batch 建表残留）。第一选择永远是「切软链 + 还原备份」；
> 只有迁移纯增量且备份丢失时才考虑 `downgrade`，且必须停服务、先备份、逐级 `-1` 执行。

## 4. 双架构发布注意事项

### 4.1 构建：`scripts/build-wheelhouse.sh`

```bash
scripts/build-wheelhouse.sh              # 两套都建
scripts/build-wheelhouse.sh aarch64      # 只建 aarch64
scripts/build-wheelhouse.sh all --force  # 强制重建（目录已存在且非空时默认跳过）
```

| 参数 / 环境变量 | 含义 |
| --- | --- |
| `x86_64` / `aarch64` / `all`（默认 `all`） | 目标架构 |
| `--force` | 目标目录已存在且非空时也重建 |
| `PYTHON_BIN` | 用于下载 wheel 的 Python，默认 `backend/.venv/bin/python`，回退 `python3.11` |

**产物**：`backend/wheelhouse-x86_64/`、`backend/wheelhouse-aarch64/`，各含 `MANIFEST.sha256`（相对路径清单）。
**内置门禁**：① `--only-binary=:all:` 保证**零 sdist**（缺 wheel 直接失败，不会悄悄下源码包）；
② 逐 `--platform` 穷举目标机能接受的 manylinux 标签，**刻意不列 `musllinux_*`**（openEuler 是 glibc）；
③ 自动补下 `pip`/`setuptools`/`wheel` 三个 bootstrap 包（`venv` 不自带 `wheel`）。

### 4.2 校验：`scripts/verify-wheelhouse.sh`

```bash
scripts/verify-wheelhouse.sh                                  # 两套都查
scripts/verify-wheelhouse.sh x86_64                           # 只查一套
scripts/verify-wheelhouse.sh x86_64 backend/wheelhouse-x86_64 # 指定目录
```

检查项：目录存在且非空；**零 sdist**；每个 wheel 文件名至少 5 段；非纯 Python wheel 必须带**目标架构**标签
且不得混入其他架构标签；不得出现 `musllinux_*`；`manylinux_2_X` 的 glibc 下限不得高于 `MAX_GLIBC_MINOR`
（默认 `38`，对应 openEuler 24.03）；`MANIFEST.sha256` 覆盖全部 wheel 且校验通过。
**退出码**：`0` = 全部通过；`1` = 存在任一 FAIL。

### 4.3 `manylinux` 标签不向上兼容

`--platform` 决定 pip **愿意接受哪些 wheel 文件名**。目标机能跑 `manylinux_2_28` 的包，但如果构建时只声明
`manylinux2014`（= `manylinux_2_17`），pip 就**看不到**只发布为 `manylinux_2_28` 的包，下载直接失败。
所以脚本从高到低把标签全列上（2_38 → … → manylinux1 → `linux_<arch>`），由 pip 自己挑。

### 4.4 「标签检查通过 ≠ 目标架构验证通过」

`verify-wheelhouse.sh` 做的是**文件级/文件名级**检查，等价于「标签对得上」。它**不做**：二进制能否在本机加载、
aarch64 的 wheel 在真实 aarch64 机器上能否装能跑。**必须在目标架构上真跑一遍离线安装**才算验证通过：

```bash
# 在 aarch64 机器（或 qemu 用户态模拟）上
uname -m                       # 期望 aarch64
cd /opt/localcraft/releases/localcraft-<版本>
( cd wheelhouse-aarch64 && sha256sum -c MANIFEST.sha256 --quiet ) && echo "清单校验通过"

# 真离线安装（这一步才证明「能装」）
/opt/localcraft/venv/bin/python -m pip install --no-index \
    --find-links=wheelhouse-aarch64 --requirement requirements/requirements.lock.txt
/opt/localcraft/venv/bin/python -m pip check

# 证明原生扩展能被加载（ELF 真能跑，不是只有文件名对）
/opt/localcraft/venv/bin/python -c "import greenlet, pydantic_core, argon2, httptools, PIL; print('native deps ok')"

# 走完整安装链路 + 探针
./install.sh
curl -sS http://127.0.0.1:8000/readyz; echo
```

常见额外动作：pip 报 `No matching distribution found for <包>` 或 `<包>.tar.gz is not a supported wheel on this platform`
说明该包在 aarch64 缺 wheel —— 先确认没把 x86_64 的 wheelhouse 拷到 aarch64 机器
（`ls /opt/localcraft/releases/localcraft-*/wheelhouse-aarch64/ | grep -E 'greenlet|pydantic_core'` 应看到 `..._aarch64.whl`），
再按 docs/05 §3.4.5 差分补齐或调整版本后重新构建。
注意：本仓库 M4 演练脚本 `scripts/m4-drill-install.sh` **明确声明**本机无 aarch64 环境，
「aarch64 的安装验证」**未做** —— aarch64 上线前必须补做上面 3~5 步。

辅助命令：

```bash
scripts/wheelhouse-arch-diff.sh      # 差异清单 → backend/dist/wheelhouse-arch-diff.txt
```

重点看「只出现在一边的包」：那意味着另一架构离线安装时会缺包。

### 5A.1 测量环境（先看局限，再看数字）

### 5A.2 并发阶梯（门户列表）

| 并发 | P50 (ms) | P95 (ms) | req/s |
| --- | --- | --- | --- |
| 1 | 8 | 29 | 111 |

### 5A.3 瓶颈定位（为什么是这里）

同一台机器上做的对照实验（`c=20`）说明了成本在哪里：

| 请求 | P95 (ms) | req/s | 说明 |
| --- | --- | --- | --- |
| `/healthz` | 15 | 3114 | 纯框架开销 —— 框架本身不是瓶颈 |
| 列表 `page_size=1` | 116 | 211 | |
| 列表 `page_size=12` | 305 | 93 | |
| 列表 `page_size=24` | 475 | 56 | 默认页大小 |
| 列表 `page_size=48` | 805 | 34 | |
| 列表 `page_size=24&page=2` | 383 | 69 | 第 2 页不算 facets |

两条结论：

1. **成本随「条目数」近似线性增长**（page_size 1→48 时 P95 从 116ms 涨到 805ms）。
   瓶颈是**每个条目的 CPU 开销**：ORM 实例化 → Pydantic 校验 → JSON 编码，
   全部在**单个 Python 进程**里，受 GIL 限制。
2. **facets 只占约 20%**（`page=1` 56 req/s vs `page=2` 69 req/s）。
   因此 M5 做的「合并两条聚合为一条 + 30 秒短时缓存」降低了数据库负载，
   但**没有**显著改善高并发下的 P95 —— 因为那时进程已经 CPU 饱和。
   （这一点在 M5 报告里如实写明，未粉饰。）

**`database is locked` 在全部压测中出现 0 次**（读压测 + 写加压至并发 40），
说明**瓶颈不是 SQLite 的写锁**。

### 5A.4 为什么默认单 worker

`deploy/localcraft.service` 明确使用 `--workers 1`（`docs/05` §6.3）：

- SQLite 是**单写者**。多 worker 只是多个进程抢同一把写锁，
  写密集时冲突概率上升、`busy_timeout` 重试增多，**整体更慢**；
- 多 worker 也意味着每个进程各自持有一份内存计数队列，
  落库时的合并与顺序更复杂（`counter_service`）。

### 5A.5 扩展触发条件（什么时候必须动）

出现下列任一情况，**不要再调参**，按下面的路径扩容：

| 触发条件 | 处置 |
| --- | --- |
| 持续在途并发 **> 20** | 迁移到 **PostgreSQL**（§7），然后把 worker 数提到 `CPU 核数` 级 |
| 写事务 **> 50/s** 持续 5 分钟 | 同上（SQLite 单写者会成为硬上限） |
| `database is locked` 在 journal 中**每小时出现 > 0 次** | 先按 §6 的锁排查；若并发确实高，直接迁 PG |
| WAL 文件持续 > 1 GB | 低峰触发 checkpoint；仍增长则说明写压力已超 SQLite 承载 |
| 门户 P95 持续 > 300ms 且并发 < 20 | 先查是否有慢查询/大事务；这属于**异常**而非容量问题 |

> 迁到 PostgreSQL 之后才谈得上多 worker：届时瓶颈从「单进程 GIL」变成
> 「进程数 × 核数」，才真正吃得到多核。

## 6. 故障排查索引

### 6.1 服务起不来

```bash
systemctl status localcraft.service --no-pager -l
systemctl show localcraft.service -p Result -p ExecMainStatus -p NRestarts -p ActiveState -p SubState
journalctl -u localcraft.service -n 200 --no-pager
systemd-analyze verify /etc/systemd/system/localcraft.service
```

| 现象 | 根因 | 处置 |
| --- | --- | --- |
| `status=200/CHDIR` | `WorkingDirectory` 不存在（软链指向的目录被删） | 修正软链或 unit |
| `status=203/EXEC` | `ExecStart` 的二进制不存在/无执行权限 | 检查 `/opt/localcraft/venv/bin/python` |
| `status=226/NAMESPACE` | 安全加固与路径冲突（`ProtectSystem=strict` 缺 `ReadWritePaths`） | 补齐 `ReadWritePaths` |
| `ModuleNotFoundError: No module named 'app'` | `PYTHONPATH`/软链问题 | 确认 `Environment=PYTHONPATH=/opt/localcraft/app/current` |
| `Address already in use` | 8000 被占用 | `ss -lntp \| grep 8000`；必要时 `pkill -f 'uvicorn app.main:app'` |
| `unable to open database file` | 路径/权限问题 | 见 §6.5；确认 `DATABASE_URL` 是**四个斜杠** |
| `Referenced but unset environment variable` | env 文件缺 `LOCALCRAFT_HOST`/`LOCALCRAFT_PORT`/`LOCALCRAFT_LOG_LEVEL` | 这三项必须保留（systemd 会在 `ExecStart` 里展开） |
| env 文件里有 `export` 或 `$(...)` | systemd 的 `EnvironmentFile` 不支持 shell 语法 | 删掉 shell 语法，含空格的值写 `KEY="a b"` |
| 反复重启后 `failed` | 触发 `StartLimitBurst` | `systemctl reset-failed localcraft.service` 后重试 |

最有效的定位手段是绕开 systemd 手工跑：

```bash
sudo -u localcraft bash -c '
  set -a; . /etc/localcraft/localcraft.env; set +a
  cd /opt/localcraft/app/current
  /opt/localcraft/venv/bin/python -c "from app.main import app; print(\"import ok\", app.title)"
'
```

### 6.2 `database is locked`

SQLite WAL 是「多读单写」：第二个写事务等不到锁（超过 `busy_timeout`）就报 `SQLITE_BUSY`。

```bash
sqlite3 /var/lib/localcraft/localcraft.db 'PRAGMA journal_mode;'   # 期望 wal
sqlite3 /var/lib/localcraft/localcraft.db 'PRAGMA busy_timeout;'
lsof /var/lib/localcraft/localcraft.db 2>/dev/null || fuser -v /var/lib/localcraft/localcraft.db
journalctl -u localcraft.service --since today | grep -iE 'database is locked|SQLITE_BUSY' | tail -n 30
ps -ef | grep sqlite3 | grep -v grep
df -h /var/lib/localcraft
```

处置（代价从小到大）：① 确认 unit 里仍是 `--workers 1`；② 把备份/VACUUM 挪到业务低峰；
③ 低峰执行 `sqlite3 /var/lib/localcraft/localcraft.db 'PRAGMA wal_checkpoint(TRUNCATE);'`；
④ `systemctl restart localcraft.service`（会触发 checkpoint）。`busy_timeout` 由环境变量 `DB_BUSY_TIMEOUT`
（单位**毫秒**，默认 `5000`）控制，改完需重启服务。

> 绝对不要：删 `-wal`/`-shm` 来「解锁」（丢数据）；`kill -9` 应用进程；把数据库放 NFS/CIFS；
> 用多 worker 提高吞吐（只会更慢）。

### 6.3 上传返回 413

413 有两个来源，先判断是谁返回的：

```bash
curl -sS -i -F "file=@bigfile.zip" http://127.0.0.1/api/v1/files/upload | head -n 20
# nginx 返回 → 响应头有 Server: nginx、错误页是 HTML，日志在 /var/log/nginx/localcraft.error.log
# 应用返回 → JSON 体含应用错误码，日志在 journalctl -u localcraft
grep -i '413\|too large' /var/log/nginx/localcraft.error.log | tail
nginx -T 2>/dev/null | grep -n client_max_body_size     # 仓库内配置为 512m
```

| 来源 | 根因 | 处置 |
| --- | --- | --- |
| nginx | `client_max_body_size` 小于上传体积 | 保证上传路径所在 `location`/`server` 的值大于应用上限的 2~2.5 倍，`nginx -t && systemctl reload nginx` |
| 应用 | 应用侧上限是**系统设置** `upload.max_file_size_mb`（默认 200），不是环境变量 | 在管理台改该设置；同步 nginx 的 `client_max_body_size` 与磁盘规划 |
| 应用 507 | 用户配额或平台总配额耗尽 | 清理或调整配额 |
| 应用 415 | 扩展名不在白名单 | 检查允许扩展名设置 |

### 6.4 502 / 504

```bash
systemctl is-active localcraft.service
curl -sS -i http://127.0.0.1:8000/healthz | head -n 5
tail -n 50 /var/log/nginx/localcraft.error.log
grep -n 'LOCALCRAFT_HOST\|LOCALCRAFT_PORT' /etc/localcraft/localcraft.env
grep -n 'proxy_pass' /etc/nginx/conf.d/localcraft.conf
ss -lntp | grep 8000
```

| error.log 关键字 | 根因 | 处置 |
| --- | --- | --- |
| `connect() failed (111: Connection refused)` | 应用未启动或端口不一致 | 启动应用；核对 `LOCALCRAFT_HOST/PORT` 与 `proxy_pass` |
| `connect() failed (13: Permission denied)` | SELinux 禁止 nginx 出网 | `setsebool -P httpd_can_network_connect on && systemctl reload nginx` |
| `prematurely closed connection` | 应用处理中崩溃/OOM | 查 journal 尾部 traceback；`dmesg -T \| grep -i 'killed process'` |
| `upstream timed out` | 超过 `proxy_read_timeout` | 调大超时并排查慢操作（仓库内配置为 600s） |
| `no live upstreams` | upstream 被全部标记失败 | 修正应用后 `systemctl reload nginx` |
| `Too many open files` | fd 不足 | 见 docs/05 §6.5，确认 `LimitNOFILE=65536` 实际生效 |

### 6.5 权限问题

```bash
ls -ld /var/lib/localcraft /var/lib/localcraft/files /var/lib/localcraft/backups /var/log/localcraft
ls -l /var/lib/localcraft/localcraft.db*; ls -l /etc/localcraft/localcraft.env
sudo -u localcraft test -r /etc/localcraft/localcraft.env && echo "可读 env"
sudo -u localcraft test -w /var/lib/localcraft && echo "可写数据目录"
namei -l /var/lib/localcraft/files/uploads      # 逐级确认 x（搜索）权限
find /var/lib/localcraft -user root -printf '%u:%g %m %p\n' | head -n 20
```

期望：目录 `drwxr-x--- localcraft localcraft`，数据库 `-rw-r----- localcraft localcraft`，env `-rw-r----- root localcraft`。修正：

```bash
chown -R localcraft:localcraft /var/lib/localcraft
chmod 0750 /var/lib/localcraft /var/lib/localcraft/files /var/lib/localcraft/backups
find /var/lib/localcraft/files -type d -exec chmod 0750 {} +
find /var/lib/localcraft/files -type f -exec chmod 0640 {} +
chown root:localcraft /etc/localcraft/localcraft.env && chmod 0640 /etc/localcraft/localcraft.env
```

权限看起来正常仍报 `Permission denied` 时按 docs/05 §12.7 查 SELinux（`ausearch -m avc -ts recent`、`audit2allow`），
不要直接关 SELinux。

### 6.6 wheel 装不上（含 aarch64）

典型报错：`Could not find a version that satisfies the requirement <包>` 或
`<包>.tar.gz is not a supported wheel on this platform`。

```bash

ls /opt/localcraft/releases/localcraft-*/wheelhouse-*/
ls /opt/localcraft/releases/localcraft-*/wheelhouse-aarch64/ | grep -E 'greenlet|pydantic_core'
```

处置：① 确认没把 x86_64 的 wheelhouse 拷到 aarch64 机器；② 按 §4.4 在目标架构上补做真实离线安装验证；

### 6.7 `/readyz` 不过

`/readyz` 会真实探测两件事：`DATA_DIR` 可写、数据库 `SELECT 1` 可通；任一失败返回 **503**。

```bash
curl -sS http://127.0.0.1:8000/readyz; echo
```

| `checks` 失败项 | 含义 | 处置 |
| --- | --- | --- |
| `storage` | `DATA_DIR` 不可写（只读挂载、磁盘满、SELinux、属主错） | §6.5 / §6.8 |
| `database` | 数据库连不上（路径错、权限、库损坏、锁死） | §6.2 / §6.5；确认四个斜杠 |
| 两项都 ok 但仍 503 | 极可能是经 nginx 探测而 nginx 侧超时 | 直连 8000 对比，按 §6.4 处理 |

> readiness 失败会让 `ExecStartPost=wait-healthy.sh` 超时，表现为「服务 active 但启动流程报失败」。
> 修复后 `systemctl restart localcraft.service`。

### 6.8 磁盘满

```bash
df -h; df -i
du -sh /var/lib/localcraft/* | sort -h
du -sh /var/lib/localcraft/backups/* | sort -h
ls -lh /var/lib/localcraft/localcraft.db*
journalctl --disk-usage
```

处置：① `journalctl --vacuum-size=1G`；② 清理 `/var/lib/localcraft/backups/pre-restore-*`（恢复脚本留下的回退点，
确认不再需要后删）；③ 调小 `LOCALCRAFT_BACKUP_KEEP_DB`/`_KEEP_FILES` 或手工删旧快照；④ 清理 `files/.trash/`
（孤儿文件清理的暂存区）；⑤ 用 `python -m app.cli purge-recycle-bin --days 30` 与
`python -m app.cli gc-versions --apply` 清理回收站与历史版本。
磁盘满是 WAL 膨胀与 `database is locked` 的常见上游原因，先解决空间再看其它告警。

### 6.9 WAL 膨胀

```bash
ls -lh /var/lib/localcraft/localcraft.db*
sqlite3 /var/lib/localcraft/localcraft.db 'PRAGMA journal_mode;'      # 期望 wal
sqlite3 /var/lib/localcraft/localcraft.db 'PRAGMA wal_checkpoint(TRUNCATE);'
ls -lh /var/lib/localcraft/localcraft.db-wal                          # 期望显著变小
```

WAL 靠 checkpoint 回收。长期 > 1 GB 的常见原因：磁盘满导致 checkpoint 失败、长事务一直持有读快照、
外部进程长期打开数据库。确认无长事务与外部会话后手工 checkpoint；必要时低峰重启服务。

## 7. 切换到 PostgreSQL

> **状态声明（重要）**：docs/02 §6.2 承诺「只改连接串 + 跑迁移」，并给出
> `python -m app.cli export-data` / `import-data` / `verify-integrity` 三条命令。
> **本手册未包含实测结论，参见 M4 报告**：仓库中找不到 PostgreSQL 迁移的实测证据，且上述三条子命令
> **在当前 `backend/app/cli.py` 中并不存在**（现有 `import-users`/`export-users` 只处理用户 CSV）。
> 另外 `psycopg` **不在** `backend/requirements.txt`/`requirements.lock` 里，也没打进 wheelhouse。
> 因此下面是**依据设计推导的操作草案**，执行前请先在测试环境完整验证。

前置条件：① 有可用的 PostgreSQL 实例与账号/库；② 在 venv 中手工安装 PG 驱动（离线环境需先把它下进 wheelhouse）：

```bash
/opt/localcraft/venv/bin/python -m pip install "psycopg[binary]"
/opt/localcraft/venv/bin/python -c "import psycopg; print(psycopg.__version__)"
```

③ 一份 `verify-backup.sh` 通过的 SQLite 备份 + env 文件副本。步骤草案：

```bash
# 1) 停服务 + 备份现状
systemctl stop localcraft.service
sudo -u localcraft /opt/localcraft/scripts/backup.sh
install -m 0600 /etc/localcraft/localcraft.env "/root/localcraft.env.sqlite-$(date +%Y%m%d)"

# 2) 只改连接串（其余配置不动）
cp /etc/localcraft/localcraft.env "/etc/localcraft/localcraft.env.bak-$(date +%Y%m%d)"
sed -i 's|^DATABASE_URL=.*|DATABASE_URL=postgresql+psycopg://localcraft:<密码>@<pg主机>:5432/localcraft|' /etc/localcraft/localcraft.env
grep '^DATABASE_URL=' /etc/localcraft/localcraft.env

# 3) 在空 PG 库上跑全量迁移
( set -a; . /etc/localcraft/localcraft.env; set +a; cd /opt/localcraft/app/current
  /opt/localcraft/venv/bin/alembic upgrade head; /opt/localcraft/venv/bin/alembic current )

# 4) 数据搬迁：当前 CLI 没有 export-data/import-data，需与研发确认方案；
#    搬迁后重建检索索引（**仅 SQLite/FTS5**；PostgreSQL 下该命令会明确报错并
#    以非 0 退出，因为 PG 部署不存在 FTS 虚表、检索由 LIKE 回退直接查 tools 表）
/opt/localcraft/venv/bin/python -m app.cli reindex-search

# 5) files/ 目录不变（换机时 rsync）；起服务并校验
systemctl start localcraft.service
/opt/localcraft/scripts/wait-healthy.sh --url http://127.0.0.1:8000/readyz --timeout 90
sqlite3 /var/lib/localcraft/localcraft.db 'SELECT COUNT(*) FROM tools;'    # 与 PG 侧对账
```

已知差异（执行前必须评估）：

| 项目 | SQLite | 切到 PG 后 |
| --- | --- | --- |
| 全文检索 | FTS5 虚表（迁移 `0003` 仅在 sqlite 方言下创建） | 自动回退 `LIKE` 匹配（`app/search/__init__.py`），**检索能力下降**；需另写 PG 版索引迁移 |
| `PRAGMA` 调优 | WAL / `busy_timeout` 仅对 SQLite 生效 | 不再执行；`DB_POOL_SIZE`/`DB_MAX_OVERFLOW` 可放大 |

## 附录 C：数据库迁移的 fix-forward 纪律（契约 §18.8）

### 规则

**一旦某个发布包（`tar.gz`）已经发出，或有人在任何环境执行过某条迁移，
该迁移文件即冻结 —— 只能新增迁移去修正，不得回改。**

这条纪律的理由：

1. **已执行的库不会回退。** Alembic 记录的是 `version_num`，不记录文件内容。
   改一个已执行过的迁移文件，不会让已有库发生变化，只会让**新库**与**老库**的
   结构产生静默差异 —— 这是最难排查的一类问题（本地全对、生产行为不同）。
2. **回滚路径会失效。** `downgrade()` 是照着当初的 `upgrade()` 写的。
   改了 `upgrade()` 而不改 `downgrade()`（或反过来），回滚就会得到第三种结构。
3. **审计链断裂。** 迁移文件是「结构变更的审计记录」。回改等于篡改历史记录。

### 正确的做法

发现迁移有问题时（例如字面量在另一种数据库上不合法）：

```bash
# 1) 不要动老迁移，新建一条
cd /opt/localcraft/app/current
/opt/localcraft/venv/bin/alembic revision -m "fix is_current predicate for pg"
# 2) 在新迁移里写「修正」语句（含针对性的 downgrade）
# 3) 本地与测试环境验证 upgrade + downgrade 都可执行
# 4) 随下一个发布包发出
```

### 本次例外（M4 → M5 的交代）

M4 修改了两条**已经写进仓库**的迁移：

| 迁移 | 改动 | 为什么被接受 |
| --- | --- | --- |
| `0001_initial_schema.py` | `WHERE is_current = 1` → `WHERE is_current IS TRUE` | 跨库修正，PG 上原写法直接报 `UndefinedFunction` |
| `0004_add_skill_tree_truncated.py` | `server_default="0"` → `"false"` | 跨库修正，PG 上布尔列不接受整型默认值 |

契约 §18.8 裁定**本次接受**，理由有两条且都必须成立：

1. **项目尚未有任何生产部署** —— 没有任何已执行的库会与新库不一致；
2. **两个改动在 SQLite 上语义完全等价** —— SQLite 里 `true` 就是 `1`，
   老库与新库的行为没有差别。

> **这是最后一次例外。** 从 M5 起，发布包一旦生成，上述两条迁移即冻结。
> 后续若还需修正，一律走新建迁移。
