# 优化点分析

**版本**：M5 checkpoint 之后（2025-03）
**方法**：所有结论均来自本机实测，脚本与命令见各节。**未实测的推测单独标注。**

---

## 0. 一句话结论

**此前对性能瓶颈的判断是错的，包括监控方在 `docs/01` 与 `docs/09` 里写下的那条。**

原来写的是「瓶颈是单 Python 进程的 CPU/GIL，源于 SQLite 单写者 → 单 uvicorn worker」。
实测显示：

- **SQLite 本身远不是瓶颈** —— 纯 DB 访问在 c=20 下能跑 **3968 req/s**
- **网络与事件循环也不是** —— `/healthz` 在 c=20 下跑 **3543 req/s**
- **序列化几乎是免费的** —— 24 条目全套 Pydantic 构造只要 **0.242 ms**
- **真正的现象是：CPU 时间随并发放大 11.6 倍**（每条目请求 4.87 ms → 56.28 ms）

这是**工作量放大**（overhead amplification），不是饱和。方向应该转向
「异步栈在高并发下的开销」而不是「加缓存减少查询」。

## 1. 实测数据（基础事实）

### 1.1 进程内单请求成本（无网络，`httpx.ASGITransport`）

| 端点 | 中位 | P95 | 查库次数 |
| --- | --- | --- | --- |
| `/healthz` | **0.279 ms** | 0.323 ms | 0 |
| `/readyz` | 0.708 ms | 0.835 ms | 1（探活） |
| `/api/v1/meta` | 0.946 ms | 1.064 ms | 1 |
| `/api/v1/tools?page_size=1` | 4.633 ms | 5.266 ms | ~4 |
| `/api/v1/tools?page_size=24` | 5.716 ms | 6.704 ms | ~4 |

**读法**：`page_size=1` 与 `24` 只差 **1.1 ms** → 每条目成本约 **0.05 ms**。
真正的成本是**列表端点的 ~4.6 ms 固定开销**（鉴权 + COUNT + facets + 查询 + ORM）。

### 1.2 序列化的成本（微基准，24 条目）

| 步骤 | 耗时 | 占比 |
| --- | --- | --- |
| A `ORM → Pydantic`（含完整校验） | 0.242 ms | 100% |
| B 纯构造 `model_construct` | 0.070 ms | 29% |
| C 仅 `model_dump(mode="json")` | 0.116 ms | 48% |

**Pydantic 校验占构造开销的 71%** —— 听起来很多，但绝对量只有 **0.17 ms**。
**它不是瓶颈。**（数据来自 ORM，本身已强类型，校验确实是冗余的，但省它也省不出多少。）

### 1.3 并发梯度（真实 HTTP，`ab -k`，c=20）

| 端点 | 查库 | req/s |
| --- | --- | --- |
| `/healthz` | 0 | **3542** |
| `/api/v1/meta` | 1 | **981** |
| `/api/v1/categories` | 1 聚合 | **284** |
| `/api/v1/tools?page_size=1` | 4 | **218** |
| `/api/v1/tools?page=2&page_size=24`（不算 facets） | ~3 | **167** |
| `/api/v1/tools?page_size=24` | 4 | **57** |

**读法**：吞吐随「每请求的 DB 工作量」急剧下降，且从 4 查询 / 1 行到 4 查询 / 24 行掉了 3.8 倍 ——
**远超序列化的 1.1 ms 所能解释**。

### 1.4 ★ CPU 时间随并发放大（最关键的一节）

同一台机器、同一构建、真实 HTTP，`/api/v1/tools?page_size=24`：

| 并发 | 墙钟 ms/req | **CPU ms/req** | 吞吐 req/s |
| --- | --- | --- | --- |
| 1 | 5.901 | **4.866** | 169.5 |
| 5 | 6.976 | 10.380 | 143.4 |
| 10 | 16.220 | 45.800 | 61.7 |
| 20 | 18.580 | **56.276** | 53.8 |
| 50 | 18.640 | 56.395 | 53.6 |

**CPU 时间从 4.87 ms 涨到 56.28 ms（11.6 倍），而吞吐从 169 掉到 54。**

如果是「单进程 CPU 饱和」，CPU/请求应当**恒定**（约 5 ms），吞吐在某个点上平台化。
实测 CPU/请求**随并发增长**，说明**每个请求做的事变多了**，而不是「同样的事排队」。

> **这是本轮推翻旧结论的核心证据。** `docs/01` 与 `docs/09` §10.2 里
> 「成本随条目数近似线性 → 瓶颈是每条目的 CPU 开销」这个推论，
> 只解释了**低并发下**的成本结构，没有解释**高并发下的放大**。

### 1.5 隔离实验：池与 `pool_pre_ping`

只做「取连接 + `SELECT 1`」，c=20，100 次：

| 配置 | CPU ms/req | 吞吐 req/s |
| --- | --- | --- |
| `pool_pre_ping=True`，pool=5+10 | 1.155 | 3000 |
| **`pool_pre_ping=False`**，pool=5+10 | **0.840** | **3968（+32%）** |
| `pool_pre_ping=True`，pool=50+50 | 1.111 | 3095 |
| `pool_pre_ping=False`，pool=50+50 | 1.080 | 3977 |

**两个结论**：

1. **`pool_pre_ping=True` 让每次查询多花约 27% CPU** —— 而对**本地 SQLite 文件**它是纯浪费
   （本地文件不会像网络连接那样"悄悄断掉"，pre-ping 只是白加一次往返）
2. **池大小完全不影响**（50+50 ≈ 5+10）→ **「连接池耗尽」的假设被证伪**

### 1.6 压测工具本身会污染结论

同一服务、同一端点 `/healthz`、同为 c=20：

| 工具 | req/s |
| --- | --- |
| `ab -k` | **3592** |
| Python `httpx` async 客户端 | **332** |

**差 10.8 倍。** Python 客户端在 c=20 时就自己饱和了。

这意味着：**`m4-drill-perf.sh` 里用 `ab` 测读接口、用自写 Python 脚本测下载，
两者的数字不可比**；而且任何用 Python 客户端做的对比实验，量到的可能主要是客户端。

### 2.5 ★ O4 实验结果（M7，2025-09）—— 归因从「异步栈」改写到「aiosqlite 的线程跳」

**假设（原文）**：`aiosqlite` + greenlet 桥接 + 线程池在 GIL 下的上下文切换开销导致 CPU 放大，
并推测「若 async 显著更差，考虑 SQLite 场景改用同步栈」。

**做法**：逐字重放从生产 app 抓下来的**同一批 18 条 SQL**，三套栈 × 5 个并发梯度 ×
每配置 5 次独立测量取中位数。

| 并发 | async（aiosqlite，生产同款） | sync（stdlib sqlite3 + `run_in_threadpool` + NullPool） | **async-thread**（stdlib sqlite3 经 `greenlet_spawn`，**只换掉 aiosqlite**） |
| --- | --- | --- | --- |
| 1 | 0.070 ms/req | 0.041 | **0.025** |
| 10 | 0.609 | 0.408 | 0.025 |
| 50 | **0.547** | 0.601 | **0.033** |
| **放大倍数（c=1→c=50）** | **7.8×** | **14.6×** | **1.3×** |

`/healthz` 控制组：两栈 CPU 恒为 0.001–0.002 ms/req，吞吐 9k→31k req/s
→ **ASGI/HTTP 层不放大**，问题确实在数据库访问层。

**结论**：

1. **放大真实存在**（async 7.8×），与 §1.4 的现象一致，方向成立。
2. **但放大器不是「async/greenlet」这一层**。变体 C 只把 `aiosqlite` 换成 stdlib `sqlite3`
   （保留 async/await + `greenlet_spawn` + 同样的语句缓存），放大从 **7.8× 降到 1.3×**，
   CPU/请求在 c=1 时就低 2.8 倍。所以主要开销来自 **`aiosqlite` 的专用工作线程那一跳**
   （每语句 `call_soon_threadsafe` + 跨线程 future + GIL 竞争）。
3. **★ 「改用同步栈」这条候选方向被本实验否掉。** sync 变体在 c=50 下 CPU/请求 0.601 ms，
   **比 async 的 0.547 还高**，放大 14.6× 更严重 —— 它只是把跳数从「aiosqlite 线程」
   换成「anyio 线程池线程 + 锁」，同一个 GIL 竞争仍在。
4. **下一步应走 O7（PG + 多 worker）**，不是换同步栈。
5. **变体 C 的好成绩不可照搬生产**：它把同步 `sqlite3` 调用放在事件循环线程上，
   只有「本地文件 + 亚毫秒查询」才成立；换成网络数据库会把整条事件循环阻塞住。

**方法学（为什么相信它）**：客户端是 C 多线程独立进程（`scripts/bench-loadgen.c`），
并**单独测量客户端自身 CPU** —— 全部数据点客户端 ≤0.013 核（10 核机器），
无一组触及客户端瓶颈。这是对 §1.6「压测工具本身会污染结论」的直接应对：
同为 c=20 时 `ab -k` 是 3592 req/s 而 Python httpx 只有 332 req/s（差 10.8 倍），
所以两者都不能用来测「服务端 CPU/请求」。

**已知弱点（不掩盖）**：`sync` 变体用 NullPool 是为了绕开「sqlite3 连接不能跨线程」的
不得已选择，其成本里含连接创建，故**该行的绝对值不能与 async 直接比**，只能看放大趋势；
结论在 async-thread 变体上得到交叉验证。

**未验证**：全部数字来自 **macOS / Apple M4 / 单 worker / SQLite**。
`docs/11` §2.4 O11 要求的 openEuler 目标硬件重测**未做**。

## 5. 需要修正的既有结论（监控方的错，记录在案）

| 位置 | 原文 | 实测后 |
| --- | --- | --- |
| `docs/09` §10.2 | 「瓶颈是每个条目的 CPU 开销（ORM 实例化 → Pydantic 校验 → JSON 编码）」 | **不完整**。序列化只占 0.24 ms / 24 条；真正现象是 **CPU 随并发放大 11.6 倍** |
| `docs/01` NFR-PERF-01 | 「瓶颈是单 Python 进程的 CPU/GIL，源于 SQLite 单写者 → 单 worker」 | **因果链未证实**。SQLite 纯 DB 访问能跑 3968 req/s；`/healthz` 能跑 3543 req/s。**M7 的 O4 进一步定位：放大来自 `aiosqlite` 的工作线程跳，不是 SQLite 本身，也不是 async/greenlet 这一层（见 §2.5）** |
| `docs/09` §10.3 | 「若需要更高并发，正确方向是降低每条目序列化成本」 | **方向偏了**。应优先验 O4（异步栈开销），序列化不是主要矛盾 |
| §18.3 / §20.2 的并发阶梯 | 拐点在 10~15 并发 | **拐点真实存在**，但归因需要改写；且 `ab` 与 Python 客户端混用使部分数字不可比 |

> **教训**：`docs/09` §10.2 那次的成本定位实验（按 `page_size` 梯度测）本身是对的，
> 但它只覆盖了「单请求内的成本结构」，**没有做「同一请求在不同并发下的成本对比」**，
> 因此把一个并发相关的现象误读成了串行成本结构。
> 新增一条方法论要求：**性能结论必须同时给出「随参数变化」与「随并发变化」两组数据。**
