### 1.5 实现图片签名能力 URL（监控方遗漏，必须补做）

`contracts/CONTRACT.md` §14.3 裁定「图片改为签名能力 URL」，但该裁定是在前端 M1 复盘时作出的，
**当时后端的 M2 任务书已经发出，M3 也没带上 —— 这个决定从未传达到实现方。这是监控方的流程失误。**

**当前实际状况**：`GET /api/v1/images/{id}` 只接受 `Authorization` 头，而 `<img>` 无法携带鉴权头，
refresh cookie 又被限制在 `Path=/api/v1/auth`。因此**真实环境下所有封面与截图必然 404**。

**要做**：

- 后端在列表/详情响应里下发带签名的 `cover_url` / `thumb_url`，形如
  `/api/v1/images/88?variant=thumb&sig=<hmac>`
- `sig` = HMAC-SHA256(从 `SECRET_KEY` **派生的子密钥**, `"{image_id}|{variant}"`)，
  有效期由新设置项 `images.signature_ttl_hours` 控制，默认 **168**（7 天）。
  派生方式与下载票据一致（不要直接复用主密钥）
- `GET /api/v1/images/{id}` 接受**两条鉴权路径**：有效 `sig`，**或**有效 `Authorization` 头
  （后者供脚本/API 用）。两者都无 → `404`
- 签名比对用 `hmac.compare_digest`（常量时间）
- 前端**无需改动**：它已按 §14.3「原样使用后端下发的 URL」实现，并保留了 `onError` 占位降级。
  URL 带上 `sig` 之后自然生效

**注意接口面冻结**：这不新增接口，只改现有接口的响应字段与鉴权方式，92 操作数不变。

**补测试**：有效签名可取图、篡改签名 404、无签名无 Header 404、带 Header 可取图。

## 易错点清单

**备份恢复类（最容易出事故）**

1. **SQLite 在 WAL 模式下不能直接 `cp` 数据库文件**。必须用 `.backup` 或 `VACUUM INTO`
2. **恢复前必须清理 `-wal` / `-shm`**，否则恢复出损坏的库
3. **恢复演练必须真的删数据再恢复**，只验证「备份文件存在」等于没验证
4. 备份要包含 `files/`，只备数据库会恢复出一个「有记录没文件」的库
5. `SECRET_KEY` 不在数据库里，恢复后如果密钥变了，所有 Token 与签名 URL 全部失效 ——
   演练时要确认密钥的处置方式

**离线打包类**

6. **`--only-binary=:all:` 若找不到 wheel 会静默退化或报错**，必须检查产物里有没有 `.tar.gz`
7. **manylinux 标签不向上兼容**：`manylinux2014`（= `manylinux_2_17`）的 wheel 能在
   更新的 glibc 上跑，反之不行。openEuler 24.03 的 glibc 2.38 较新，所以
   `manylinux_2_17` / `manylinux_2_28` 都可用
8. **纯 Python wheel 是 `py3-none-any`**，两套 wheelhouse 里都会有，架构差异清单要能区分

**清理类**

9. **清理任务必须幂等且分批**，否则长事务会锁库
10. **孤儿文件清理先移入 `.trash` 再删**，给误删留后悔时间（`docs/02` §5 有此要求）
11. **删除前先确认没有被引用**，`tool_acl.subject_id` 是多态外键，数据库不会拦你

**性能类**

12. **不要为了让 benchmark 好看而加缓存然后不说明**。如果加了，要在报告里写明缓存策略与失效条件
13. **并发测试要确认服务是单 worker**（`docs/05` §6.3 的约定），多 worker 的结果没有意义
