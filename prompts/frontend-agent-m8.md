## ⚠️ 关于并行开发的类型依赖（先读这一节）

后端的 M8 与本轮**并行**进行，它会重新生成 `backend/openapi.json`，
而 `npm run check:api-types` 会读它生成前端类型。

**因此**：

- 你的新增 API 调用**照 `contracts/CONTRACT.md` §23 的形状写**，不要等 openapi.json。
- 在收尾时如果 `check:api-types` **因后端尚未落地**而失败，
  报告里要说清是**执行顺序造成的暂时现象**，而**不是**你的缺陷 ——
  但你必须先确认失败的**具体内容**确实是「后端新端点还没出现在 openapi.json 里」，
  而不是你自己写错了类型。**不要把任何失败都归给后端。**
- 这也意味着 `docs/12` §U2 那个「用错 token」的教训依然适用。

## 本轮的 6 项任务

### F7 · 收藏

1. **卡片星标**：门户卡片右上角加收藏切换（已收藏/未收藏两态，视觉要明确）。
   未登录时**不显示按钮**，只显示计数 —— 与既有的「登录后可下载」文案处理保持一致，
   不要造两套不同的匿名策略。
2. **详情页**：`ToolDetailPage` 标题区加收藏按钮。
3. **「我的收藏」页面**：新增路由与页面，接 `GET /api/v1/me/favorites`，
   **复用门户工具列表项组件**，不要新写一套卡片。
4. **入口**：门户左侧导航加「我的收藏」项（**匿名不显示**），并在 `UserMenu` 里加直达链接。
5. **乐观更新**：收藏要立刻反馈，失败要回滚且给出提示。用 TanStack Query 的既有模式，
   不要手写状态机。**注意**：回滚时要让计数与按钮状态**一起**回滚，不要只回滚一个。

### F8 · 点赞

1. **详情页**加点赞按钮（切换态 + 整数计数）。
2. **卡片上只显示计数，不放可点按钮** —— 卡片已经很密，避免误触。
3. 按契约 §23.7：**只做整数计数，不做 1~5 平均分、不做星星**。
   后端也不会给平均分，不要自己算。

### F9 · 上传去重提示

**先读契约 §23.2 —— 它解释了为什么不在浏览器里算 SHA-256**
（`crypto.subtle` 需要安全上下文，而本项目按 D39 用 `http://<ip>:<port>` 直连，
该 API 在此场景下 `undefined`）。

所以：**不要引入任何客户端哈希**。去重信息由上传响应回带（后端 B9）。
你要做的是：

- 上传成功后，若响应里带了「与工具 X 的版本 Y 完全相同」这类信息，
  展示一条**非阻塞**提示（可关闭），并提供跳转到该工具的链接。
- 提示**不能**挡住「上传成功」这个事实 —— 上传是成功的，只是提示可能重复。
- 后端字段名以 `backend/openapi.json` 为准（或按后端在 `contracts/CONTRACT.md`
  §23 之后登记的字段名对接）。**若后端还没落地，先按约定字段写好并在报告里说明。**
- 复用 `CopyButton.tsx` 的守卫惯例：任何依赖浏览器能力的代码都要有**降级路径**，
  **不允许**因为某个 API 不存在就白屏或抛错。

### F10 · 工具表单新增「预计节省时长」

`ToolForm` 加一个可选字段 `estimated_saving_minutes`（契约 §23.5）：

- 校验 **1 ~ 1440** 的整数，**允许留空**。
- 界面要**明确说明这是「单次使用的预计节省分钟数」**，并且说明它会用于平台的效率估算。
  **不要让用户以为不填就没事** —— 留空会让该工具从估算里消失。
  显示当前填写率之类的提示更好，但至少要有这一句说明。
- 留空必须真的提交 `null`，**不要**提交 0（契约 §23.5 明确说 `NULL` 不等于 0）。

### F11 · 管理台数字概览增强

接 `GET /api/v1/admin/stats/insights`（形状见契约 §23.6），在**既有**管理台概览页上扩展，
显示：30 日下载趋势、活跃贡献者、分类分布、效率估算。

**契约 §23.6 与 §23.8 对展示方式有硬约束，照做**：

1. **禁止把 30 日趋势画成图表**（D10 / D35：数字与列表，不做图表；不新增图表依赖）。
   用**数字 + 迷你列表/进度条**这类无依赖的形式表达即可。
2. **效率估算的展示是本次最容易做错的一项**。`savings.basis` 是常量
   `"author_estimate"`，它的存在就是为了让前端**无法**脱离口径单独渲染数字。
   你**必须同时展示**：
   - 口径文案：明确写出这是**基于工具作者自述的估算，非实测**
   - 覆盖率：`covered_tool_count / total_tool_count`（并说明有多少工具未填、未计入）
   - `total_minutes` 换算成人日/人时后**仍要保留「估算」标注**

   **绝对禁止**只显示一个孤零零的「已节省 320 人时」。
   这个数字会被拿去汇报，脱离口径就是误导。
3. 若 `total_tool_count` 里**绝大多数工具都没填**（覆盖率很低），
   要**显式提示数据不足以支撑结论**，而不是把这个大数字漂亮地摆出来。

### F12 · Mock 与 E2E

1. `web/src/mocks/handlers.ts` 补上本轮所有新端点与新字段，
   mock 数据要能覆盖：未登录、已登录未收藏、已登录已收藏、计数非零 四种情况。
2. mock E2E 基线 **79 passed**、真机 E2E **16 passed**，**不得回归**。
3. 新增的收藏/点赞交互要**有 e2e 覆盖**（至少：收藏后计数 +1、取消后 -1、
   刷新后状态保持）。
4. **测试之间不要互相污染** —— 收藏/点赞是**有状态**的，mock 里要能重置。
   这是本轮最容易造成 flaky 的地方，请显式处理。

## 通用硬约束

1. **`npm run verify` 必须通过**（`check:api-types` 的并行期例外见上文约定）。
2. **对比度**：新增/改动的颜色必须过 WCAG AA；**禁止硬编码 `text-white`**，
   一律用语义令牌（`docs/12` §U2 就是这个教训）。把实测数字写进报告。
3. **主题三态**：light / dark / system 都要验。
4. **无障碍**：图标按钮必须有可访问名；收藏/点赞是**切换**控件，
   要用 `aria-pressed` 或等价语义，不能只靠颜色区分状态。
5. 不新增运行时依赖；不升级既有依赖版本。
6. 遵守既有代码风格（TS strict，无 `any`，组件与 hooks 分层，Query key 走既有约定）。
