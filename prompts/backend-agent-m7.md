## 本轮的 4 项任务

### B1 · O12：每请求 SQL 条数计数器 + 回归断言

`docs/11` §2.4 O12：现在**没有 SQL 条数统计**，N+1 悄悄回归了看不出来。

1. 用 SQLAlchemy 的 `before_cursor_execute` 事件挂一个**只在测试/调试下启用**的计数器
   （生产默认关闭，不要给每个请求增加常数开销）。
2. 在热读端点上加**查询数上限断言**：至少覆盖门户列表与工具详情。
   门户列表当前已知是 **4 条查询**（见 §2.2 O5），把它固化成断言。
3. **不要**在本轮做 O5 的查询合并 —— 那是 O4 出结论之后的事。

> 注意：断言写太死会在合理改动时假报警。用「上限」而不是「精确等于」的地方就用上限，
> 并在报告里说明你每个断言为什么选这个数字。

### B2 · M2：慢请求告警日志

`docs/11` §3.4 M2：结构化日志有耗时字段，但**无阈值告警**。

超过阈值的请求单独 `warn`，日志里**必须带 `request_id`** 以便对账。
阈值走环境变量，给一个合理默认值，并登记到 `docs/05` §14.2 会覆盖的位置
——**但 `docs/` 你不能改**，所以请在报告里给出你要新增的变量名、类型、默认值，
由监控方补文档。

### B3 · M1：`/metrics` 端点（Prometheus 文本格式）

`docs/11` §3.4 M1：现在只有 `/healthz` / `/readyz`，没有指标。

暴露：请求数、P50/P95、每端点 SQL 条数、连接池等待时长、WAL 大小。

**监控方裁定（几条硬要求，照做）**：

1. **`/metrics` 位于 `/api/v1` 冻结面之外**，**不**计入 93 operations / 75 paths 的冻结基线。
2. **必须 `include_in_schema=False`**，即**不得**出现在 `backend/openapi.json` 里。
   理由：前端有 `check:api-types` 会读 `openapi.json` 生成类型，
   把运维端点塞进去会制造一次无意义的前后端耦合与跨 agent 破坏。
3. **默认关闭**：只有 `LOCALCRAFT_METRICS_ENABLED=true` 时才注册该路由。
4. **默认不可匿名读**：要求 `Authorization: Bearer <LOCALCRAFT_METRICS_TOKEN>`，
   或请求来源为 `127.0.0.1`。**未配置 token 且非本机来源时必须 404 或 401，
   绝不能裸奔**。这是一个内网平台，但指标里可能含端点名与用量分布，不要假设内网即安全。
5. **注意全局鉴权依赖**：确认新增路由不会被现有的强制认证中间件拦成 401 而无法按
   上面的规则工作，两者要能共存。这是本次最容易踩的集成问题。
6. **禁止引入 Prometheus 客户端依赖**。手写文本格式输出即可（格式很简单），
   项目重视离线可安装与依赖最小化。

### B4 · O4：sync vs async 对比实验（**出结论，不改架构**）

`docs/11` §1.4 测到 **CPU 时间随并发放大**（4.79 ms → 46.36 ms，约 10 倍），
§2.1 的 O1~O3 只降低了常数项，**没有触及放大本身**。§2.2 O4 是定位根因的关键实验。

假设：`aiosqlite` + greenlet 桥接 + 线程池在 GIL 下的上下文切换开销导致放大。
对比组：同步 SQLAlchemy + `run_in_threadpool`（或同步 worker）。

**监控方裁定**：

1. **本轮只做实验和测量，不得改动 `backend/app/` 的生产代码路径。**
   实验代码放在独立脚本或用测试内联的对照实现。
2. 脚本放 `scripts/`，命名体现用途（如 `scripts/bench-sync-vs-async.py`）。
3. **必须报 CPU/请求**（`process_time()`），不能只报延迟和吞吐 —— §2.4 O10 就是这个教训。
4. **必须遵守 §1.6 的教训**：压测工具本身会污染结论。说明你如何排除工具影响。
5. 结论**允许是"假设不成立"或"差异不显著"**。不要为了交差把噪声说成发现。
   若差异不显著，就如实说，并给出下一步（如转 PG + 多 worker，§2.3 O7）。
6. 报告里给出：原始数字表、实验条件、以及**你为什么相信这个结论**（对照是否干净）。

## 通用硬约束

1. **后端测试基线是 465 passed**，不得回归。
2. **不得修改 `/api/v1` 已冻结的 93 个操作的请求/响应形状**。若确实发现必须改，先停下来报告，不要自行改。
3. 不新增运行时依赖（B3 已明确禁止 Prometheus 客户端）。
4. 遵守既有代码风格：Python 3.11 语法目标、SQLAlchemy 2.0 async 风格、Pydantic v2、
   类型注解齐全。本机 Python 可能是 3.13，**代码必须能在 3.11 上跑**
   （`docs/00` D34，已有静态守卫，别绕过它）。
5. **SQLite 与 PostgreSQL 两种方言都要考虑**。你是可以跑 SQLite 的；
   PG 的路径如果你的改动会碰（如 `metrics` 的 WAL 大小显然只适用于 SQLite），
   要做好方言判断，**在报告里明确说明哪些部分未在 PG 上验证**。
6. **`scripts/` 下的 shell 脚本**：bash 3.2 兼容性有守卫（见 `backend/tests/test_shell_portability.py`）。
   `$VAR` 后面紧跟全角字符会崩，用 `${VAR}` 包起来。
