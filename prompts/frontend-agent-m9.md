## 缺陷描述（监控方用真机后端实测，非推断）

```
viewer 登录                         → ✅ 成功
PUT  /api/v1/tools/{slug}/favorite  → 403「需要以下角色之一：approver, superadmin, user」
PUT  /api/v1/tools/{slug}/like      → 403
GET  /api/v1/me/favorites           → 200
```

后端 `engagement_guard`（`backend/app/api/v1/tools.py:67`）要求
`user` / `approver` / `superadmin`，**不含 `viewer`**。
而前端 `EngagementActions` 与卡片星标**完全不区分角色**，所以 viewer 会看到
收藏/点赞控件，**点下去必定报错**。

**根因是契约漏规定了角色**（§23.4 只冻结了形状与幂等语义），两个 agent 各做了
合理但相反的假设。**裁定：后端胜出，`viewer` 不可收藏/点赞，前端隐藏控件。**

## 任务

### T1 · 对 `viewer` 隐藏收藏/点赞控件（主要任务）

**监控方裁定，照做**：

1. **`viewer` 角色下不渲染可交互的收藏/点赞按钮。**
   覆盖全部出现位置：门户卡片星标、工具详情页、我的收藏页，
   以及任何其它你能找到的入口。
2. **给出原因，不要静默消失**。沿用既有下载按钮的处理方式
   （「当前角色无下载权限」那一套），让用户知道是权限问题而不是坏了。
   具体文案你定，但要与既有文案风格一致、且**不要泄漏内部角色名**。
3. **计数照常显示**。`favorite_count` / `like_count` 是全站可见的公共数字，
   `viewer` 只是不能投票，不是看不见。
4. **隐藏方式要处理"角色未知"这一态**：用户信息还没加载完时不要闪一下按钮再消失
   （既有的下载按钮应该已经有处理，照抄它的做法）。
5. **`/me/favorites` 路由与左栏入口**：裁定是 `viewer` 不能收藏，
   所以这些入口对 `viewer` **也应隐藏**。**但**：`GET /api/v1/me/favorites`
   后端是放行的（200），所以如果你判定保留入口更简单，也可以保留并显示
   空态 —— **二选一，在报告里说明你选了哪个以及为什么**。
6. **不要改动非 `viewer` 角色的任何行为**。`user` / `approver` / `superadmin`
   的收藏点赞必须与 M8 完全一致（含乐观更新语义）。
